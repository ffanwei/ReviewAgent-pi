# 为什么 OCR 在 91 条交集上大幅领先 review-pi

数据口径：91 条交集 / 588 GT；同一 judge（`deepseek-v4-pro`）、文件级语义指标、单轮。
OCR：`open-code-review v1.13.10` + `deepseek-v4.1-flash`；review-pi：`0.6.1` + `deepseek-v4.1-flash`。

## 0. 核心结论

差距的核心不是“模型判得准不准”，而是 review-pi 缺少 OCR 的**确定性审查范围层 + precision-first 输出纪律**。

- **模型能力不是瓶颈**：同一模型，二者在“有 GT 的文件内”的命中率几乎相同（38.1% vs 36.7%）。
- **输出纪律差距**：review-pi 13.6 条/PR vs OCR 6.6；无 GT 意见 978 vs 108。
- **输入靶向差距**：review-pi 的评论覆盖 807 个文件（其中 643 个无 GT 文件），OCR 评论落在
  213 个 (instance, file) 上（75 个无 GT 文件）；GT 文件覆盖 74 vs 138。
- **只压输出量不够**：即使做 top 8 / 每文件 3 条的预算，on-GT share 也只到 30.3%，远低于 OCR 的 82.0%；
  还需要输入侧的确定性文件选择/规则匹配。

一句话：OCR 是“确定性工程 + Agent”，review-pi 目前更像“通用 Agent + 证据门”；
差距在围绕模型的工程层，不在模型本身。

## 1. 直接原因：意见落在“有 GT 的文件”上的比例

| 指标 | OCR | review-pi |
|---|---:|---:|
| 生成意见 | 601 | 1242 |
| 落在有 GT 的文件 | **493（82.0%）** | **264（21.3%）** |
| 落在无 GT 的文件 | 108（18.0%） | **978（78.7%）** |
| 有 GT 文件内命中新 GT | 188 | 97 |
| 有 GT 文件内重复命中 | 18 | 8 |
| 有 GT 文件内未命中 | 287 | 159 |
| **有 GT 文件内命中率** | **38.1%** | **36.7%** |

**关键：两者在“有 GT 的文件内”的命中率几乎一样（38.1% vs 36.7%）。** 总 precision 的 4 倍差距，
主要不是语义理解差，而是 review-pi 把 79% 的意见花在了没有 GT 的文件上，而 OCR 只花 18%。

反事实估算：

- 如果 review-pi 也有 OCR 的靶向比例：`0.820 × 0.367 ≈ 0.301`，接近 OCR 的 0.313；
- 如果 OCR 只有 review-pi 的靶向比例：`0.213 × 0.381 ≈ 0.081`，接近 review-pi 的 0.078。

**precision 差距基本可以由“文件靶向”解释。**

## 2. 召回差距：覆盖的 GT 文件和上下文级别都更多

| 指标 | OCR | review-pi |
|---|---:|---:|
| 覆盖的 GT 文件 | **138 / 272（50.7%）** | 74 / 272（27.2%） |
| Diff Level GT | 109 / 257（42.4%） | 50 / 257（19.5%） |
| File Level GT | 67 / 218（30.7%） | 38 / 218（17.4%） |
| Repo Level GT | 41 / 113（36.3%） | 18 / 113（15.9%） |
| 总覆盖 GT | **217 / 588（36.9%）** | 106 / 588（18.0%） |

OCR 在三种上下文级别上都约为 review-pi 的 2 倍，不只是 diff 行内；说明差距不是“行号定位”或
`findingScope` 造成的（本次 review-pi 的 `findingScope` 已关闭）。

按 category：

| 类别 | OCR 覆盖 | review-pi 覆盖 |
|---|---:|---:|
| Code Defect | 157/404（38.9%） | 78/404（19.3%） |
| Maintainability / Readability | 21/101（20.8%） | 7/101（6.9%） |
| Performance | 29/57（50.9%） | 12/57（21.1%） |
| Security Vulnerability | 10/26（38.5%） | 9/26（34.6%） |

Defect / Performance / Maintainability 差距最大；Security 两者接近。

## 3. review-pi 的“多而散”

- review-pi 平均每条样本生成 **13.6** 条意见，OCR 为 **6.6** 条；但 GT 平均只有 6.5 条。
- review-pi 的 978 条无 GT 文件意见分布在 **686 个 (instance, file) 组合**（643 个唯一路径）；
  OCR 的 108 条无 GT 文件意见只分布在 **75 个 (instance, file) 组合**——差约 **9 倍**。
- 两边在每个非 GT 文件上的意见密度差不多（约 1.4–1.5 条/文件），差别是**触碰了多少个非 GT 文件**。
- review-pi 的 978 条无 GT 意见并不只是 style：

| 类别 | 非 GT 文件上的意见 |
|---|---:|
| 可靠性 | 475 |
| 可维护 | 238 |
| 可读性 | 101 |
| 性能 | 48 |
| 安全 | 44 |
| 可移植 | 43 |
| 可测试性 | 18 |
| 可维护性（拼写变体） | 11 |
| **合计** | **978** |

严重级：P2 516、P1 139、P3 321、P0 2。**大部分是 P1/P2 的“可靠性”意见**，模型确实认为它们是问题，
只是 AACR 的 GT 没有标注这些文件。

- review-pi 无 GT 意见最集中的样本：`ragflow` 65、`FreeCAD` 57、`immich` 55、`vllm` 49、`keycloak` 48——
  都是大仓库/大 diff 样本；smoke10 恰好没有充分覆盖这些样本，所以看起来两者接近。
- 规模背景：91 条交集有 **7,640** 个 changed 文件，但只有 **272** 个文件带 GT；OCR 审查了 **512** 个文件、
  评论落在 **213** 个 (instance, file) 上（138 个 GT 文件 + 75 个非 GT 文件）；review-pi 的评论覆盖
  **807** 个唯一文件。review-pi 的“文件广度”明显更大。

### 3.1 为什么 review-pi 铺到这么多非 GT 文件

1. **默认纪律是“证据优先”，不是“精度优先”。**
   - review-pi 的 “No Evidence, No Finding” 只保证“有证据”，不保证“值得报”；
   - 它没有“不确定就沉默、style/idiom 默认不报、只报本次 diff 引入的问题”的硬规则；
   - OCR 的规则文档明确写 “Favor precision over recall… stay silent when the surrounding context is unclear…
     style or idiom suggestions as non-blocking”。

2. **本次没有加载规则 Skill。**
   - OCR 默认有内置的语言/文件规则层（`system_rules.json` + `rule_docs/*`）；
   - review-pi 的 benchmark arm2 是**无规则包**的通用 Agent 形态，靠通用判断，容易把
     “可靠性/可维护性”意见铺到大量未标注文件。

3. **没有意见预算/密度目标。**
   - 13.6 条/样本 vs GT 6.5 条；
   - 没有 max per PR / max per file 的输出约束，门禁只保证“有证据”。

4. **文件过滤比 OCR 弱。**
   - review-pi 的 `mrFilter` 只有 md/lock/fixtures/snap 等少量模式；OCR 有扩展名 allowlist、默认路径排除、
     密钥/二进制/删除/超大文件筛选；
   - 但这次 978 条非 GT 意见大多是 `.ts/.py/.java/.go/.c/.js` 代码文件，**文件类型过滤不是主因**；
     主因是“对代码文件也报得太多”。

5. **GT 本身稀疏。**
   - 7,640 个 changed 文件里只有 272 个带 GT；两边都会看到大量未标注文件；
   - review-pi 报得多，自然撞上更多“无 GT”文件；这 978 条里有一部分可能是**真实但未标注**的问题。

6. **不是 `findingScope` 的问题。**
   - arm2 的 1,242 条意见里只有 40 条在 hunk 外 / 文件不在 diff；
   - 978 条非 GT 意见绝大多数在 changed 文件内，scope 开关拦不住。

一句话因果链：**没有 precision-first 规则 + 没有规则 Skill + 没有意见预算 + 通用 Agent 广泛探索
→ 13.6 条/样本 → 铺到 686 个非 GT 文件组合 → 978 条进入 precision 分母 → precision 7.8%。**

### 3.2 按 PR 规模分层：小 PR 接近，大 PR 差距扩大

- 按 **changed files**：≤5 文件 B 0.328 vs 0.327（几乎打平）；6–15 文件 +0.034；
  16–40 文件 +0.180；>40 文件 **0.046 vs 0.353（+0.307）**。
- 按 **diff 字节**：<50KB +0.038；50–200KB +0.229；>500KB +0.295。
- 按 **changed lines**：所有箱差距都在 +0.21～+0.26，说明“改动行数”不是好变量；
  驱动因素是**文件广度/diff 足迹**。

完整表见 [`size-stratification.md`](size-stratification.md)。这也解释了 smoke10/iter20
为什么接近：它们优先选小 diff/短耗时样本，天然落在“接近”区间。

## 4. 内部拦截链不是主因

91 条 ok 样本的 review-pi 审计汇总：

| 阶段 | 拒绝数 |
|---|---:|
| VERIFICATION_FAILED | 38 |
| DUPLICATE_ID | 113 |
| NO_EVIDENCE | 0 |
| OUT_OF_SCOPE | 0 |

- 38 条验证失败会损失一些召回，但相对 482 条未覆盖 GT 不是主因；
- 113 条重复说明 review-pi 在反复报同一批问题，但没有转化为更广的 GT 覆盖；
- `findingScope` 本次关闭，`OUT_OF_SCOPE = 0`，所以不是 scope 过滤造成的。

## 5. 效率：按“每覆盖一条 GT”算

| 指标 | OCR | review-pi |
|---|---:|---:|
| 每条覆盖 GT 需要生成意见 | 2.77 条 | 11.72 条 |
| 每条覆盖 GT 消耗总 token | 915K | 1.89M |
| 每条覆盖 GT 消耗非缓存 token | 137K | 178K |
| 每条覆盖 GT 耗时 | 124s | 407s |

review-pi 的“意见量大”没有转化为覆盖：覆盖一条 GT 需要 4.2 倍的意见数、2.1 倍的总 token、3.3 倍的时间。

## 6. 结构性解释

- **OCR**：确定性工程层负责选文件、分组、规则匹配、评论定位/过滤，Agent 只在被选中的文件/规则上工作。
  结果是意见集中、每个 PR 意见数接近 GT、82% 落在有 GT 的文件上。
- **review-pi（本次 arm2）**：通用 Agent 循环 + codeintel，未加载规则 Skill，`findingScope` 关闭。
  模型会在大 diff/大仓库上广泛探索并报出大量意见，其中很多落在没有 GT 的文件（包括配置/数据文件）；
  内部证据门/去重门能过滤一部分，但不改变“文件靶向”这一层。
- **smoke10 的误导**：smoke10 是 10 条 outcome-stratified 开发集，优先小 diff/短耗时，且包含 review-pi
  表现较好的 `lvgl`、`filament`、`linera`；它没有覆盖 ragflow/FreeCAD/immich/vllm 这类“review-pi 大量
  无 GT 意见”的样本，所以两者看起来接近。

## 7. 必须说明的边界

1. **无 GT 文件上的意见不一定是误报。** 91 条交集里 GT 只覆盖 272 个文件，review-pi 在
   686 个 (instance, file) 组合（643 个唯一路径）上报了意见；这些意见可能有效，只是 AACR-Bench 没有标注。
   文件级 precision 把它们全部计为误报，所以 4 倍 precision 差距里有一部分是**标注覆盖**造成的，
   不完全等于真实质量差。
2. **这些非 GT 意见不只是 style。** 978 条里 475 条“可靠性”、238 条“可维护”、101 条“可读性”、
   48 条“性能”、44 条“安全”、43 条“可移植”、18 条“可测试性”；严重级以 P2（516）和 P1（139）为主。
   这更像“模型报了很多真实但未标注的问题”，而不是纯噪声；但仍需人工抽检区分。
3. **有 GT 文件内的命中率接近（38.1% vs 36.7%）**，说明“语义匹配能力”本身差距不大；
   差距主要在“报在哪里、报多少”，而不是“报得对不对”。
4. OCR 版本 v1.13.10 与官方 v1.3.1/v1.8.7 不同；单轮 judge；AACR v2 的 GT 77% 是 AI 评论。
5. review-pi 的 arm1（`findingScope` 开）没有跑全量；离线估算显示它只会丢掉 40/1242 条意见，
   命中新 GT / 覆盖 GT 均无损失——scope 不是这次差距的主因。

## 结论

OCR 的领先主要来自**更好的文件靶向 + 更少的无 GT 噪声**，而不是语义理解碾压：

- 82% vs 21% 的意见落在有 GT 的文件；有 GT 文件内命中率几乎相同（38.1% vs 36.7%）；
- 覆盖的 GT 文件 138 vs 74、三种上下文级别均约 2 倍；
- review-pi 意见量 2 倍、无 GT 文件意见约 9 倍（978 vs 108）、无 GT 文件组合 686 vs 75；
  其中 814/978 是“可靠性/可维护/可读性”，P1/P2 合计 655 条，不是纯 style；
- 覆盖一条 GT 需要 4.2 倍意见、2.1 倍总 token、3.3 倍时间。

因此，如果 review-pi 要缩小差距，优先级应是**文件/规则靶向与输出抑制**（规则 Skill、文件筛选、评论预算/反射过滤），
而不是继续增加意见数量或单纯提高召回。
