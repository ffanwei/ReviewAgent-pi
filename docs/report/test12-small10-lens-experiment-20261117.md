## 4. 但出现了「注意力置换」

B 组不是只加不减，它同时丢了 3 条 v2 已覆盖的 GT：

| 样本 | 丢失 GT | 原因 |
|---|---|---|
| `aspnetcore` | GT#2 端口 short 截断 | 本轮 3 条候选变成「可空契约/字节序/scope ID」，端口问题被挤出 |
| `three.js` | GT#4 显式 dispatchSize 绕过上限 | 候选从 5 条降到 4 条，该条未再出现 |
| `ragflow` | GT#1 闭包晚绑定 | 候选换成 GT#4 的串行删除，闭包问题未再出现 |
| `filament` | GT#2/#3 | 候选已生成（L79/L78），judge 三轮均返回空内容，被当成未命中 |

净效果：补回 5 条目标 GT（另有 `ragflow` #4 补上但 #1 同时丢失）；丢掉 3 条原有 GT（`aspnetcore` #2、`three.js` #4、`ragflow` #1）；`filament` 2 条被 judge 空响应吞掉。覆盖从 16 到 16.7。

这说明**单个 Phase 5 提示词的长度增加会挤占原有候选**，而不是简单叠加。更稳的做法是把六项镜头做成**独立的第二遍扫描**，与主 Phase 5 候选合并去重，而不是塞进同一次生成。

## 5. judge 空响应

3 轮共出现 4/2/2 条空响应，集中在：

- `filament` L79：3 轮全空；
- `filament` L78：第 3 轮空；
- `gofr` L152：前两轮空；
- `aspnetcore` L46、`FreeCAD` L421：第 1 轮空。

其中 `aspnetcore` L46 在第 2/3 轮正常判分并命中 GT#1；`filament` L79 三轮全空，直接影响 2 条 GT。

对 v2 的同位置等价候选做隔离重判时，judge 返回 `[3,4]`（命中 GT#2/#3）。若 B 组 L79 也按此计分，B 组将达到约 **17 条命中 / 19 条覆盖 / P 0.63 / R 0.40 / B 0.49**。但本次尝试复判时 judge API 超时，未取得 L79 的直接结果，上述只能作为估算。

**结论：B 组的官方 B 0.441 是下限；修掉 judge 空响应后预计在 0.47–0.49。**

## 7. 结论与下一步

1. **B 组方向验证通过**：补回了 scope ID、字节序、nonce 重放、整除边界、串行删除 5 条目标 GT，P 没有下降。
2. **但单提示词存在置换效应**：新增检查会挤掉原有候选（aspnetcore 端口、three.js 绕过上限、ragflow 闭包）。
3. **B 组官方 B 0.441，修正 judge 空响应后约 0.47–0.49**，已接近/达到 OCR 水平；但要稳定超过 OCR，需要解决置换。
4. **建议下一步做 B2**：把六项镜头改成 Phase 5 内的**独立第二次扫描**，输出 `additionalCandidates` 并与主候选合并（沿用现有去重），而不是把检查项塞进第一次生成。预期保留 v2 原有命中，同时补回 F 类。
5. 在 B2 之前，先把评测侧 judge 空响应重试加上，否则每次对比都会有 2–4 条随机漏判。
