# 0050. MCP 业务 tool：60 s 默认超时与瞬时失败重试

**状态**：已接受（2026-11-07，用户决策）
**关联**：ADR-0037（MCP 上报：进度事件流——事件通道保持原样、默认关闭）、ADR-0045（MCP 业务 tool——本 ADR 修订其决策 3「单次尝试，不重试」）
**范围**：本仓 pi 线 0050。只改 MCP 业务调用的超时缺省值与重试策略；四个 tool 的名字、参数、调用时点与旁路纪律不动。

## Context

ADR-0045 决策 3 当时把业务调用定为**单次尝试、不重试**，理由是业务调用串在关键路径上，「3 次退避 × `server.timeoutMs` 会让收尾多挂十几秒」。该权衡默认了 `mcp.servers.*.timeoutMs` 只有 10 s；实际接入企业 MCP 服务后暴露出两个问题：

1. **10 s 对真实服务端偏紧**：服务端在 `mrReviewResult` / `saveReviewSummary` 上可能做落库、鉴权、转发等动作，冷启动或高负载时单次请求超过 10 s 并不罕见。超时后业务调用直接判失败，平台看到的是「有始无终」或「有文件无意见」。
2. **瞬时故障没有第二次机会**：DNS 抖动、连接被回收、网关 502/503/504 这类故障重试一次就可能成功，而确定性错误（tool 不存在、参数非法）重试多少次都不会变好。二者混在一个「不重试」策略里，等于把可恢复故障和不可恢复故障同等对待。

## Decision

### 1. `mcp.servers.*.timeoutMs` 缺省值 10 s → 60 s

该值是**每条 MCP 请求**的上界（握手、`tools/call`、老式 SSE 的等待），不是整批/整次业务调用的预算。缺省改为 **60 000 ms**，合法范围保持 `100 … 600_000`。显式配置仍然优先。

### 2. 业务 tool 共 3 次尝试（2 次重试）

四个业务 tool（`startTask` / `endTask` / `saveReviewSummary` / `mrReviewResult`）从「单次尝试」改为「首次 + 最多 2 次重试」，退避 **100 ms / 400 ms**（与批量事件通道共用同一组常量）。

### 3. 只重试瞬时失败

| 失败形态 | 是否重试 | 判据 |
|---|---|---|
| 传输层失败（DNS / 拒绝连接 / 连接中断 / 超时） | **是** | `ProtocolError.code === "transport"` |
| HTTP 5xx | **是** | `ProtocolError.code === "http-status"` 且 `status >= 500` |
| JSON-RPC `server-error`（tool 不存在、参数非法等） | 否 | `ProtocolError.code === "server-error"` |
| `tools/call` 返回 `isError: true` | 否 | 服务端业务拒绝 |
| HTTP 4xx / 无响应 / 响应不合法 | 否 | 确定性失败 |

`ProtocolError` 新增可选 `status` 字段，仅 `http-status` 分类携带，供重试策略区分 4xx 与 5xx（不改变任何对外错误文案）。

### 4. 旁路纪律不变

业务调用仍然：绝不抛错、失败只落一行 stderr、**绝不改变退出码**、不进审计。批量事件通道（`mcp.report.tool`）的队列 / 批量 / 背压 / 重试语义**原样保留**；该通道仍为可选、默认关闭（不配置 `tool` 即不启用）。

## Options（为什么不是别的）

- **保持单次尝试、只把超时调到 60 s**：否。能解决「慢服务端被 10 s 掐死」，但瞬时网络/网关故障仍然一次就失败。
- **所有失败都重试 3 次**：否（用户决策）。`server-error` / `isError` 是确定性拒绝，重试只会让一次失败多挂两条退避与两倍超时，日志还会出现「重试 3 次仍失败」的误导性噪声。
- **首次 + 3 次重试（共 4 次）**：否（用户决策）。默认 60 s 下最坏耗时约 `4 × 60 s + 1.7 s`，`endTask` 在 `finally` 里可能把进程收尾拖到 4 分钟以上；3 次尝试已覆盖绝大多数瞬时抖动。
- **每次调用一个独立超时预算（总耗时上限）**：暂不做。当前实现以「尝试次数 × 单请求超时」为天然上界；如后续出现「服务端持续 hang 但每次都在超时前返回」的场景，再引入总预算，避免现在多开一个配置面。

## Consequences

- **好**：慢服务端不再被 10 s 误杀；瞬时故障有恢复机会；确定性错误不浪费重试；业务面与事件面继续共用连接与握手，配置面零新增。
- **代价**：最坏耗时从 `1 × timeout` 变为 `3 × timeout + 500 ms`（缺省 60 s 时约 180.5 s/次）。四个 tool 串行，若平台服务端持续不可达，一次 run 的收尾最多多等约 3 分钟；旁路纪律保证这只会影响 stderr 与耗时，不影响产物与退出码。
- **测试面**：`mcp/report.test.ts` 覆盖「传输失败 3 次后失败」「第 3 次成功」「server-error 不重试」「`isError` 不重试」「4xx 不重试 / 5xx 重试 3 次」；`mcp/protocol.test.ts` 不涉及 `status`（可选字段，旧构造方式仍合法）。
- **与 ADR-0037 / ADR-0045 的关系**：ADR-0045 决策 3 的「单次尝试」被本 ADR 取代，其余决策（调用时点、参数、旁路纪律、报文生成）全部有效；ADR-0037 的事件通道契约不受影响，仅其 `timeoutMs` 缺省值随本 ADR 调整。
