# 0023. `reviews_tips_zh.json` 按「同文件同行」去重

**状态**：已接受（2026-10-30，用户要求「相同代码行出现多次只取第一次」）
**关联**：ADR-0017（分组意见的字段映射与时序）、ADR-0022（tips 是唯一中文产物）、ADR-0014（skill 候选与主候选按 `(file, line, category)` 合并——本 ADR 是它下游的**呈现层**收口）
**跨仓**：本 ADR 为本仓 pi 线序列 0023；引用 DSH 兄弟仓决策须写全限定语「DSH 线 ADR-XXXX」。

## Context

同一行代码出现多条 finding 是常见形态，来源有三：

1. **多类别命中**：一行里同时有「空指针」与「日志缺失」（`category` 不同，候选门的 `(file, line, category)` 键不同 ⇒ 两条都存活）；
2. **主会话 + skill 会话**：规则会话对同一行再报一次（键不同则不被合流丢弃）；
3. **模型自身重复**：同一行用不同措辞报两遍。

这些在 `reviews_en.json`（结构化真源，逐 finding）里是合理的——它们代表不同的判据。但 `reviews_tips_zh.json` 是**给人按行改代码**的排版：同一行并列两条会让人读两遍、改两遍，且下游按「行」生成工单/评论时会重复刷屏。

## Decision

1. **去重键 = `(file, line)`**，去重发生在**映射层**（`src/presentation/tips.ts` 的 `dedupeFindingsByLine`，纯函数）。
2. **保留首条**（finding 源序的最先出现者），其余**忽略**——不做「取更严重」「取更具体类别」之类的择优。理由：择优规则会引入第二个排序轴，而 finding 源序本身已经是主会话→skill 会话→相位顺序的产物，可解释、可复现。
3. **不同文件的同号行各自保留**：`line` 只有在同一文件内才指向同一行代码。
4. **`suggestion` 只为保留行生成**：核外引擎先 `dedupeFindingsByLine(projected.findings)` 再逐条生成建议（每条一次网关调用，并发 4）。已丢弃的行不该再花一次调用——这也是本 ADR 的成本收益。
5. **只影响 tips**：`stdout` 的 `findings` 与 `reviews_en.json` **仍是全量**（含同行多条），结构化字段、候选门、审计、RunRecord 零改动。
6. **零 finding 与去重后为空仍照产** `{ files: [] }`（「本次没发现问题」是结论，不因去重变成缺席）。

## Options（为什么不是别的）

- **在候选门（`candidate-merge`）按 `(file, line)` 去重**：那是**测量面**——会改变 findings 数量与评测口径，跨仓对照立刻失真。放弃。
- **取最严重的一条**：`severity` 与实际修复价值不同构（一行既可能是 P0 空指针、也可能是 P2 日志问题，修 P0 时顺带修 P2 是常见诉求）。而「保留首条」至少是可预测的；真要分严重度得让下游按 findings 处理。放弃。
- **把同行多条合并成一条（拼 review 文本）**：破坏 ADR-0017 的 10 键语义（`severity`/`category`/`ruleId` 都是单值），且拼出来的文本既非原文也非译文。放弃。
- **在 CLI 缝（`presentation-projection.ts`）过滤**：那里只做形状校验，加业务规则会让「引擎产什么 = 落盘什么」的对应关系消失，排障时分不清是引擎还是 CLI 丢的。放弃。
- **同时给 `suggestion` 仍按全量生成**：白花网关调用（同行重复时每多一条多一次请求），且生成结果根本不会被使用。放弃。

## Consequences

- **正**：
  - 输出按行唯一，人读与下游工单都不再重复；
  - 去重口径单源（`dedupeFindingsByLine`），映射与建议生成不会各走一套；
  - 同行重复越多，省下的 `suggestion` 调用越多（每少一条省一次网关请求）。
- **负/风险**：
  - **信息损失（有意）**：被丢弃的 finding 在 tips 里不可见——要看全量请读 `reviews_en.json` 或 stdout（同一行的不同判据仍在）。
  - **「首条」依赖 finding 源序**：源序变化（例如新增 skill、相位调整）可能换掉保留的那条。这是可接受的（tips 非测量面）。
  - **与候选门的去重口径不同**：候选门是 `(file, line, category)`，tips 是 `(file, line)`。两处都必须按各自的键理解，别互相套用。
- **中性**：不新增旗标/环境变量；10 键结构、`{files}` 顶层、文件路径与生命周期全部不变。

## 验收标准

1. 同文件同 `line` 三条 finding ⇒ tips 只有一条，内容取自源序第一条（含它的 `code`/`severity`），不因其他条更严重而改选。
2. 不同文件出现同一 `line` 号 ⇒ 各自保留一条。
3. 去重后仍按 `lineNum` 升序、`files` 按首见序；`{files: []}` 行为不变。
4. 引擎侧：同行重复的 finding **不产生**额外的 `suggestion` 网关调用（3 条 finding 其中 2 条同行 ⇒ 只 2 次建议请求）。
5. `reviews_en.json` 与 stdout findings 仍含全量（同行多条都在）。
