# 0043. review 参数回显提前到开跑前

**状态**：已接受（2026-11-05，用户要求「调用时候的参数都在一开始就打印出来，不要放到检视结束」）
**关联**：ADR-0031（本 ADR 取代其决策 1 的打印点；回显内容、stderr-only、值转义与单点实现均沿用）、ADR-0030（收尾总结行）、ADR-0016（stderr 运行投影 / stdout 单 JSON 文档硬约束）、ADR-0033（`--taskId` / `--tasks-dir`）
**范围**：本仓 pi 线 0043；DSH 兄弟仓的对应实现不在本 ADR 范围内。

## Context

ADR-0031 把「本次 review 传入参数」回显放在 `runReview` 返回后、呈现投影之前，理由是「用户要的是执行后确认这次到底跑了什么」，并显式否决了「打印在 `runReview` 之前」的选项。

实际使用中这个位置有两个问题：

1. **开跑前无法确认输入**：`--repo` 指错快照、`--mr-diff` 拿错文件、`--taskId` 拼错，都要等整轮检视跑完才暴露，成本是几十秒到几分钟的模型调用。
2. **失败路径完全看不到参数**：diff 读取 / 解析失败、模型报错、配额不足等都在回显之前抛错，stderr 只剩一行错误，无法从日志判断「这次到底传了什么」。

本轮用户明确要求提前打印。ADR-0031 顾虑的「提前打印会被进度行打散」，可以通过把打印点放在进度投影启动之前解决。

## Decision

1. **打印点**：`runReviewCommand` 内，`--tasks-dir` / `--taskId` 解析之后、diff 读取与 `startProgress` 之前。此时回显所需的全部值已确定（相对路径已按 cwd 解析）。
2. **只走 stderr**（不变）：stdout 仍是单 JSON 文档契约。
3. **回显内容与形态不变**（沿用 `cli/args-echo.ts` 的 `formatReviewArgs`）：逐行、生效值、缺省标注来源、`--issue` JSON 转义、可重复旗标全列、不含 apiKey / baseUrl。
4. **stderr 顺序变为**：参数回显 →（diff 装载）→ 进度事件 → 检视 → 收尾总结行 → 呈现投影 → stdout。
5. **失败可见性**：只要走到参数解析之后，diff 读取 / 解析失败与检视期错误都能在错误行之前看到本次参数；更早的用法错误（未知旗标、`--repo` 不是目录、缺 `reviewer.apiKey`）仍只报错误。

## Options（为什么不是别的）

- **保留在结尾、再加一块开头**：同一信息打两遍，日志消费方要维护两套筛除规则。否。
- **只在开头打印、删掉结尾**：本 ADR 的选择。结尾的总结行（ADR-0030）已承担「本次跑了什么」的量化信息，参数面不再重复。
- **打印点再往前挪到 `resolveReviewerEndpoint` 之前**：需要把 key 校验与路径解析拆开重排，收益仅是「缺 key 时也能看到参数」——而缺 key 是秒级 fail fast。否。
- **改成 stdout 的 JSON 字段**：违反单 JSON 文档契约（ADR-0016 硬约束 1），且会让检视结论被日志字段污染。否。

## Consequences

- **好**：开跑即见输入，参数错误在第一个模型请求前就能发现；失败日志自带输入面。
- **代价**：非 TTY 批跑日志开头多 13 行（1 行头 + 12 行参数），日志消费方需要按固定前缀 `review-pi: 本次 review 传入参数` 起、到下一条 `review-pi:` 行止筛掉——与 ADR-0031 记录的代价相同，只是位置从尾部挪到头部。
- **测试面**：`cli/args-echo.test.ts`（文本形态不变）；`cli/bin.process.test.ts`（回显头存在且**早于** `✓ 完成` 总结行）。
