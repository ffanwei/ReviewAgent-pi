## Context

用户于 2026-11-17 定稿平台侧总结规范：固定四节——检视总览（变更规模 / 预算使用 / 资源加载）、意见分布（fatal / major / minor / suggestion）、高优先级意见速览、星级评价（硬判据）。

原实现由模型自由撰写（`SUMMARY_SYSTEM_PROMPT` 只约束"中文、Markdown、事实性"这类大方向），存在三个问题：

1. **结构不可消费**：小节顺序、表格形状每次都可能不同，平台无法按固定格式渲染；
2. **数字不可信**：意见分布、优先级排序都靠模型自己从 tips 里数，与平台 `mrReviewResult` 明细可能不一致——违反 ADR-0057「总结必须与平台明细一致」；
3. **指标根本不在输入里**：规范要求的变更规模 / 预算使用 / 资源加载，原 `ReviewSummaryInput` 一个都没有，模型只能编。

另外，零意见 / 零上报原为两条纯文案（ADR-0057 决策 3），与有意见路径形态完全不同。

## Decision

1. **固定四节**：`## 检视总览`（三行表格）、`### 意见分布`（四行表格）、`### 高优先级意见速览`、`### 星级评价`。小节顺序、表头、severity 顺序（fatal → major → minor → suggestion）固定。
2. **数字权威在代码**：意见计数、涉及文件、优先级排序、星级全部由代码确定性计算，并随 user 消息作为"权威数据"下发；模型只补「一句话描述」（可改写 `finding.title`），**不得改数字、不得改判星级**。权威数据为 null 的指标渲染为 `—`。
3. **指标口径**：
   - **变更规模** = 文件数 / hunk 数 / 变更行数。hunk 与变更行数是「方法级变更数」的**退化口径**（方法级需要按语言解析变更行所在符号，本 ADR 不做）；`measureDiffScale` 与 MR 边界护栏共用同一 diff 解析器，不可度量时写「N 个文件 / 变更规模不可度量」。
   - **预算使用** = 模型调用总数（主会话 + 规则 Skill，`ReviewRunResult.modelCalls`）；**不带分母**——轮次上限可配（ADR-0046），任何固定分母都会随配置漂移。
   - **资源加载** = 输入 token 合计（未命中 + 缓存命中）。
4. **严重级展示映射**：P0 → fatal、P1 → major、P2 → minor、P3 → suggestion（与 `candidate-normalize` 的英文别名表同口径）。「高优先级」= fatal / major（P0 / P1）。
5. **星级硬判据（确定性，2–4 档）**：
   - ⭐⭐：存在 ≥1 条 fatal 或 major，需整改后方可合入；
   - ⭐⭐⭐：0 条 fatal、0 条 major，仅 minor + suggestion；
   - ⭐⭐⭐⭐：0 条 fatal / major / minor，仅 suggestion。
   - ⭐（仅配置 / 格式化 / 生成代码）**本 ADR 不实现**：需要变更文件分类，且与"有无意见"是两个轴，留作后续。
6. **零意见 / 零上报同模板、省略速览**：
   - 两者都不调用模型，直接确定性渲染；
   - 零意见附「本次检视未发现缺陷。」，星级按硬判据给 ⭐⭐⭐⭐；
   - 零上报附「本次检视未向平台上报任何检视意见。」，星级写「—（未上报任何检视意见，不作星级评价）」——**绝不能把「没上报」评成「没问题」**（ADR-0057 的诚实口径）。
7. **降级模板同构**：模型失败 / 回空串时走同一渲染函数（`renderStructuredSummary`），只缺模型润色的一句话（回落 `finding.title`）；平台始终只见到一种结构。
8. **跳过检视的固定文案不变**：diff 超大（ADR-0075）/ 无可检视文件（ADR-0078）仍用各自固定总结——那是「没检视」，不是「零意见」。

## Options（为什么不是别的）

- **只改 `SUMMARY_SYSTEM_PROMPT`**：规范里的三类运行指标不在输入里，模型只能编；结构也无强约束。否。
- **方法级变更统计**：准确，但要按语言把变更行映射到所属符号，成本与维护面都大；先以 hunk / 行数退化，后续可替换 `measureDiffScale` 而不动渲染面。
- **预算使用带固定分母（30 / 轮次 × 6）**：轮次上限可配（ADR-0046），分母会漂移；用户口径只要求「模型调用数」。否。
- **让模型自己数、自己定星级**：与「硬判据」矛盾，且可能与意见分布表自相矛盾。否。
- **零意见继续保持两条纯文案**：平台要按两种形态解析；改为同一模板（诚实语义与不调模型的纪律都保留）更一致。
- **零上报也给 ⭐⭐⭐⭐**：等于把「没上报」说成「没问题」，直接违反 ADR-0057。否。

## Consequences

- **好**：平台拿到稳定、可解析的结构；表格数字与审计 / 上报口径同源，模型没有编数空间；模型失败时平台看到的形状不变。
- **代价 / 风险**：模型若不严格遵守结构，输出仍可能漂移（当前不做输出结构校验）；星级只有 2–4 三档，`⭐` 未实现；方法级变更数暂以 hunk 数近似。
- **测试面**：`review-summary.test.ts`（四节结构、星级边界、指标渲染、两种零路径、降级同构）、`bin.process.test.ts`（saveReviewSummary 进程断言改为结构断言）、`mr-boundary-guard.test.ts`（`measureDiffScale` 的 hunk / 行数 / 不可度量）。全量测试 1057 通过。
