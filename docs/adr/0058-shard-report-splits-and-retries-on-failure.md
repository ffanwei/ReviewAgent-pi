# 0058. 片级报文生成失败后按条数二分重试

**状态**：已接受（2026-11-07，用户决策）
**关联**：[ADR-0045](0045-mcp-business-task-tools.md)（片级报文与统一生成）、[ADR-0056](0056-mr-review-result-covers-files-without-tips.md)（无意见文件补空包；「有意见文件绝不发空包」已被 ADR-0061 取代）、[ADR-0057](0057-summary-covers-only-reported-findings.md)（总结只覆盖已上报）、[ADR-0051](0051-llm-call-retry-and-timeout.md)（一次性调用的重试与超时）
**范围**：本仓 pi 线 0058。只改**片级报文生成失败之后的路径**：同一提示词、同一终检、同一报文组装，只把 findings 子集缩小后重发。正常路径（全量一次成功）零额外模型调用、报文与提示词字节不变。

> **后续修订（ADR-0061，2026-11-09）**：最终仍失败的文件不再「不发空包」——`saveReviewSummary` 前仍按文件补发 `reviewTips: []`（覆盖率优先）。二分重试本身的批次、次数与串行纪律不变。

## Context

片级报文生成（ADR-0045）是**一次**一次性模型调用：整片 findings 进同一个请求，`limits.timeouts.oneShotMs`（缺省 90 s）× `limits.retry.maxAttempts`（缺省 3 次）。这条路径的失败模式与**批次大小**强相关：

- 输入 finding 越多，提示词越长；输出 tips 越多，completion 越长；
- 达到 `oneShotMs` 时抛 `TimeoutError`；输出被截断或返回非法 JSON 时按解析失败处理；
- 模型侧偶发超载时同样表现为长尾失败。

失败后此前的处理是「本片整体放弃」：`outcome.kind === "failed"` → 全部保留 finding 登记 `uncoveredByKey` → 有意见的文件一条 `mrReviewResult` 都不发（ADR-0056 的排除面）→ 收尾总结按已上报集合生成（ADR-0057），于是总结也随之变空。

实测（`F027` 一类大 MR）出现的是：**同一次运行里大部分片成功、个别大片的报文调用超时**，导致这些片的意见在平台上整片缺席。失败的不是「模型不会写这些意见」，而是「一次要生成太多」——把同一批 finding 切小后重发，往往就能成功。

## Decision

### 1. 只在失败后拆，正常路径零成本

`buildShardReportResilient` 先按**全量** findings 调一次 `buildShardReport`：

- 成功 → 原样返回，不产生拆分留痕（`split` 字段缺席），零额外调用；
- 失败 → 才进入拆分重试。

这条保证「报文与提示词字节不变」：提示词模板、system message、终检、结构字段组装全部复用，唯一变化是 `findings` 数组变短。

### 2. 按条数二分，最多两层

失败批次按**条数连续二分**（`ceil(n/2)` 切点，不重排、不去重），因此每批都是原 findings 的连续切片：

- `maxSplitDepth` 缺省 2：全量 → 两半 → 四分之一；
- 最坏模型调用数 = `1 + 2 + 4 = 7`（首调用本身按配置重试，拆分批次不再叠加重试）；
- 单条 finding 失败时不再拆（`findings.length < 2`），深度为 0 时等同旧行为。

不做更深的理由：拆到单条仍失败说明问题不在批次大小（鉴权、模型不可用、提示词本身），继续拆只是多烧调用。

### 3. 拆分批次只尝试一次、串行执行

- 拆分批次把 runtime 覆盖为 `SINGLE_ATTEMPT_POLICY`（1 次尝试）：全量调用已经消耗过配置的重试次数，再叠 3 次会把失败路径的墙钟放大到不可接受；
- 各批次**串行** await（与片间上报同纪律）：失败路径不瞬时放大网关并发。

### 4. 部分成功照常上报，仍失败条目逐条留痕

- 成功批次组成的 `files` 照常按文件上报 `mrReviewResult`（上报粒度仍是文件，不变）；
- 仍失败的 finding 逐条登记 `uncoveredByKey`，原因串为 `片级语义生成失败（已拆分为更小批次仍失败）：<原始原因>`；
- **绝不给有意见的文件发空包**（ADR-0056）：拆分只增加成功面，不改变「不知道 ≠ 没有问题」；
- 全部批次失败 → `kind:"failed"`，原因串 `拆分为 N 批后仍全部失败：<原始原因>`，由调用方按整片失败处理（回落到原有行为）。

### 5. 合并保持原序

多批成功结果合并时：

- 文件组按**首次出现序**（即原全量顺序）；
- 同一文件的 tips / findings 按批次序拼接（拆分是连续切片，故等于原 finding 序）；
- `semanticByKey` / `uncoveredByKey` 首见优先；`skippedTips` / `degradedTips` / `skippedFiles` 去重后拼接。

这保证「拆过一次」在产物上不可见：文件序、行序、12 键 tips 与全量一次成功时一致。

### 6. 零静默

触发拆分时 stderr 打一行（不含正文）：

`review-pi: MCP mrReviewResult${label} 报文生成失败，已拆分为 N 批重试（M 批成功）`

`batches` = 首次全量失败后实际发出的小批次调用数，`succeeded` = 成功叶子批次数。

## Options（为什么不是别的）

- **引擎兜底上报（方案 C）**：否。引擎 tips 是另一套文案与另一条生成链（ADR-0045 明确「同源不同译」），让它在报文失败时顶上等于**同一条意见两个来源**：提示词不同、终检不同、字段来源不同，平台侧无法区分，也破坏了统一生成的单一文案事实。分批重试保持单一来源。
- **让模型修复坏输出（再发一次「请修正 JSON」）**：否。要新增提示词 / 改 system message，且修复输入包含已经超长或截断的坏输出，成功率与成本都不可控；这不是「同一任务换小批次」，是新的任务。
- **一开始就按小批生成**：否。正常路径会从 1 次调用变成 N 次，成本和墙钟线性放大，只为覆盖少数失败。
- **失败后重新全量生成（不缩小子集）**：否。失败原因与批次大小相关，原样重试等于把已消耗的重试再花一遍。
- **拆到单条为止（深度不设限）**：否。对大小无关的失败（鉴权 / 模型不可用）无效；深度 2 已覆盖「太大」这一类，剩下的是确定性失败。
- **并行拆分批次**：否。与 ADR-0050 / 片间上报的串行纪律冲突；失败路径瞬时并发翻倍最容易踩网关限流，反而扩大失败面。
- **拆分批次的失败也进总结**：否。总结只看 `mrReviewResult` 实际收下的意见（ADR-0057），此处不破例。

## Consequences

- **好**：单片报文超时不再等于该片意见全灭；部分成功时能救回多少报多少，覆盖率随批次缩小而恢复。正常路径零额外调用、报文与提示词字节不变，`reviews_tips_zh.json` / stdout / 退出码均不受影响。
- **代价 / 风险**：失败路径墙钟变长。最坏情况 = 全量调用的配置重试（缺省 3 × 90 s）+ 6 个拆分批次各 1 次尝试（6 × 90 s），合计约 13.5 分钟；这是故障路径的上界，不是常规成本。若模型侧整体不可用，会依次白跑 7 次调用——深度上限 2 是对这笔浪费的封顶。
- **口径**：拆分是**失败后的补救**，不是新的生成范式；`uncoveredByKey` 仍是「没生成出来」的唯一真源，总结、stderr 与审计都从它派生。
- **测试面**：`cli/report-payload-resilient.test.ts` 覆盖全量成功不拆分、二分成功合并、部分失败、全失败、`maxSplitDepth=0`、单条失败、拆分批次单次尝试、同文件跨批合并、语义登记全覆盖；`cli/bin.process.test.ts` 覆盖进程级「全量报文非法 JSON → 两批都成功 → 两个文件都上报」的完整链路（含 stderr 拆分行与一次性调用计数）。
