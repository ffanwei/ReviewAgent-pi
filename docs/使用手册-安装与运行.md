# 使用手册：安装、配置与运行

> **面向谁**：拿到 `review-pi` 发行包、想在自己机器或 CI 上跑一次 MR 检视的人。不需要 clone 本仓，也不需要懂 pi 内核。
>
> **对应形态**：npm 多包发行（ADR-0028）。六个包 = 内核四包 `@review-agent-pi/pi-{telemetry,chord,ai,agent-core}` + `review-llm` + `review-pi`；用户只需要装 `review-pi`，其余是它的依赖。
>
> **口径来源**：配置面 ADR-0025 / 0026，产物与规则包信任边界 ADR-0027，发行形态 ADR-0028。本文只描述**已经实现**的行为，不引入新配置键、新开关。
>
> **配套文档**：单次检视的旗标细节与产物读法见《[运行手册-单次检视](运行手册-单次检视.md)》；仓内开发（clone + pnpm）也看那份。本文覆盖「装好的形态」从零到跑通的全过程。

---

## 0. 五分钟最短路径

如果你只想先跑通，按这五步做；每一步的细节在后面对应章节。

```bash
# 1. 确认 Node 版本（必须 >= 22.19.0）
node -v

# 2. 全局安装（包已发布到 registry 时；只有 tarball 见 §2.4，自己打包见 §2.7）
npm i -g review-pi

# 3. 生成用户级配置，然后填入 reviewer.apiKey
review-pi config init

# 4. 自检网关与模型（会发一次极小的真实请求）
review-pi smoke

# 5. 跑一次检视（所有路径都可以是绝对路径）
review-pi review --repo /abs/path/to/repo --mr /abs/path/to/change.diff --out /abs/path/to/out
```

跑完检查三处：

1. **stdout**：单个 JSON 文档，`ok: true`，`findings` 是本次检视意见；
2. **`<out>/runs/mr/<caseId>/rep-1/reviews_en.json`**：英文 findings 真源；
3. **`<out>/audit/mr/<caseId>/rep-1/audit/<runId>.json`**：审计与配置快照。

> **没有 `--help` / `--version`**：直接执行 `review-pi`（不带子命令）会打印 usage 并 **exit 1**，这是设计行为，不是安装失败。版本用 `npm ls -g review-pi --depth=0` 查看。

## 1. 安装前检查

### 1.1 Node.js 版本

`review-pi` 的 `engines` 是 **`>=22.19.0`**（与 pi 内核一致）。

```bash
node -v
npm -v
```

期望 `node -v` 输出 `v22.19.0` 或更高。低于该版本时：

- npm 可能只给 `EBADENGINE` 警告并继续安装，但运行时可能因内核 API 缺失而崩；
- 建议用 nvm / fnm / volta 切到 Node 22 LTS 最新版，或 Node 24。

**不要**用 Node 18 / 20 尝试运行。内核四包与 CLI 都按 Node 22 的 ESM 行为构建。

### 1.2 npm 与全局 bin 目录

```bash
npm config get prefix
```

- **Windows**：通常是 `C:\Users\<你>\AppData\Roaming\npm`，全局命令是 `review-pi.cmd`；
- **macOS / Linux**：通常是 `/usr/local` 或 `~/.nvm/versions/node/vXX/bin`，全局命令是 `review-pi`。

确认该目录在 `PATH` 里：

```powershell
# Windows PowerShell
Get-Command review-pi -ErrorAction SilentlyContinue
$env:PATH -split ';' | Select-String 'npm'
```

```bash
# macOS / Linux
command -v review-pi
echo "$PATH" | tr ':' '\n' | grep -E 'npm|node'
```

装完后 `Get-Command review-pi` / `command -v review-pi` 必须能定位到命令；否则先修 `PATH`，不要靠每次写全路径。

### 1.3 registry 与网络

```bash
npm config get registry
npm ping
```

默认是 `https://registry.npmjs.org/`。如果包发布在公司私有 registry，需要按 §2.3 配 scope 映射。

`npm ping` 失败通常意味着代理 / 证书 / 内网 DNS 问题。公司环境常见做法：

```bash
npm config set proxy http://proxy.example.com:8080
npm config set https-proxy http://proxy.example.com:8080
# 或使用环境变量 HTTPS_PROXY / HTTP_PROXY（npm 会读）
```

### 1.4 ripgrep 二进制（postinstall）

`review-pi` 依赖 `@vscode/ripgrep`，安装时会执行 postinstall 从 GitHub Releases 下载对应平台的 `rg` 二进制。

- 需要能访问 `github.com`（或公司镜像）；
- 下载失败时 `npm i` 可能仍显示成功，但运行检视会在代码检索阶段报 `failed to spawn ripgrep binary`；
- 验证方式见 §2.5 的安装面自检；
- 受限网络下可先配置 `@vscode/ripgrep` 的镜像环境变量（按其包 README），或改用带外网缓存的 registry。

### 1.5 平台与运行时依赖

| 项 | 要求 | 说明 |
|---|---|---|
| OS | Windows 10+ / macOS / Linux | 发行面冒烟（`verify:pack`）在当前平台验证安装布局（bin 腿表、配置子命令、builtin 引擎、wasm、ripgrep） |
| 架构 | x64 / arm64 | 取决于 `@vscode/ripgrep` 与 Node 的支持 |
| Java | **不需要** | tree-sitter-java 是 wasm，不调 `javac` / JDK |
| shell | 不需要 | 主检视不依赖 bash；规则包的 `bash` 工具是另一层（见 §6.3） |
| 磁盘 | 每次 run 数 MB 起 | 审计、转录、规则包缓存都在 `<out>` 下；大仓 / 多轮 / 多规则包可到数十 MB |

### 1.6 权限

全局安装需要写 `npm prefix` 目录：

- **不要**用 `sudo npm i -g`（会把 root 属主文件带进用户环境，后续升级/卸载都麻烦）；
- 推荐 nvm / fnm / volta 管理的 Node，prefix 在用户目录；
- 或者改用户级 prefix：`npm config set prefix ~/.npm-global`，再把 `~/.npm-global/bin` 加进 `PATH`。

## 2. 安装

发行面是六个包；用户只需要显式安装 `review-pi`，其余由 npm 按依赖解析：

| 包 | 版本 | 角色 |
|---|---|---|
| `@review-agent-pi/pi-telemetry` | `0.85.1` | 上游 telemetry 定制件 |
| `@review-agent-pi/chord` | `0.85.1` | 上游 chord 定制件 |
| `@review-agent-pi/pi-ai` | `0.85.1` | 上游 pi-ai 定制件（含 provider 模型数据） |
| `@review-agent-pi/pi-agent-core` | `0.85.1` | 上游 agent 定制件 |
| `review-llm` | `0.1.0` | LLM 接入共享缝（产品依赖） |
| `review-pi` | `0.1.0` | Review CLI，提供 `bin: review-pi`（唯一面向用户的入口） |

> 内核四包版本跟随上游锚点 `0.85.1`；两个产品包版本跟产品走。scope 可整体替换（ADR-0028 §7），替换后以下命令里的包名以实际发布名为准。

| 你现在的情况 | 走哪一节 |
|---|---|
| 六个包已发布到能访问的 registry | §2.1（全局）或 §2.2（项目内） |
| 只有私有 registry，或 scope 被替换过 | §2.3 |
| 手上已有六个 `.tgz`（还没发布 / 内网拷贝） | §2.4 |
| 手上没有 `.tgz`，需要自己从源码打 | §2.7，再回到 §2.4 安装 |

### 2.1 方式 A：公开 registry 全局安装（推荐）

```bash
npm i -g review-pi
```

装完后：

```bash
review-pi
```

预期输出（stderr）开头是：

```text
review-pi: missing command (expected `review`, `smoke` or `config`)
usage: review-pi review --repo <path> --mr <diff-file> ...
```

退出码 **1**。这条命令的作用只是确认 bin 能被拉起、main 入口能跑到用法提示。真正的成功标志是后面 `config init` / `smoke` / `review`。

### 2.2 方式 B：装进项目（不污染全局）

```bash
cd /path/to/your-project
npm i review-pi
npx review-pi config init
npx review-pi smoke
npx review-pi review --repo ... --mr ... --out ...
```

或在 `package.json` 里加 script：

```json
{
  "scripts": {
    "review": "review-pi review --repo ./repo --mr ./change.diff --out ./review-out"
  }
}
```

`npm run review -- --model ep-xxxx` 可透传额外参数（`--` 之后）。

> 项目内安装同样会把六个包装进 `node_modules`；`review-pi` 在 `node_modules/.bin/` 下有 shim。

### 2.3 方式 C：私有 registry

六个包必须**全部**发布到同一个 registry（或可互相解析的 registry 组）。客户端 `.npmrc` 示例：

```ini
# 如果 scope 仍是 @review-agent-pi
@review-agent-pi:registry=https://npm.example.com/repository/npm/
# 产品包没有 scope，需要单独指（或把默认 registry 指到内网）
registry=https://npm.example.com/repository/npm/
//npm.example.com/repository/npm/:_authToken=${NPM_TOKEN}
```

然后：

```bash
npm i -g review-pi
```

**scope 被替换过**（ADR-0028 §7：改六个 `package.json` 的 `name` 与全仓 specifier）时，把上面的 `@review-agent-pi` 和 `review-pi` 换成实际发布名。安装命令以实际包名为准，不要照抄本文的占位名。

常见失败：

| 现象 | 原因 | 处置 |
|---|---|---|
| `404 Not Found - GET .../review-pi` | 产品包没发，或 registry 路径不对 | 确认 `npm view review-pi version --registry ...` 能查到 |
| `404 .../@review-agent-pi%2fpi-ai` | scope 没映射，或内核包没发 | 补 `@review-agent-pi:registry=...`；确认六个包都在 |
| `E401` / `ENEEDAUTH` | token 缺失或过期 | 重新生成 token，写进 `.npmrc`（不要提交到仓库） |
| `ETARGET` / 版本找不到 | 只发了部分版本 | 六个包版本必须成套：内核 `0.85.1`、产品 `0.1.0` |

### 2.4 方式 D：从 tarball 安装（未发布 / 内网分发）

适用：包还没发到 registry，或目标机器只能拷文件过去。前提是手上已有六个 `.tgz`（自己打见 §2.7；别人给的先按 §2.7.3 核对文件名与版本成套）。

六个 tarball（名字 = 包名去掉 scope 前缀）：

```text
review-agent-pi-pi-telemetry-0.85.1.tgz
review-agent-pi-chord-0.85.1.tgz
review-agent-pi-pi-ai-0.85.1.tgz
review-agent-pi-pi-agent-core-0.85.1.tgz
review-llm-0.1.0.tgz
review-pi-0.1.0.tgz
```

六个**一起**装，不要只装 `review-pi`：`review-pi` 的 `dependencies` 指向另外五个包的真实版本号，npm 只会去 registry 找同名同版本，单装一个会失败或装到 registry 上的旧版。

```powershell
cd <tarball 所在目录>
npm i -g .\review-agent-pi-pi-telemetry-0.85.1.tgz `
         .\review-agent-pi-chord-0.85.1.tgz `
         .\review-agent-pi-pi-ai-0.85.1.tgz `
         .\review-agent-pi-pi-agent-core-0.85.1.tgz `
         .\review-llm-0.1.0.tgz `
         .\review-pi-0.1.0.tgz
```

```bash
cd <tarball 所在目录>
npm i -g ./review-agent-pi-pi-telemetry-0.85.1.tgz \
         ./review-agent-pi-chord-0.85.1.tgz \
         ./review-agent-pi-pi-ai-0.85.1.tgz \
         ./review-agent-pi-pi-agent-core-0.85.1.tgz \
         ./review-llm-0.1.0.tgz \
         ./review-pi-0.1.0.tgz
```

注意：

- **必须带 `./` 或 `.\`**：裸写 `review-pi-0.1.0.tgz` 会被当成包名去 registry 找，报 404。路径带空格时整段加引号。
- 一条命令里六者的先后**不影响结果**（npm 一次解析整批）；拆成六条命令则要先装依赖方（telemetry → chord → ai → agent → review-llm → review-pi），否则前面的会因依赖缺失失败。
- 机器上已装过 registry 版同名包时，`npm i -g <tarball>` 直接覆盖，版本号相同也覆盖，不会提示「已是最新」。
- tarball 里的 `workspace:*` 已被改写成真实版本号，但**第三方依赖**（`@vscode/ripgrep`、`tree-sitter-java`、`web-tree-sitter`、`jsonc-parser`）仍要从 registry 解析。所以六个 tarball 只解决我们自己的包，**不是完全离线安装**；纯离线的安装布局验证走仓内的 `pnpm verify:pack`（§2.7.4）。
- 装完按 §2.5 四步验证，别直接跳到 `smoke`。

### 2.5 安装后验证（四步）

**第 1 步：命令可见**

```powershell
Get-Command review-pi
```

```bash
command -v review-pi
```

**第 2 步：入口能跑**

```bash
review-pi
```

看到 usage、退出码 1，即 bin → dist → main 这条链是通的。

**第 3 步：配置子命令能跑**

```bash
review-pi config show
```

- 没有配置文件时输出 `（not found — 全缺省；review/smoke 会因缺 reviewer.apiKey 中止）`，退出码 **0**；
- 有配置文件时逐键打印生效值与来源 `(file|default)`，`reviewer.apiKey` 只显示 `set` / `missing`。

**第 4 步：确认版本与安装位置**

```bash
npm ls -g review-pi --depth=0
npm root -g
```

Windows 默认包目录：`%APPDATA%\npm\node_modules\review-pi`；POSIX：`$(npm prefix -g)/lib/node_modules/review-pi`。包内应能看到 `bin/`、`dist/`、`presentation/`、`THIRD-PARTY-NOTICES.md`。

### 2.6 升级与卸载

```bash
# 升级到最新
npm i -g review-pi@latest

# 指定版本
npm i -g review-pi@0.1.0

# 卸载（会连带移除六个包中不再被需要的依赖）
npm rm -g review-pi
```

升级不会动你的 `~/.PiAgent/PiAgent.jsonc`。卸载也不会删它——里面可能还有 key，需要时手工删除。

### 2.7 自己打包（从源码产出 tarball）

> **面向谁**：要自己产出/分发 tarball 的人（仓主、内网分发者、要在离线机器上部署的人）。只装包的人读完 §2.4 就可以跳到 §3。
>
> 结论先说：`pnpm build:dist` → `pnpm pack:packages` → `pnpm verify:pack`，三步各自独立，**pack 不会替你构建**。

#### 2.7.1 前置：Node、pnpm、依赖、构建

```bash
git clone <repo-url> && cd ReviewAgent-pi
node -v      # 必须 >= 22.19.0（engines 硬要求）
pnpm -v      # 仓库用 pnpm workspace，版本以 package.json 的 packageManager 为准
pnpm install # 打包和 verify 都依赖仓内已装的第三方依赖
```

打包前必须有 `dist` 制品：

```bash
pnpm build:dist
```

它按固定顺序跑三步，不要拆开只跑后两步：

1. `pnpm build:pi` —— 内核四包 tsc：telemetry → chord → pi-ai → pi-agent-core；
2. `pnpm --filter review-llm build` —— 共享 LLM 缝；
3. `pnpm build:presentation` —— 先 `pnpm --filter review-pi build`（CLI 的 `dist/`），再 `tsc -p tsconfig.presentation.json`（呈现层产物先落 `.tmp-gen/presentation/`），最后 `scripts/copy-presentation.mjs` 复制到 `packages/review-pi/presentation/`（`presentation.engine = "builtin"` 从这里取）。

**为什么 pack 不隐式构建**：`prepack` 只**断言**产物在位——`dist/cli/main.js`、`dist/index.js`、`bin/review-pi.js`、`bin/lib/cli-runtime.js`、`presentation/` 的四个文件（`engine-zh.js` / `terminology.js` / `tips.js` / `translate-projection.js`）、以及履约文本 `THIRD-PARTY-NOTICES.md`。缺一项就打印「发布物不完整（N 项缺席）——先跑 pnpm build:dist」并 exit 1。这样打包是确定性且离线的：产物由构建显式产出，打包阶段不会因为环境不同悄悄编译出不同内容。

确认构建到位（可选）：

```powershell
dir packages\review-pi\presentation
```

```bash
ls packages/review-pi/presentation
```

应看到上列四个 `.js`；`dist/cli/main.js` 与 `bin/review-pi.js` 也应在。

#### 2.7.2 打包：`pnpm pack:packages`

```bash
pnpm pack:packages
```

`scripts/pack-packages.mjs` 做四件事：

1. **先清空** `.artifacts/tarballs/`（`rm -rf` 后重建）——每次都是干净目录，不要往里手工塞旧包，它们会被删掉；
2. 按拓扑序逐包跑 `pnpm pack --pack-destination .artifacts/tarballs`：telemetry → chord → ai → agent → review-llm → review-pi；
3. 任一个包失败就计数，最后 `pack: N 个包打包失败` 并 **exit 1**；
4. 成功时打印 tarball 数量、目录与每个的大小。

拓扑序只为日志可读、并与 `pnpm -r publish` 的发布序一致；tarball 之间**没有打包期依赖**——`pnpm pack` 会把每个包 `dependencies` 里的 `workspace:*` 就地改写成真实版本号（仓内开发仍走 workspace 链接，两者互不影响）。

成功输出末尾形如（本次实测）：

```text
review-pi prepack: 发布物在位（dist / bin / presentation / 许可证履约）

pack: 6 个 tarball -> .artifacts/tarballs
  review-agent-pi-chord-0.85.1.tgz  144.5 KiB
  review-agent-pi-pi-agent-core-0.85.1.tgz  564.4 KiB
  review-agent-pi-pi-ai-0.85.1.tgz  669.4 KiB
  review-agent-pi-pi-telemetry-0.85.1.tgz  27.4 KiB
  review-llm-0.1.0.tgz  7.8 KiB
  review-pi-0.1.0.tgz  270.4 KiB
```

产物清单与内容要点：

| tarball | 大小 | 内容要点 |
|---|---|---|
| `review-agent-pi-pi-telemetry-0.85.1.tgz` | 27.4 KiB | `dist/` + `package.json` + `README.md` |
| `review-agent-pi-chord-0.85.1.tgz` | 144.5 KiB | 同上 + `src/delta/README.md`（文档，见下表说明） |
| `review-agent-pi-pi-ai-0.85.1.tgz` | 669.4 KiB | 同上（最大，含 provider 模型数据） |
| `review-agent-pi-pi-agent-core-0.85.1.tgz` | 564.4 KiB | 同上（运行循环） |
| `review-llm-0.1.0.tgz` | 7.8 KiB | 只有 `dist/` + `package.json` |
| `review-pi-0.1.0.tgz` | 270.4 KiB | `bin/` + `dist/` + `presentation/` + `THIRD-PARTY-NOTICES.md` |

合计约 1.6 MiB。**文件名 = 包名去掉 scope 前缀**（`@review-agent-pi/chord` → `review-agent-pi-chord-0.85.1.tgz`：去掉 `@`、`/` 换成 `-`）。scope 被整体替换（ADR-0028 §7）后文件名随之改变，安装命令必须按实际文件名写。

`.artifacts/` 已在 `.gitignore` 里：产物不进版本库，也不需要提交。

#### 2.7.3 检查 tarball 内容（装之前先看）

`tar` 用系统自带的（Windows 10+ 内置 bsdtar，PowerShell 里直接 `tar`；Git Bash 的 GNU tar 也行）。

```powershell
# 列出全部条目
tar -tzf .artifacts/tarballs/review-pi-0.1.0.tgz

# 只看顶层
tar -tzf .artifacts/tarballs/review-pi-0.1.0.tgz | Select-String "^package/[^/]+/?$"

# 不落盘直接看包清单
tar -xzOf .artifacts/tarballs/review-pi-0.1.0.tgz package/package.json
```

```bash
tar -tzf .artifacts/tarballs/review-pi-0.1.0.tgz
tar -tzf .artifacts/tarballs/review-pi-0.1.0.tgz | grep -E '^package/[^/]+/?$'
tar -xzOf .artifacts/tarballs/review-pi-0.1.0.tgz package/package.json
```

条目都以 `package/` 开头（npm/pnpm 的固定布局）。三个必看点：

1. **没有 `package/src/**/*.ts`**：源码不随包发出。`files` 是白名单，`exports.source` 条件只在仓内（vitest / typecheck）生效，安装方走 `exports.default` 的 `dist/*.js`。唯一的 `src` 是 `chord` 上游带出的 `package/src/delta/README.md`（文档，不是代码，`verify:pack` 也放行）；
2. **依赖里没有 `workspace:*`**：`package/package.json` 应看到 `"review-llm": "0.1.0"`、`"@review-agent-pi/pi-ai": "0.85.1"` 这类真实版本号。看到 `workspace:*` 说明是用 `npm pack` 而非 `pnpm pack` 打的，装出去必然解析失败；
3. **`review-pi` 必须有四样**：`package/bin/review-pi.js`、`package/dist/cli/main.js`、`package/presentation/engine-zh.js`、`package/THIRD-PARTY-NOTICES.md`。

#### 2.7.4 安装布局验证：`pnpm verify:pack`

```bash
pnpm verify:pack
```

这是**离线**的安装面冒烟：不联网、不发布、不写 registry、不碰全局 `node_modules`。做法是把 `.artifacts/tarballs/` 的六个 tarball 解到 `.artifacts/verify/app/node_modules/`（模拟真实安装布局），再把仓内 `packages/*/node_modules` 里已装好的第三方依赖按包 junction 过去（**只借依赖图，不借源码**），然后逐项断言：

| # | 断言 | 红了说明 |
|---|---|---|
| 1 | 内容面：六个包名都在发行清单里、`src` 下没有源码文件（`chord` 的 `src/delta/README.md` 放行）、每个包有必需文件 | `files` 配错 / 打包漏文件 / 混进源码 |
| 2 | `review-pi`（无子命令）打印含 `missing command` 的 usage | `bin` 的腿表在安装布局下定位不到 `dist` |
| 3 | `config init` 能写、`config show --json` 出配置快照（`version: 1`、`limits.boundary.maxFiles` 是数字） | 配置面引用了仓内路径 |

全绿时尾部输出：

```text

```

它还会在 `.artifacts/verify/INSTALLED.md` 留一份安装面清单（包名 + 版本 + 临时目录），排障时先看这个。每次运行都会先 `rm -rf` 整个 `.artifacts/verify/`，可以随时删。

注意：

- 需要系统 `tar`，缺了会报 `verify-pack: 无法列出 tarball（需要系统 tar）`；
- 借用的是**本仓已安装**的第三方依赖，所以先 `pnpm install`；仓里没装 `@vscode/ripgrep` 时第 5 条会红；
- 它不是发布门（发布必须由人确认 registry），只是「打出来的包到底能不能用」的本地门。

#### 2.7.6 打包 ≠ 发布

- `pnpm pack:packages`：只往本地产出文件，**不联网**；
- `pnpm publish:packages`：= `pnpm build:dist && pnpm -r publish`，**会真的往 registry 推**。需要：`.npmrc` 指向目标 registry（§2.3）、有写权限的 token、六个包版本成套且 registry 上不存在同版本号（npm 不允许覆盖已发布版本）；
- `pnpm -r publish` 按拓扑序发布，保证 `review-pi` 推上去时它的五个依赖已经可解析；
- 只想把 tarball 交给别人（U 盘 / 内网制品库）时，**不要**跑 `publish:packages`。

发布前检查单：

- [ ] `pnpm build:dist` 是本次新跑的（不是昨天的 `dist/`）；
- [ ] `pnpm pack:packages` exit 0，六个 tarball 都在；
- [ ] `pnpm verify:pack` 全绿；
- [ ] `git status` 干净（`prepack` 复制的 `packages/review-pi/THIRD-PARTY-NOTICES.md` 是 gitignored，不算脏）；
- [ ] 已确认 registry 与凭据，再执行 `pnpm publish:packages`。

#### 2.7.7 打包失败对照

| 现象 | 原因 | 处置 |
|---|---|---|
| `review-pi prepack: 发布物不完整（N 项缺席）——先跑 pnpm build:dist` | 没构建，或只跑了 `build:pi` | 跑完整 `pnpm build:dist`，再打包 |
| `ERR_PNPM_BIN_CRLF` | `bin/` 行尾被改成 CRLF（编辑器 / git autocrlf） | `git checkout -- packages/review-pi/bin` 恢复；`.gitattributes` 已把 `packages/review-pi/bin/**` 固定为 LF，不要手工改行尾 |
| tarball 的 `package.json` 里依赖还是 `workspace:*` | 用了 `npm pack` 而非 `pnpm pack` | 只用 `pnpm pack:packages`（内部即 `pnpm pack`） |
| `pack: N 个包打包失败` | 某包 `pnpm pack` 非零退出（常见是 `review-llm` 的 `prepare` 重跑 tsc 报类型错） | 看该包上面那段输出，先修类型 |
| `verify-pack: 没有 tarball —— 先跑 pnpm pack:packages` | `.artifacts/` 被清过 | 重新打包 |
| `verify-pack: ... 里混进了源码` | 包的 `files` 白名单被改宽 | 改回白名单，不要把 `src` 加进去 |
| `verify-pack: 无法列出 tarball（需要系统 tar）` | 系统没有 `tar` | 装 tar（Windows 用内置 bsdtar 即可） |
| 装完 `review-pi` 报 `Cannot find module 'review-llm'` | 只装了 `review-pi` 一个 tarball | 六个一起装（§2.4） |

## 3. 配置

配置是**唯一**的凭据与运行参数来源（ADR-0025）。环境变量层已彻底移除：`REVIEWER_*` / `DEEPSEEK_*` / `REVIEW_PI_*` 不再被读取，`--env` 是确定性错误。

### 3.1 文件位置与优先级

| 场景 | 路径 |
|---|---|
| Windows 默认 | `%USERPROFILE%\.PiAgent\PiAgent.jsonc` |
| macOS / Linux 默认 | `$HOME/.PiAgent/PiAgent.jsonc` |
| 显式指定 | `--config <path>`（`review` / `smoke` / `config` 全子命令通用） |

规则：

1. `--config` 优先；相对路径按**进程 cwd** 解析。
2. 没给 `--config` 就读用户主目录（Windows 读 `USERPROFILE`，POSIX 读 `HOME`）。
3. **WSL 读的是 Linux 的 `$HOME`**，不是 Windows 的 `C:\Users\...`。两边要各配一份，或者统一用 `--config /mnt/c/Users/...`。
4. 配置文件**不存在**不是错误：按内置缺省运行，但 review / smoke 会因为没有 `reviewer.apiKey` 而 fail fast。
5. 配置在进程启动时**读一次**，运行中改文件不影响本次 run。

### 3.2 生成配置文件

```bash
review-pi config init
```

输出：

```text
review-pi: 已写入配置文件 /home/you/.PiAgent/PiAgent.jsonc
```

行为：

- 目录自动创建；POSIX 下目录 `0700`、文件 `0600`（Windows 上 mode 只影响只读位）；
- 文件已存在时**拒绝覆盖**：`配置文件已存在（...）——加 --force 覆盖`，退出码 1；
- `--force` 会整文件覆盖，**包括你已填的 key**。更推荐用编辑器改，而不是 `--force`；
- 写到自定义路径：`review-pi config init --config /path/to/PiAgent.jsonc`。

生成的内容是完整模板（所有键 + 注释 + 缺省值），与仓库根 [`PiAgent.example.jsonc`](../PiAgent.example.jsonc) 同源。

### 3.3 最小可跑配置

手工创建也可以。文件**一旦存在就必须有 `version: 1`**（缺 `version` 会 fail fast）：

```jsonc
{
  "version": 1,
  "reviewer": {
    "apiKey": "sk-..."
  }
}
```

其余键全部走内置缺省：

- `reviewer.baseUrl` = `https://api.deepseek.com`（官方直连）
- `reviewer.maxOutputTokens` = `null`（自动判档）
- `model.default` = `deepseek-v4-flash`
- `model.presentation` = `null`（跟随检视模型）
- `presentation.engine` = `null`（手写最小文件、整段省略时不投影中文）；`config init` 生成的模板会显式写 `"builtin"`（默认开中文）
- `limits` = 内置缺省（见 §3.5.4）

### 3.4 推荐配置（两个场景）

**场景 A：官方直连**

```jsonc
{
  "version": 1,
  "reviewer": {
    "apiKey": "sk-...",
    "baseUrl": "https://api.deepseek.com",
    "maxOutputTokens": null
  },
  "model": {
    "default": "deepseek-v4-flash",
    "presentation": null
  },
  "presentation": {
    "engine": "builtin"
  }
}
```

**场景 B：OpenAI 兼容网关 / 方舟接入点**

```jsonc
{
  "version": 1,
  "reviewer": {
    "apiKey": "gw-...",
    "baseUrl": "https://gateway.example.com/v1",
    "maxOutputTokens": 32768
  },
  "model": {
    "default": "ep-20261031-xxxxxxxx",
    "presentation": null
  },
  "presentation": {
    "engine": "builtin"
  }
}
```

要点：

- **`baseUrl` 必须自带网关要求的路径前缀**（通常是 `/v1`）。OpenAI SDK 只会追加 `/chat/completions`，不会替你补 `/v1`；
- `maxOutputTokens` 显式写 `32768` 与写 `null` 在网关档效果相同（自动判档就是 32768）；只有在网关上限更小、或你想压成本时才需要调小；
- 目录外的模型 id（网关别名、`ep-xxx`）也能直接跑，但内置目录没有它的画像，`contextWindow` / `maxTokens` / `cost` 会借用 `deepseek-v4-flash`（见 §3.5.2）；成本数字因此可能失真；
- `presentation.engine` 模板默认就是 `"builtin"`；改成 `null` 才会关掉中文按行建议（§3.5.3）。

### 3.5 字段逐项说明

#### 3.5.1 `reviewer`（检视链接入点）

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `reviewer.apiKey` | string | 无（`null`） | **必填**。只写在这个文件里；`config show` 与审计只报 `set|missing`（stdout 不输出配置），绝不回显值或长度。缺失时 review / smoke 在触碰文件系统前 fail fast。 |
| `reviewer.baseUrl` | string | `https://api.deepseek.com` | OpenAI 兼容 base URL。尾斜杠会被归一；官方/网关判档对 **scheme + host 大小写不敏感**，但 **path 逐字符有意义**（`/v1` 不是同一端点）——所以 `HTTPS://API.DEEPSEEK.COM/` 仍算官方直连，而 `https://api.deepseek.com/v1` 算网关。网关路径（如 `/v1`）要自己写全。 |
| `reviewer.maxOutputTokens` | 正整数或 `null` | `null` | 输出预算。`null` = 自动：**官方直连不发 `max_tokens`**；其他 baseUrl（网关）发 `32768`。显式数字则无论官方/网关都发送该值。 |

**`maxOutputTokens` 判档细节**：

- 官方直连不发 `max_tokens`，是为了对齐历史审计 wireBody 字节；不要为了「显式一点」而写 `32768`，那会改变请求体；
- 网关不显式给预算时，很多网关默认 2048，会把思维链吃光并静默截断——所以网关档默认发 32768；
- 网关上限较小（例如只允许 8192）时写 `8192`，否则会被网关以 `400` 拒绝；
- 出现 `truncationReasons` 含 `MODEL_MAX_TOKENS_REACHED` 时，优先调大该值（官方直连需要显式写才会下发）。

#### 3.5.2 `model`（模型选择）

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `model.default` | 非空 string | `deepseek-v4-flash` | 不传 `--model` 时使用。自由 id 透传，不做别名映射。 |
| `model.presentation` | 非空 string 或 `null` | `null` | **中文呈现投影**使用的模型。`null` = 跟随本次检视模型（三级链：`model.presentation` → `--model` → `model.default`）。 |

`--model <id>` 优先于 `model.default`；`model.presentation` 只影响翻译与建议生成，不影响检视模型。

目录外 id 的画像回退：id 不在内置目录（`deepseek-v4-flash` / `deepseek-v4-flash-vision-exp` / `deepseek-v4-pro`）时，使用 `deepseek-v4-flash` 的画像作模板，只替换 id。因此这类 id 的上下文窗口与单价都按 flash 计算，成本数字仅供参考；`--model` 的 id 本身不做别名映射，网关要能直接识别。

#### 3.5.3 `presentation`（中文投影引擎）

| 值 | 含义 |
|---|---|
| `"builtin"` | 使用包内自带的引擎（安装形态下是 `<包目录>/presentation/engine-zh.js`）。**`config init` 生成的默认值** |
| `null` | 不投影：stdout 是英文，只产 `reviews_en.json`（整段省略 = 同此） |
| 路径 | 模块路径。**相对路径按配置文件所在目录解析**，不是进程 cwd（ADR-0026） |

- 引擎模块不存在时：启动期打一行 stderr，按「未配置引擎」恒等直通，**exit 0**，不会白等投影超时；
- 引擎加载失败 / 协议不符 / 超时：stdout 回退英文源 + `presentation.degraded: true`，stderr 一行原因，**exit 0**；
- 投影成功时 stdout 的 `findings` 是中文，并追加 `presentation` 键（`language: "zh"`、术语表版本、`findingLinks`）；
- 中文落盘产物只有一份：`reviews_tips_zh.json`（ADR-0022）。`reviews_zh.json` 已停产，旧文件会被主动清除。

#### 3.5.4 `limits`（超时、并发、边界、归档、文本截断）

完整缺省：

```jsonc
{
  "limits": {
    "timeouts": {
      "skillPassMs": 600000,
      "skillBashMs": 120000,
      "ruleSkillExtractMs": 30000,
      "ripgrepMs": 30000,
      "probeHealthMs": 15000,
      "probeModelMs": 120000,
      "presentationRequestMs": 90000,
      "presentationBufferMs": 30000
    },
    "concurrency": { "suggestion": 4 },
    "boundary": {
      "maxFiles": 10,
      "maxDiffLines": 2000
    },
    "archive": {
      "maxArchiveBytes": 8388608,
      "maxEntries": 2000,
      "maxTotalUncompressed": 67108864,
      "maxCompressionRatio": 100
    },
    "micro": {
      "skillBashOutputChars": 256000,
      "packageHeadBytes": 8192,
      "queryEchoChars": 120,
      "callChainHops": 2,
      "toolNameChars": 60,
      "argumentsSummaryChars": 80,
      "progressDetailChars": 120
    }
  }
}
```

| 组 | 作用 |
|---|---|
| `timeouts` | 各阶段超时（毫秒）。`skillPassMs` 单个规则 Skill 会话；`skillBashMs` 规则包里的 bash 调用；`probeHealthMs` / `probeModelMs` 是 smoke 双探针；`presentationRequestMs` 单次翻译/建议请求；`presentationBufferMs` 投影总超时余量。 |
| `concurrency.suggestion` | 每条 finding 的 `suggestion` 并发生成数（缺省 4）。只影响中文 tips，不影响检视主循环。 |
| `boundary` | MR 边界护栏。`maxFiles` / `maxDiffLines` 任一维设 `null` = 该维不设界；**两维都 `null` = 护栏整体停用**（不度量、不告警）。超界只**告警**并加 `domainWarning`，不截断、不改退出码。 |
| `archive` | 规则包解压前的审计上限：压缩包字节、条目数、解压后总字节、压缩比。 |
| `micro` | 文本截断（工具输出、包头部、检索回显、调用链跳数、工具名/摘要、进度明细）。一般不用改。 |

### 3.7 从旧 `.env.local` 迁移（一次性）

```bash
review-pi config init --from-env .env.local
```

- `--from-env` 只在 `config init` 有效；路径按 **cwd** 解析；
- 读文件，但**不写 `process.env`**，不改变「env 层已关闭」的语义；
- 可迁移的源键只有七个：

| 源键 | 落到 |
|---|---|
| `REVIEWER_API_KEY` / `DEEPSEEK_API_KEY` | `reviewer.apiKey` |
| `REVIEWER_URL` / `DEEPSEEK_URL` | `reviewer.baseUrl`（必须以 `http(s)://` 开头，尾斜杠会去掉） |
| `REVIEWER_MAX_TOKENS` | `reviewer.maxOutputTokens`（必须是正整数） |
| `REVIEW_PI_PRESENTATION_ENGINE` | `presentation.engine`（相对路径按**迁移时的 cwd** 解析成绝对路径再写入） |
| `REVIEW_PI_PRESENTATION_MODEL` | `model.presentation` |

- 其余键会被丢弃，并在 stdout 列出 `已丢弃未识别键：...`；
- 源文件有无法解析的行时逐行提示并跳过；
- **`REVIEW_PI_PRESENTATION_ENGINE=builtin` 也会被当成相对路径**（迁移时统一 `resolve(cwd, value)`），不会保留哨兵。要内置引擎，迁移后手工把 `presentation.engine` 改回 `"builtin"`；
- 目标配置已存在时仍受 `--force` 约束；
- 迁移完成后建议删除 `.env.local`。它不会再被读取；放在 cwd 里只会让每次 review / smoke 多打一行提示：

```text
review-pi: 已不再读取 .env.local（本版配置见 --config 或 ~/.PiAgent/PiAgent.jsonc）；迁移：review-pi config init --from-env .env.local
```

> 这行提示只 stat 当前目录的 `.env.local`，不读内容。看到它不代表配置被使用。

### 3.8 多份配置（项目 / 环境切换）

```bash
review-pi review --config ./ci/PiAgent.ci.json --repo ... --mr ... --out ...
review-pi smoke  --config ./ci/PiAgent.ci.json
review-pi config show --config ./ci/PiAgent.ci.json
```

- `--config` 相对路径按 cwd；
- 每份配置独立 `digest`，审计里能区分；
- 不要把带 key 的配置提交到仓库；CI 里用 secret 挂载到临时文件，或由流水线在 job 内生成。

### 3.9 配置安全

- **秘密只进配置文件**：没有 `--api-key` 之类的旗标，避免 key 出现在 shell history / 进程列表 / CI 日志；
- POSIX 权限建议 `0600`；文件宽于 `0600` 只警告，不影响运行，但同机其他用户可能读到；
- 目录 `0700` 的意义是「连这里有个配置文件都不让其他用户看到」；
- `config show`、审计、stdout、错误信息都不会回显 key 值或长度；
- 审计里的 `config` 是**脱敏快照**（`secret.reviewer.apiKey = set|missing`），`digest` 不是 key 的哈希，不能反推。

## 4. 网关自检（`smoke`）

### 4.1 什么时候跑

- 第一次安装后；
- 改了 `reviewer.baseUrl` / `reviewer.apiKey` / `model.default`；
- 换了网关、换了模型 id（尤其是 `ep-xxx`）；
- review 报网络错、401、404、429、长时间无输出；
- 升级 `review-pi` 后。

### 4.2 命令

```bash
review-pi smoke
review-pi smoke --model ep-20261031-xxxxxxxx
review-pi smoke --config ./ci/PiAgent.ci.json
```

`smoke` 只认 `--model` 与 `--config`；端点与 key 永远取配置。不传 `--model` 时用 `model.default`。

### 4.3 它实际做什么

两个探针，**成功时都会发真实 HTTP 请求**（健康探针失败时第 2 步会跳过）：

| 探针 | 请求 | 目的 |
|---|---|---|
| 1/2 网关健康 | `GET <baseUrl>/models` | 确认网关可达、DNS/TLS/代理通、key 至少能过传输层 |
| 2/2 模型可达 | `POST <baseUrl>/chat/completions`，body 含 `max_tokens: 1`、`stream: false` | 确认该模型 id 被网关接受，并且返回带 `choices` 与 `usage` 的 chat completion |

第 2 步会消耗极少 token（`max_tokens: 1`），但不是零成本。

### 4.4 输出怎么读

通过时：

```text
smoke probes at https://gateway.example.com/v1 (model ep-20261031-xxxxxxxx): OK
[1/2] gateway health: gateway is up at https://gateway.example.com/v1 (HTTP 200)
      models visible at the gateway (first 8 of 42): ..., ...
[2/2] model reachability: model "ep-20261031-xxxxxxxx" is reachable at https://gateway.example.com/v1 (...)
```

失败时第 1 行是 `FAILED`，随后每个探针给出人话归因与 `detail`（网关错误体摘要）。退出码：**通过 0 / 任何失败 1**。

### 4.5 失败诊断对照

| 诊断关键字 | 含义 | 处置 |
|---|---|---|
| `gateway unreachable ... DNS lookup failed` | 域名解析不了 | 检查 `baseUrl` 拼写、内网 DNS、VPN |
| `connection refused` | 主机端口没人监听 | 检查端口、是否该走代理 |
| `request timed out` | 连接/响应超时 | 检查网络与代理；网关慢时调大 `limits.timeouts.probeHealthMs` / `probeModelMs` |
| `authentication failed (HTTP 401/403)` | key 被拒 | `review-pi config show` 确认 `set`；确认 key 属于该网关；环境变量不再生效 |
| `rate limited (HTTP 429)` | key 有效但被限流 | 稍后重试；批量跑时降低并发 |
| `model ... was not found (HTTP 404)` | 模型 id 不被该端点服务，或 `baseUrl` 少了 `/v1` | 补 `/v1`；确认 `ep-xxx` 属于该 region/账号；`GET /models` 的列表可对照 |
| `gateway server error (HTTP 5xx)` | 网关自身故障 | 重试或联系网关运维 |
| `rejected the request body (HTTP 4xx)` | 请求体不被接受（常见是 `max_tokens` 超上限或参数不兼容） | 调小 `reviewer.maxOutputTokens`；确认网关是 OpenAI Chat Completions 兼容 |
| `not with a chat completion carrying choices and usage` | 返回不是标准 chat completion，或缺 `usage` | 该网关不满足计费/审计契约；换端点或让网关补齐 `usage` |
| `silently routed to a different model` | 请求的 id 与实际响应 model 不一致 | 典型是 `baseUrl` 路径错（缺 `/v1`）；修好前不要相信任何 run 结果 |

### 4.6 smoke 通过但 review 仍失败

| 可能 | 说明 |
|---|---|
| 模型在长上下文/工具调用下才失败 | smoke 只发一条 `ping`；review 会发系统提示、工具 schema、仓内代码。看 stderr 与审计里的 `truncationReasons` |
| 429 在批量时出现 | smoke 是单请求；批量跑会叠加并发，见 §7 |
| 输出预算不够 | 网关档默认 32768；若被路由到小输出模型，显式调小反而可能更稳；出现 `MODEL_MAX_TOKENS_REACHED` 时调大 |
| MR 超界 | 只告警不失败，但结论按 out-of-domain 看待（§5.10） |
| 规则包脚本失败 | 主检视照常；看审计 `ruleSkill[]` / `skillPassLog[]` 与 stderr |

## 5. 第一次检视

### 5.1 准备三样输入

| 输入 | 要求 | 说明 |
|---|---|---|
| 仓库快照 | 一个**目录** | 停在 diff 的 **base 侧**。CLI 不会 apply diff；它读的是目录现状。 |
| diff 文件 | 一个**可读文件** | 标准 unified diff。`caseId` = 文件名去掉最后一个扩展名。 |
| issue 文本 | 可选字符串 | 原样进入初始 user 消息。建议用数据集原文，不要自编写。 |

`caseId` 细节：

- `VUL4J-38.diff` → `VUL4J-38`；
- `a.b.diff` → `a.b`（只去掉最后一段扩展名）；
- 无扩展名 → 整个文件名；
- 落盘时会再做文件系统安全化：非 `[A-Za-z0-9_.-]` 的字符替换成 `_`。所以 `a b.diff` 与 `a_b.diff` 在同一个 `--out` 下会落到同一个 `caseId` 目录。

### 5.2 最简命令

```bash
review-pi review \
  --repo /data/snapshots/my-repo-base \
  --mr /data/diffs/change-001.diff \
  --out /data/reviews/change-001
```

- `--out` 省略时是 **`review-pi-output`**（相对 cwd）；
- `--repo` / `--mr` / `--out` 都按 **cwd** 解析相对路径；
- 建议第一次就用绝对路径，避免「我在哪个目录跑的」这种问题。

### 5.3 带 issue

```bash
review-pi review \
  --repo /data/snapshots/my-repo-base \
  --mr /data/diffs/change-001.diff \
  --issue "Fix NPE in OrderService when customer is null (CVE-2026-xxxx)." \
  --out /data/reviews/change-001
```

PowerShell 里 issue 含空格、括号、URL 时整体用双引号包住；注意 `$` 会被 PowerShell 展开，issue 文本里尽量避免 `$`，或用单引号。

### 5.4 带规则 Skill

规则包**只认显式输入**，不会扫描被检视仓库的 `.review-rules/`（ADR-0027）。

```bash
# zip 包（可重复，顺序 = 执行顺序）
review-pi review ... \
  --rule-skill-zip /data/rules/general-code-review.zip

# 已解压目录（可重复；与 zip 共存时排在全部 zip 之后）
review-pi review ... \
  --rule-skill /data/rules/general-code-review

# 包内多 skill 时指定一个
review-pi review ... \
  --rule-skill-zip /data/rules/pack.zip \
  --rule-skill-name general-code-review

# 装载失败即失败（CI / 生产）
review-pi review ... \
  --rule-skill-zip /data/rules/general-code-review.zip \
  --strict-rule-skill
```

不传规则包也能跑：主检视照常，stderr 一行提示，exit 0。带 `--strict-rule-skill` 但不传任何包会报错。

### 5.5 带中文投影

前提是配置里 `presentation.engine` 不是 `null`（推荐 `"builtin"`）。命令不变，不加任何旗标：

```bash
review-pi review --repo ... --mr ... --out ...
```

stderr 会先出一行：

```text
review-pi: 呈现投影进行中（自然语言字段译中文）……
```

然后 stdout 的 `findings` 是中文，并追加 `presentation` 键；同一 `rep-1/` 下多出 `reviews_tips_zh.json`，cwd 里多出 `review-result.json`。

### 5.6 一次 review 的完整行为

```text
parse args
  → 配置装载（读一次 → 不可变快照）
  → 凭据 fail fast（缺 reviewer.apiKey）
  → 读 --repo 目录 / --mr 文件
  → runReview：
       MR 初始上下文 → 六阶段循环（工具驱动 + Context Ledger）
       → Phase 5 后每个规则 Skill 一个独立会话
       → 候选门 → 合并 → 判定
       → 写 RunRecord / 审计 / 会话转录 / reviews_en.json
  → 可选中文投影（只改 stdout 与 reviews_tips_zh.json）
  → stdout 单 JSON
  → 退出码
```

**stdout 契约**：整个 stdout 是**一个 JSON 文档**，不会混入日志。顶层键：

```json
{
  "ok": true,
  "caseId": "change-001",
  "runId": "20261031T101500.000-change-001",
  "truncated": false,
  "rounds": 5,
  "toolCalls": 23,
  "findings": [ ... ],
  "auditPath": "/data/reviews/change-001/audit/mr/change-001/rep-1/audit/<runId>.json",
  "presentation": { "language": "zh", "terminologyVersion": 1, "findingLinks": [...] }
}
```

- `presentation` 只在配置了投影引擎时出现；降级时是 `{ "language": "en", "degraded": true }`；
- 成本与 usage **不在 stdout**，在 `rep-1.json` 与审计里；
- 一切诊断、进度、警告都在 **stderr**。

**退出码**：

| 码 | 含义 |
|---|---|
| `0` | 完成。包括**诚实截断**（`truncated: true`）——截断是完成的一种，不是失败 |
| `1` | 用法错误、配置错误、凭据缺失、网络/模型错误、产物写失败、`--strict-rule-skill` 装载失败等 |

**stderr 常见但不算失败的行**：

- `review-pi: 未装载任何规则包（...），照常检视`
- `review-pi: 呈现投影进行中（自然语言字段译中文）……`
- `review-pi: 呈现投影降级为英文源文档（原因）`
- `review-pi: 本次未产分组意见（原因）`
- `review-pi: 执行目录副本写入失败（路径: 原因）`（cwd 只读等，exit 仍 0）
- `.env.local` 已不再读取的提示

### 5.7 产物树

`<out>` 是落盘根（Runs Root；ADR-0027 没有实验标识层）：

```text
<out>/
├── runs/mr/<safeCaseId>/
│   ├── rep-1.json                                  # RunRecord（模型、usage、findings 计数、auditPath）
│   ├── session-<runId>.json                        # 主会话转录
│   ├── session-<runId>-skill-<name>-r<N>.json      # 每个规则 Skill 会话一条
│   └── rep-1/
│       ├── reviews_en.json                         # 英文 findings 真源（恒产）
│       └── reviews_tips_zh.json                    # 中文按行分组建议（配了引擎且 tips 合法才产）
├── audit/mr/<safeCaseId>/rep-1/audit/
│   └── <runId>.json                                # 审计：请求、工具调用、相位、ledger、ruleSkill、config
└── .cache/rule-skills/
    ├── <sha256>/                                   # zip 规则包解压缓存
    └── dir-<sha256>/                               # 已解压目录的内容哈希缓存
```

cwd（进程执行目录）里还会有：

```text
<你执行命令的目录>/
└── review-result.json        # 仅当本次产出 tips；与 rep-1/reviews_tips_zh.json 逐字节相同
```

- 权威真源永远是 `<out>/.../rep-1/reviews_tips_zh.json`；
- cwd 副本是便利文件，写失败只警告、不改退出码；
- 本次不产 tips 时，cwd 里的 `review-result.json`（以及旧版本写过的 `reviews_tips_zh.json`）会被删除，保证「有就是本次的」；
- 如果你在 git 仓库根目录跑，记得把 `review-result.json` 加进 `.gitignore`。

### 5.8 结果怎么读

| 入口 | 适合看什么 |
|---|---|
| stdout JSON | 快速接管道、CI 提取 `findings` / `truncated` / `auditPath` |
| `rep-1/reviews_en.json` | 人工阅读英文 findings（结构化真源） |
| `rep-1/reviews_tips_zh.json` | 按文件、按行分组的 10 键中文建议 |
| `audit/.../<runId>.json` | 成本、轮次、工具调用、上下文账本、规则包装载、配置快照 |
| `runs/mr/<caseId>/rep-1.json` | 一眼看模型、usage、finding 数、`auditPath` |
| `session-*.json` | 复盘消息序列与工具调用细节 |

三个快速校验（PowerShell / bash 通用思路，把路径换成你的）：

```bash
# stdout 是否为合法 JSON 且 ok=true
review-pi review ... | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{const j=JSON.parse(s);console.log(j.ok,j.caseId,j.findings.length,j.truncated)})"

# tips 的文件数与每组条数
node -e "const d=require('./review-result.json');console.log(d.files.length,d.files.map(f=>f.reviewTips.length))"

# en 与 tips 的条数对照（tips 按同文件同行去重，通常 <= en）
node -e "const fs=require('fs');const en=JSON.parse(fs.readFileSync(process.argv[1]));const tips=JSON.parse(fs.readFileSync('review-result.json'));console.log(en.findings.length,tips.files.reduce((n,f)=>n+f.reviewTips.length,0))" path/to/reviews_en.json
```

### 5.9 重跑与覆盖语义

`rep` 恒为 **1**（单次检视没有 rep 采样概念）。同一个 `--out` 再跑一次：

| 产物 | 行为 |
|---|---|
| `runs/mr/<caseId>/rep-1.json` | **覆盖** |
| `runs/mr/<caseId>/rep-1/reviews_en.json` | **覆盖** |
| `runs/mr/<caseId>/rep-1/reviews_tips_zh.json` | 覆盖；本次不产则**删除** |
| cwd `review-result.json` | 覆盖；本次不产则**删除** |
| `audit/.../<runId>.json` | **新增**（`runId` 含时间戳，旧审计保留） |
| `session-<runId>.json` | **新增**（旧转录保留） |
| `<out>/.cache/rule-skills/` | 命中缓存则复用；规则包内容变了就是新哈希目录 |

所以：

- **想保留多次结果 → 每次换一个 `--out`**；
- 同一个 `--out` 适合「同一 case 的迭代重跑」，磁盘上只留最新一份 canonical 产物，但审计/转录会累积；
- `caseId` 由 `--mr` 文件名决定，改文件名就是换 case。

### 5.10 MR 边界

超过 `limits.boundary.maxFiles`（缺省 10）或 `maxDiffLines`（缺省 2000）：

- **只告警**，不截断、不改退出码；
- 结果顶层带 `domainWarning`，审计尾部带 `mrBoundary`（度量值 + 降级决策）；
- 结论按 out-of-domain 看待；
- 任一维设 `null` = 该维不设界；两维都 `null` = 护栏停用。

## 6. 在任意目录运行

### 6.1 为什么可以

安装形态下，命令不依赖你在哪个目录：

1. **bin 在 PATH 里**：`npm i -g` 生成全局 shim（Windows 是 `review-pi.cmd`），由 npm 的全局 bin 目录提供；
2. **依赖从包的安装位置解析**：bin 用 `import.meta.url` 定位自己，再按 Node 的包解析规则找 `dist/` 与六个包的 `node_modules`，与 cwd 无关；
3. **配置从 home 读**：默认 `~/.PiAgent/PiAgent.jsonc`，与 cwd 无关；
4. **builtin 引擎在包内**：`"builtin"` 解析到 `<包目录>/presentation/engine-zh.js`，不依赖 cwd；
5. **只有输入/输出路径相对 cwd**：那是你显式给 CLI 的路径，理应按你当前所在目录解释。

### 6.2 相对路径基准表

| 参数 | 相对谁 | 说明 |
|---|---|---|
| `--repo` | cwd | `resolve(args.repo)` |
| `--mr` | cwd | `readFile(resolve(args.mr))` |
| `--out` | cwd | 缺省 `review-pi-output` 也在 cwd 下 |
| `--config` | cwd | 缺省走 home |
| `--rule-skill-zip` | cwd | loader 直接 stat/read |
| `--rule-skill` | cwd | loader 直接 stat/copy |
| `--from-env` | cwd | 仅 `config init` |
| 自定义引擎路径 | **配置文件所在目录** | 不是 cwd（ADR-0026） |

### 6.3 cwd 的三个副作用

跑 review 时，当前目录会发生三件事：

1. **`review-result.json` 的写/删**：产出 tips 时写一份；不产时删除旧副本。写失败只警告，exit 0。
2. **`.env.local` 探测**：只 `stat`，不读内容；存在就打一行「已不再读取」提示。
3. **规则 Skill 的 bash 子进程 cwd 是规则包缓存目录**，不是你的 cwd。规则包里的脚本写相对路径文件时，落在 `<out>/.cache/rule-skills/<digest>/` 下。

除此之外，review **不写 cwd**：审计、转录、导出、规则包缓存全部在 `--out` 下。

### 6.4 推荐姿势

- 第一次跑：所有路径用**绝对路径**；
- 长期跑：给每个 case 一个固定工作目录，`cd` 进去再用相对路径；
- 不要在只读目录（如系统目录、挂载的只读盘）里跑：canonical 产物写 `<out>` 没问题，但 cwd 副本会失败并警告；
- 在 git 仓库根跑时，把 `review-result.json` 加进 `.gitignore`。

### 6.5 三种 shell 的示例

**PowerShell**

```powershell
$case = "change-001"
$base = "D:\reviews\$case"
New-Item -ItemType Directory -Force -Path $base | Out-Null
review-pi review `
  --repo "D:\data\repos\my-repo-base" `
  --mr "D:\data\diffs\change-001.diff" `
  --issue "Fix NPE when customer is null." `
  --out "$base\out"
```

**cmd**

```bat
review-pi review --repo D:\data\repos\my-repo-base --mr D:\data\diffs\change-001.diff --out D:\reviews\change-001\out
```

**bash**

```bash
review-pi review \
  --repo /data/repos/my-repo-base \
  --mr /data/diffs/change-001.diff \
  --out /data/reviews/change-001/out
```

### 6.6 CI 里的最小步骤

```yaml
- run: npm i -g review-pi
- run: |
    mkdir -p "$RUNNER_TEMP/review-cwd"
    cd "$RUNNER_TEMP/review-cwd"
    review-pi review \
      --repo "$REPO_PATH" \
      --mr "$DIFF_PATH" \
      --out "$RUNNER_TEMP/review-out" \
      --no-progress
```

- `--no-progress`：stderr 不是 TTY 时本来就缺省关，显式写只是让日志更确定；
- key 用 CI secret 写进临时配置文件，跑完删除；
- 退出码直接作为 job 结果：0 成功（含截断），1 失败。

## 7. 并发与隔离

### 7.1 结论先说

**不同 `--out` + 不同 cwd = 不冲突。**

两个 run 只要满足：

- `--out` 指向不同的物理目录；
- 进程 cwd 不同（或你接受 cwd 副本互相覆盖）；

那么它们的 canonical 产物、审计、转录、规则包缓存、cwd 副本全部隔离，可以并行跑（前提是网关与机器资源扛得住并发请求；见 §7.4 第 6 条）。

但以下情况会冲突：

| 场景 | 冲突点 | 严重度 |
|---|---|---|
| 同 `--out` + 同 `caseId` | `rep-1.json`、`reviews_en.json`、`reviews_tips_zh.json` 互相覆盖 | 高（产物不可信） |
| 同 `--out` + 不同 `caseId` | run/audit 目录不同；但共享 `<out>/.cache/rule-skills` | 中（规则包冷启动竞态） |
| 不同 `--out` + 同 cwd | cwd 的 `review-result.json` 互相覆盖/删除 | 中（只影响便利副本） |
| 同 `--out` + 同 cwd | 以上全部 | 高 |
| 不同字符串但同一物理目录 | 等价于同 `--out` | 高 |

### 7.2 「不同」怎么判定

- CLI 对 `--out` 做 `path.resolve`：相对路径按 cwd 展开，`.` / `..` 会归一；
- 但 `resolve` **不跟随符号链接 / junction**。两个字符串指向同一个物理目录（例如 `D:\reviews` 与 `D:\link-to-reviews`）仍然会冲突；
- Windows 文件系统大小写不敏感：`D:\Reviews` 与 `D:\reviews` 是同一目录；
- 网络盘 / 挂载点：不同挂载路径指向同一后端存储，也会冲突；
- `caseId` 由 `--mr` 的 basename 派生，不看目录。`a/change.diff` 与 `b/change.diff` 在同一个 `--out` 下是同一个 case。

### 7.3 共享 out 时到底共享什么

**1）canonical 产物按 `caseId` 分目录**

```text
<out>/runs/mr/<caseId>/
<out>/audit/mr/<caseId>/
```

不同 `caseId` 不会互相覆盖 `rep-1.json` / `reviews_en.json`。

**2）规则包缓存是 out 级共享**

```text
<out>/.cache/rule-skills/<sha256>/
<out>/.cache/rule-skills/dir-<sha256>/
```

装载逻辑是「查 ready marker → 没有就 `rm -rf` → 重建 → 写 marker」。**没有跨进程锁**。两个进程同时冷启动同一个规则包时，可能：

- A 正在解压，B 把目录删了重建；
- A 刚写完 marker，B 又把目录删掉重建，A 后续加载读到的是被替换的目录；
- 结果是一个 run 的规则包装载降级（stderr / 审计 `degradedReason`），`--strict-rule-skill` 时直接 exit 1。

**3）规则 Skill 的 bash 以缓存目录为 cwd**

规则包里的脚本如果写相对路径文件（日志、临时产物），会写进共享缓存目录。两个 run 用同一个规则包、同一个 `out` 时会互相踩。

**4）cwd 副本是进程级共享**

`review-result.json` 固定写在 cwd，没有 case 前缀。两个 run 共用一个 cwd 时，后完成的覆盖先完成的；不产 tips 的 run 还会删掉它。

**5）不共享的东西**

- 配置：每个进程启动时读一次，互不影响；
- 审计 / 转录：文件名含 `runId`（时间戳 + caseId），不同 run 不会覆盖；
- 被检视仓库：只读，规则包缓存绝不写回仓库；
- `review-pi` 包本身：只读。

### 7.4 绝对安全的并发 checklist

1. **一次 run 一个 `--out`**，用绝对路径；不要复用、不要指向符号链接的同一目标。
2. **一次 run 一个 cwd**（`mkdir` 一个空目录再 `cd` 进去），或者接受 `review-result.json` 最后写入者胜。
3. **同一个 `out` 内保证 `caseId` 唯一**；不同目录的同名 diff 先改名。
4. **共享规则包时先预热一次**：单独跑一个最小 case，让缓存 marker 落地，再并行；或者每个 run 用独立 `out`。
5. **不要并行 `config init --force` 同一个文件**；配置文件是读一次的，运行中改不影响当前进程，但会让下一次 run 拿到不同配置。
6. **控制对外并发**：`concurrency.suggestion` 是**单进程内**建议生成的并发，不是全局限流；N 个 run 并行 = N 倍请求，容易撞 429。
7. **CI 里给每个 job 独立 workspace / out**；不要多个 job 共享缓存目录。

### 7.5 并行配方

**bash（每个 case 独立 cwd + out）**

```bash
run_one() {
  local case_id="$1" repo="$2" diff="$3"
  local base="/data/reviews/$case_id"
  mkdir -p "$base/cwd"
  (
    cd "$base/cwd" || exit 1
    review-pi review \
      --repo "$repo" \
      --mr "$diff" \
      --out "$base/out" \
      --no-progress \
      >"$base/stdout.json" 2>"$base/stderr.log"
  )
}

run_one change-001 /data/repos/a /data/diffs/change-001.diff &
run_one change-002 /data/repos/b /data/diffs/change-002.diff &
run_one change-003 /data/repos/c /data/diffs/change-003.diff &
wait
```

**PowerShell 7（`ForEach-Object -Parallel`）**

```powershell
$cases = @(
  @{ Id = "change-001"; Repo = "D:\data\repos\a"; Diff = "D:\data\diffs\change-001.diff" },
  @{ Id = "change-002"; Repo = "D:\data\repos\b"; Diff = "D:\data\diffs\change-002.diff" }
)

$cases | ForEach-Object -Parallel {
  $base = Join-Path "D:\reviews" $_.Id
  $cwd  = Join-Path $base "cwd"
  New-Item -ItemType Directory -Force -Path $cwd | Out-Null
  Push-Location $cwd
  try {
    review-pi review --repo $_.Repo --mr $_.Diff --out (Join-Path $base "out") --no-progress `
      *> (Join-Path $base "console.log")
  } finally {
    Pop-Location
  }
} -ThrottleLimit 3
```

PowerShell 5.1 没有 `-Parallel`，用 `Start-Process -Wait` 或 `Start-Job`，同样保证每个进程独立 cwd/out。

**CI matrix**

```yaml
strategy:
  matrix:
    case: [change-001, change-002, change-003]
steps:
  - run: |
      mkdir -p "runs/${{ matrix.case }}/cwd"
      cd "runs/${{ matrix.case }}/cwd"
      review-pi review \
        --repo "${{ github.workspace }}/repos/${{ matrix.case }}" \
        --mr "${{ github.workspace }}/diffs/${{ matrix.case }}.diff" \
        --out "${{ github.workspace }}/runs/${{ matrix.case }}/out" \
        --no-progress
```

每个 matrix job 天然独立 workspace；如果 runner 复用缓存，确保 `--out` 不落到共享路径。

## 8. 排障

### 8.1 安装

| 现象 | 原因 | 处置 |
|---|---|---|
| `review-pi: command not found` / `不是内部或外部命令` | 全局 bin 目录不在 PATH | `npm config get prefix`，把对应 bin 目录加进 PATH；重开终端 |
| `EBADENGINE` | Node < 22.19 | 升级 Node；不要忽略 |
| `EACCES` / `EPERM` | 全局目录无写权限 | 用用户级 prefix 或 nvm；不要 `sudo` |
| `failed to spawn ripgrep binary` | postinstall 没下到二进制 | 重装 `@vscode/ripgrep`，检查 GitHub 访问/代理/镜像 |
| `Cannot find module '@review-agent-pi/pi-ai'` | 只装了 `review-pi` 一个 tarball，或 registry 缺内核包 | 六个包成套安装 / 发布 |
| `ERR_PNPM_BIN_CRLF`（打包侧） | bin 行尾被改成 CRLF | 保持 `.gitattributes` 的 `eol=lf`；重新 checkout |
| `config show` 报 `--config 指定的文件不存在` | 显式路径写错 | 用绝对路径或先 `config init --config <path>` |

### 8.2 配置

| 现象 | 原因 | 处置 |
|---|---|---|
| `未找到用户级配置文件 ...（按内置缺省运行）` | 还没 init，或 home 不对（WSL） | `review-pi config init`；WSL 下注意 Linux home |
| `配置文件已存在（...）——加 --force 覆盖` | 重复 init | 直接编辑；确需重置才 `--force` |
| `parse error at line N, column M` | JSONC 语法错 | 按行列修；JSONC 允许注释和尾逗号，但字符串里的注释符是字面量 |
| `version is required` / `version must be 1` | 文件存在但缺/错 `version` | 加 `"version": 1` |
| `reviewer.apiKey must be a string` 等 | 类型错 | 按提示改；不做静默钳制 |
| `unknown key ...` 警告 | 拼写错、旧键或已删除的键（如 `models`） | 删掉或改成正确键；警告不阻断 |
| `... 已钉死（pinned），不会被采用` | 写了轮次/工具调用/温度等死钉项 | 删掉；行为不变 |
| `配置文件权限过宽`（POSIX） | 宽于 `0600` | `chmod 600 ~/.PiAgent/PiAgent.jsonc` |
| 缺 key 的人话错误 | `reviewer.apiKey` 为空 | 填 key；`config show` 确认 `set`；环境变量不再生效 |
| `--env 已移除...` | 旧命令 | 改用 `--config`；旧 `.env.local` 用 `config init --from-env` 迁移 |

### 8.3 smoke

见 §4.5 的完整对照表。补充两条：

| 现象 | 处置 |
|---|---|
| 第 1 步通过、第 2 步 `MODEL_NOT_FOUND` | 90% 是 `baseUrl` 少了 `/v1`，或 `--model` 不是该网关服务的 id |
| 第 1 步通过、第 2 步 `MALFORMED_RESPONSE` | 网关返回不是标准 chat completion 或缺 `usage`；换端点或让网关补齐 |

### 8.4 review

| 现象 | 原因 | 处置 |
|---|---|---|
| `--repo is not a directory: ...` | 路径错，或传了文件 | 传仓库快照根目录 |
| `ENOENT ... open ...diff` | diff 路径错 | 用绝对路径；确认文件可读 |
| `missing required flag --repo` / `--mr` | 少参数 | 补参数；注意 PowerShell 续行反引号后不能有空格 |
| `unknown flag --xxx` | 拼写错 / 旧旗标 | 对照 §9 速查；规则包用 `--rule-skill-zip` / `--rule-skill` |
| `未装载任何规则包...` | 没显式给规则包 | 合法降级，exit 0；要跑 skill 会话就补参数 |
| `no rule-skill archive given...` | `--strict-rule-skill` + 没给包 | 补包，或去掉 strict |
| 规则包抛错（strict） | 路径错 / 非 zip / 无 `SKILL.md` / 多 skill / 目录含符号链接 | 先去掉 strict 看审计 `degradedReason`；多 skill 用 `--rule-skill-name`；目录用 `--rule-skill` |
| stdout 长时间静默 | 中文投影逐字段调网关 | 正常；stderr 有「呈现投影进行中」；不需要中文就把 `presentation.engine` 设 `null` |
| 配了引擎但没产 tips | 投影降级 / tips 形状非法 / 网关不认呈现模型 | 读 stderr 原因；`model.presentation` 显式指定或设 `null` 跟随 |
| `presentation.engine 指向的模块不存在` | 路径错 / builtin 制品缺失 | 用 `"builtin"`；自建引擎用绝对路径 |
| `退出码 0 但 truncated=true` | 诚实截断（轮数 / 工具预算） | 不是失败；看审计 `truncationReasons` |
| `MODEL_MAX_TOKENS_REACHED` | 输出撞 `max_tokens` | 调大 `reviewer.maxOutputTokens`；官方直连需显式设才会下发 |
| cwd 没 `review-result.json` | 本次不产 tips / cwd 不可写 | 看 stderr；真源在 `rep-1/reviews_tips_zh.json` |
| 目录里有旧 `reviews_zh.json` | 已停产产物 | 本次 run 会主动清除；中文看 `reviews_tips_zh.json` |

### 8.5 并发

| 现象 | 原因 | 处置 |
|---|---|---|
| 两个 run 的 `reviews_en.json` 内容混了 | 同 out + 同 caseId | 每个 run 独立 `--out` |
| 规则包偶发降级 / `--strict` 偶发 exit 1 | 共享 out 的规则包缓存冷启动竞态 | 先预热，或独立 out |
| cwd 的 `review-result.json` 时有时无 | 多 run 共用 cwd，且有的不产 tips | 每个 run 独立 cwd |
| 大量 429 | 并行 run 叠加请求 | 降低并行度；错峰；看 `concurrency.suggestion` 只限单进程 |
| 一个 run 写产物时报 EACCES | out 在只读盘 / 网络盘权限 | 换本地可写目录 |

review-pi                                  # 打印 usage，exit 1（正常）

### 9.2 完整 usage（原样）

```text
usage: review-pi review --repo <path> --mr <diff-file> [--issue <text>] [--out <dir>] [--model <id>] [--config <path>] [--rule-skill-zip <path>]... [--rule-skill <dir>]... [--rule-skill-name <name>] [--strict-rule-skill] [--progress | --no-progress]
       review-pi smoke [--model <id>] [--config <path>]
       review-pi config <init|show> [--config <path>] [--force] [--from-env <file>] [--json]
  （smoke = 网关冒烟自检，P1b 双探针：网关健康 + 模型可达，输出人话诊断）
  （config init = 写缺省 JSONC；config show = 脱敏打印生效配置与来源）

配置（ADR-0025）：~/.PiAgent/PiAgent.jsonc（Linux $HOME / Windows %USERPROFILE%），JSONC。
环境变量不再被读取；--env 以移除（改用 --config）。

review 旗标：
  --repo    <path>       仓库快照根目录（必需）
  --mr      <diff-file>  MR diff 文件路径（必需；caseId = 文件名去扩展名）
  --issue   <text>       MR 议题描述（缺省空）
  --out     <dir>        输出目录（审计与运行记录落盘；缺省 review-pi-output）
  --model   <id>         评审模型 id（缺省取配置文件 model.default；自由 id 透传）
  --config  <path>       配置文件显式路径（相对路径按 cwd 解析；缺省用户级路径）
  --rule-skill-zip  <path>  规则 Skill zip 显式路径（可重复，顺序 = 执行顺序；
                            不自动扫描仓库内目录——不传就不装载规则包，ADR-0027）
  --rule-skill      <dir>   规则 Skill **已解压目录**（可重复；排在全部
                            --rule-skill-zip 之后；目录先审计再按内容哈希复制进 run
                            缓存，符号链接/越界一律拒绝）
  --rule-skill-name <name>  指定装载的规则 Skill 名（包内多 skill 消歧，逐包生效）
  --strict-rule-skill       规则 Skill 装载失败即报错（缺省降级、run 照常）
  --progress                显示运行进度（阶段 / 模型请求 / 工具调用 / skill 会话）到 stderr；
                            stderr 是 TTY 时缺省开，重定向收日志时缺省关
  --no-progress             关闭运行进度（批跑收日志时显式静音）

smoke 旗标：
  --model   <id>         冒烟模型 id（同缺省与校验；端点/key 取配置文件，绝不回显）
  --config  <path>       配置文件显式路径

config 旗标：
  init                   写缺省配置模板（已存在需 --force；POSIX 0600）
  show                   逐键打印生效值与来源（reviewer.apiKey 只显示 set/missing）
  --from-env <file>      init 时从 .env 文件一次性迁移（key / url / 呈现配置）
  --json                 show 输出机器可读 JSON（与审计 config 同形）
```

## 10. 安全与隐私

- **凭据**：只放配置文件；不通过命令行参数传 key；不提交配置文件；CI 用 secret 挂临时文件并在 job 末尾删除。
- **发送范围**：检视会把 `--repo` 中被工具读取的文件内容、`--mr` 的 diff、`--issue` 文本发给配置的模型端点。确认数据出境/留存政策后再对敏感仓库使用。
- **产物敏感性**：`reviews_en.json` / `reviews_tips_zh.json` / 审计 / 转录会包含代码片段、文件路径、模型输出与用量。`<out>` 与 cwd 副本都应按内部资料管理。
- **规则包信任**：`--rule-skill-zip` / `--rule-skill` 里的脚本由规则 Skill 的 `bash` 工具执行，工作目录是 `<out>/.cache/rule-skills/<digest>/`。只装载可信来源的规则包；不要把不可信 zip 直接喂给生产环境。
- **cwd 副本**：`review-result.json` 可能包含代码行与建议；在共享目录跑完后注意清理，或把它加进 `.gitignore`。
- **审计脱敏**：审计顶层 `config` 只记 `reviewer.apiKey: set|missing`，不记值；`digest` 不能反推 key。
