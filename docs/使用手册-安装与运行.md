# 使用手册：安装、配置与运行

> **面向谁**：拿到 `review-pi` 发行包、想在自己机器或 CI 上跑一次 MR 检视的人。不需要 clone 本仓，也不需要懂 pi 内核。
>
> **对应形态**：单包发行（ADR-0035）。产品只有一个包 `review-pi`；内核四包 `@earendil-works/{pi-telemetry,chord,pi-ai,pi-agent-core}` 是它的**普通 npm 依赖**（版本精确锁定，随安装自动拉取），本仓既不打包也不发布它们。
>
> **口径来源**：配置面 ADR-0025 / 0026，产物与规则包信任边界 ADR-0027，发行形态 ADR-0035（取代 ADR-0028 的多包形态）。本文只描述**已经实现**的行为，不引入新配置键、新开关。
>
> **配套文档**：单次检视的旗标细节与产物读法见《[运行手册-单次检视](运行手册-单次检视.md)》；仓内开发（clone + pnpm）也看那份。本文覆盖「装好的形态」从零到跑通的全过程。

---

## 0. 五分钟最短路径

如果你只想先跑通，按这六步做；每一步的细节在后面对应章节。

```bash
# 1. 确认 Node 版本（必须 >= 22.19.0）
node -v

# 2. 全局安装（包已发布到 registry 时；只有 tarball 见 §2.4，自己打包见 §2.7）
npm i -g @baize/review-pi

# 3. 生成用户级配置，然后填入 reviewer.apiKey
review-pi config init

# 4. 自检网关与模型（会发一次极小的真实请求）
review-pi smoke

# 5. 跑一次检视（所有路径都可以是绝对路径；--taskId 必需）
review-pi review --repo /abs/path/to/repo --mr-diff /abs/path/to/change.diff --taskId change-001

# 6. 取回本次 run 的 session 路径（主 session 在前；缺省 OpenCode 兼容版，--native 原生；加 --path <dir> 可复制出来）
review-pi export
```

跑完检查四处：

1. **stdout**：单个 JSON 文档，`ok: true`，`findings` 是本次检视意见；
2. **`~/.PiAgent/tasks/<taskId>/runs/reviews_en.json`**：英文 findings 真源；
3. **`~/.PiAgent/tasks/<taskId>/audit/<ts>.json`**：审计与配置快照（`<ts>` = 首次模型请求时刻，也是 stdout 的 `runId`）；
4. **执行目录的 `.review-pi-session.json`**：本次成功 run 的 session 索引（绝对路径；`review-pi export` 直接读它，见 §5.8）。

> **没有 `--help` / `--version`**：直接执行 `review-pi`（不带子命令）会打印 usage 并 **exit 1**，这是设计行为，不是安装失败。版本用 `npm ls -g @baize/review-pi --depth=0` 查看。

## 1. 安装前检查

### 1.1 Node.js 版本

`review-pi` 的 `engines` 是 **`>=22.19.0`**（与 pi 内核一致）。

```bash
node -v
npm -v
```

期望 `node -v` 输出 `v22.19.0` 或更高。低于该版本时：

- npm 可能只给 `EBADENGINE` 警告并继续安装，但运行时可能因内核 API 缺失而崩；
- 建议用 nvm / fnm / volta 切到 Node 22 LTS 最新版，或 Node 24。

**不要**用 Node 18 / 20 尝试运行。内核四包与 CLI 都按 Node 22 的 ESM 行为构建。

### 1.2 npm 与全局 bin 目录

```bash
npm config get prefix
```

- **Windows**：通常是 `C:\Users\<你>\AppData\Roaming\npm`，全局命令是 `review-pi.cmd`；
- **macOS / Linux**：通常是 `/usr/local` 或 `~/.nvm/versions/node/vXX/bin`，全局命令是 `review-pi`。

确认该目录在 `PATH` 里：

```powershell
# Windows PowerShell
Get-Command review-pi -ErrorAction SilentlyContinue
$env:PATH -split ';' | Select-String 'npm'
```

```bash
# macOS / Linux
command -v review-pi
echo "$PATH" | tr ':' '\n' | grep -E 'npm|node'
```

装完后 `Get-Command review-pi` / `command -v review-pi` 必须能定位到命令；否则先修 `PATH`，不要靠每次写全路径。

### 1.3 registry 与网络

```bash
npm config get registry
npm ping
```

默认是 `https://registry.npmjs.org/`。如果包发布在公司私有 registry，需要按 §2.3 配 scope 映射。

`npm ping` 失败通常意味着代理 / 证书 / 内网 DNS 问题。公司环境常见做法：

```bash
npm config set proxy http://proxy.example.com:8080
npm config set https-proxy http://proxy.example.com:8080
# 或使用环境变量 HTTPS_PROXY / HTTP_PROXY（npm 会读）
```

### 1.4 ripgrep 二进制（postinstall）

`review-pi` 依赖 `@vscode/ripgrep`，安装时会执行 postinstall 从 GitHub Releases 下载对应平台的 `rg` 二进制。

- 需要能访问 `github.com`（或公司镜像）；
- 下载失败时 `npm i` 可能仍显示成功，但运行检视会在代码检索阶段报 `failed to spawn ripgrep binary`；
- 验证方式见 §2.5 的安装面自检；
- 受限网络下可先配置 `@vscode/ripgrep` 的镜像环境变量（按其包 README），或改用带外网缓存的 registry。

### 1.5 平台与运行时依赖

| 项 | 要求 | 说明 |
|---|---|---|
| OS | Windows 10+ / macOS / Linux | 发行面冒烟（`verify:pack`）在当前平台验证安装布局（bin 腿表、配置子命令、builtin 引擎、wasm、ripgrep） |
| 架构 | x64 / arm64 | 取决于 `@vscode/ripgrep` 与 Node 的支持 |
| 语言运行时 | **不需要** | Java / Go / C/C++ 等语法均为 tree-sitter wasm，不调 `javac` / `go` / `g++` |
| shell | 不需要 | 主检视不依赖 bash；规则包的 `bash` 工具是另一层（见 §6.3） |
| 磁盘 | 每次 run 数 MB 起 | 审计、转录、规则包缓存都在 `<tasks 根>/<taskId>` 下；大仓 / 多轮 / 多规则包可到数十 MB |

### 1.6 权限

全局安装需要写 `npm prefix` 目录：

- **不要**用 `sudo npm i -g`（会把 root 属主文件带进用户环境，后续升级/卸载都麻烦）；
- 推荐 nvm / fnm / volta 管理的 Node，prefix 在用户目录；
- 或者改用户级 prefix：`npm config set prefix ~/.npm-global`，再把 `~/.npm-global/bin` 加进 `PATH`。

## 2. 安装

发行面是一个包；内核四包作为依赖由 npm 按 `dependencies` 自动解析：

| 包 | 版本 | 角色 |
|---|---|---|
| `@baize/review-pi` | `0.5.0` | Review CLI，提供 `bin: review-pi`（**唯一**发布的包，也是唯一需要显式安装的包） |
| `@earendil-works/pi-telemetry` | `0.85.1` | 依赖：遥测 |
| `@earendil-works/chord` | `0.85.1` | 依赖：编排 |
| `@earendil-works/pi-ai` | `0.85.1` | 依赖：模型接入（含 provider 模型数据） |
| `@earendil-works/pi-agent-core` | `0.85.1` | 依赖：代理循环 |

> 内核四包是**上游 npm 包**（MIT），版本四包成套、精确锁版（不带 `^`，ADR-0035）。`@baize/review-pi` 里已经声明了它们，`npm i -g @baize/review-pi` 会自动装齐——不需要、也不应该单独安装这四个包。

| 你现在的情况 | 走哪一节 |
|---|---|
| 已发布到能访问的 registry | §2.1（全局）或 §2.2（项目内） |
| 只有私有 registry，或需要代理上游 scope | §2.3 |
| 手上已有 `@baize/review-pi` 的 `.tgz`（还没发布 / 内网拷贝） | §2.4 |
| 手上没有 `.tgz`，需要自己从源码打 | §2.7，再回到 §2.4 安装 |

### 2.1 方式 A：公开 registry 全局安装（推荐）

```bash
npm i -g @baize/review-pi
```

装完后：

```bash
review-pi
```

预期输出（stderr）开头是：

```text
review-pi: missing command (expected `review`, `smoke` or `config`)
usage: review-pi review --repo <path> (--mr-diff <diff-file> | --mr-json <files-json>) ...
```

退出码 **1**。这条命令的作用只是确认 bin 能被拉起、main 入口能跑到用法提示。真正的成功标志是后面 `config init` / `smoke` / `review`。

### 2.2 方式 B：装进项目（不污染全局）

```bash
cd /path/to/your-project
npm i @baize/review-pi
npx review-pi config init
npx review-pi smoke
npx review-pi review --repo ... --mr-diff ... --taskId ...
```

或在 `package.json` 里加 script：

```json
{
  "scripts": {
    "review": "review-pi review --repo ./repo --mr-diff ./change.diff --taskId change-001 --tasks-dir ./review-tasks"
  }
}
```

`npm run review -- --model ep-xxxx` 可透传额外参数（`--` 之后）。

> 项目内安装同样会把 `review-pi` 和它的依赖（含内核四包）装进 `node_modules`；`review-pi` 在 `node_modules/.bin/` 下有 shim。

### 2.3 方式 C：私有 registry

现在要解析的是**两个 scope**：`@baize`（产品包）+ `@earendil-works`（上游内核四包）。内网 registry 需要两者都能解析——要么代理这两个 scope，要么把默认 registry 指到内网代理。客户端 `.npmrc` 示例：

```ini
# 上游内核四包（npm 上真实存在，内网需代理该 scope 或缓存 tarball）
@earendil-works:registry=https://npm.example.com/repository/npm-proxy/
# 产品包（@baize scope）
@baize:registry=https://npm.example.com/repository/npm/
registry=https://npm.example.com/repository/npm/
//npm.example.com/repository/npm/:_authToken=${NPM_TOKEN}
```

然后：

```bash
npm i -g @baize/review-pi
```

**产品包改名过**（发行前调整过包名）时，把上面的 `@baize/review-pi` 换成实际名。安装命令以实际包名为准，不要照抄本文的占位名。

常见失败：

| 现象 | 原因 | 处置 |
|---|---|---|
| `404 Not Found - GET .../@baize%2freview-pi` | 产品包没发，或 `@baize` registry 路径不对 | 确认 `npm view @baize/review-pi version --registry ...` 能查到 |
| `404 .../@earendil-works%2fpi-ai` | 上游 scope 没代理 | 补 `@earendil-works:registry=...`，或让默认 registry 走代理 |
| `E401` / `ENEEDAUTH` | token 缺失或过期 | 重新生成 token，写进 `.npmrc`（不要提交到仓库） |
| `ETARGET` / 版本找不到 | 代理源没缓存该版本 | 内核四包必须四包同版本成套（当前 `0.85.1`）；缓存/代理缺版本时按 ADR-0035 判定序换版本并回写 ADR |

### 2.4 方式 D：从 tarball 安装（未发布 / 内网分发）

适用：产品包还没发到 registry，或目标机器只能拷文件过去。前提是手上已有 `@baize/review-pi` 的 `.tgz`（自己打见 §2.7；别人给的先按 §2.7.3 核对文件名与版本）。

只有一个 tarball：

```text
baize-review-pi-0.5.0.tgz
```

内核四包**不在这里面**：它们是普通 npm 依赖，仍由 npm 按 `dependencies` 从 registry 解析（内网见 §2.3）。

```powershell
cd <tarball 所在目录>
npm i -g .\baize-review-pi-0.5.0.tgz
```

```bash
cd <tarball 所在目录>
npm i -g ./baize-review-pi-0.5.0.tgz
```

注意：

- **必须带 `./` 或 `.\`**：裸写 `baize-review-pi-0.5.0.tgz` 会被当成包名去 registry 找，报 404。路径带空格时整段加引号。
- 机器上已装过 registry 版同名包时，`npm i -g <tarball>` 直接覆盖，版本号相同也覆盖，不会提示「已是最新」。
- tarball 里的 `workspace:*` 已被改写成真实版本号；**内核四包与第三方依赖**（`@earendil-works/*`、`@vscode/ripgrep`、`web-tree-sitter`、`tree-sitter-java`、`tree-sitter-typescript`、`tree-sitter-python`、`tree-sitter-go`、`tree-sitter-cpp`、`jsonc-parser`）仍要从 registry 解析，所以**不是完全离线安装**。纯离线的安装布局验证走仓内的 `pnpm verify:pack`（§2.7.4）。
- 装完按 §2.5 五步验证，别直接跳到 `smoke`。

### 2.5 安装后验证（五步）

**第 1 步：命令可见**

```powershell
Get-Command review-pi
```

```bash
command -v review-pi
```

**第 2 步：入口能跑**

```bash
review-pi
```

看到 usage、退出码 1，即 bin → dist → main 这条链是通的。

**第 3 步：配置子命令能跑**

```bash
review-pi config show
```

- 没有配置文件时输出 `（not found — 全缺省；review/smoke 会因缺 reviewer.apiKey 中止）`，退出码 **0**；
- 有配置文件时逐键打印生效值与来源 `(file|default)`，`reviewer.apiKey` 只显示 `set` / `missing`。

**第 4 步：`export` 子命令可用**

```bash
review-pi export
```

没有索引时应当输出一行人话（`未找到 session 索引 …/.review-pi-session.json（先在本目录跑一次 review，或用 --taskId <id> 指定任务）`）并退出码 **1**——这是**预期结果**，说明子命令已在安装包里、参数解析也通了。`export` 不需要配置与 key（ADR-0036）。

**第 5 步：确认版本与安装位置**

```bash
npm ls -g @baize/review-pi --depth=0
npm root -g
```

Windows 默认包目录：`%APPDATA%\npm\node_modules\@baize\review-pi`；POSIX：`$(npm prefix -g)/lib/node_modules/@baize/review-pi`。包内应能看到 `bin/`、`dist/`、`presentation/`、`THIRD-PARTY-NOTICES.md`。

### 2.6 升级与卸载

```bash
# 升级到最新
npm i -g @baize/review-pi@latest

# 指定版本
npm i -g @baize/review-pi@0.5.0

# 卸载（会连带移除不再被需要的依赖，包括内核四包）
npm rm -g @baize/review-pi
```

升级不会动你的 `~/.PiAgent/PiAgent.jsonc`。卸载也不会删它——里面可能还有 key，需要时手工删除。

### 2.7 自己打包（从源码产出 tarball）

> **面向谁**：要自己产出/分发 tarball 的人（仓主、内网分发者、要在离线机器上部署的人）。只装包的人读完 §2.4 就可以跳到 §3。
>
> 结论先说：`pnpm build:dist` → `pnpm pack:packages` → `pnpm verify:pack`，三步各自独立，**pack 不会替你构建**。

#### 2.7.1 前置：Node、pnpm、依赖、构建

```bash
git clone <repo-url> && cd ReviewAgent-pi
node -v      # 必须 >= 22.19.0（engines 硬要求）
pnpm -v      # 仓库用 pnpm workspace，版本以 package.json 的 packageManager 为准
pnpm install # 打包和 verify 都依赖仓内已装的第三方依赖
```

打包前必须有 `dist` 制品：

```bash
pnpm install
pnpm build:dist
```

`build:dist` 只有一段：`pnpm build:presentation`，它先 `pnpm --filter @baize/review-pi build`（CLI 的 `dist/`），再 `tsc -p tsconfig.presentation.json`（呈现层产物先落 `.tmp-gen/presentation/`），最后 `scripts/copy-presentation.mjs` 复制到 `packages/review-pi/presentation/`（`presentation.engine = "builtin"` 从这里取）。

**为什么 pack 不隐式构建**：`prepack` 只**断言**产物在位——`dist/cli/main.js`、`dist/index.js`、`bin/review-pi.js`、`bin/lib/cli-runtime.js`、`presentation/` 的四个文件（`engine-zh.js` / `terminology.js` / `tips.js` / `translate-projection.js`）、以及履约文本 `THIRD-PARTY-NOTICES.md`。缺一项就打印「发布物不完整（N 项缺席）——先跑 pnpm build:dist」并 exit 1。这样打包是确定性且离线的：产物由构建显式产出，打包阶段不会因为环境不同悄悄编译出不同内容。

确认构建到位（可选）：

```powershell
dir packages\review-pi\presentation
```

```bash
ls packages/review-pi/presentation
```

应看到上列四个 `.js`；`dist/cli/main.js` 与 `bin/review-pi.js` 也应在。

#### 2.7.2 打包：`pnpm pack:packages`

```bash
pnpm pack:packages
```

`scripts/pack-packages.mjs` 做四件事：

1. **先清空** `.artifacts/tarballs/`（`rm -rf` 后重建）——每次都是干净目录，不要往里手工塞旧包，它们会被删掉；
2. 对唯一发行包跑 `pnpm pack --pack-destination .artifacts/tarballs`（`packages/review-pi`）；
3. 失败就 `pack: N 个包打包失败` 并 **exit 1**；
4. 成功时打印 tarball 数量、目录与大小。

成功输出末尾形如（本次实测）：

```text
review-pi prepack: 发布物在位（dist / bin / presentation / 许可证履约）

pack: 1 个 tarball -> .artifacts/tarballs
  baize-review-pi-0.5.0.tgz  493.6 KiB
```

产物内容要点：

| tarball | 大小 | 内容要点 |
|---|---|---|
| `baize-review-pi-0.5.0.tgz` | 约 494 KiB | `bin/` + `dist/` + `presentation/` + `THIRD-PARTY-NOTICES.md` |

内核四包**不在 tarball 里**：它们随 `npm i` 从 registry 拉取（ADR-0035）。`.artifacts/` 已在 `.gitignore` 里：产物不进版本库，也不需要提交。

#### 2.7.3 检查 tarball 内容（装之前先看）

`tar` 用系统自带的（Windows 10+ 内置 bsdtar，PowerShell 里直接 `tar`；Git Bash 的 GNU tar 也行）。

```powershell
# 列出全部条目
tar -tzf .artifacts/tarballs/baize-review-pi-0.5.0.tgz

# 只看顶层
tar -tzf .artifacts/tarballs/baize-review-pi-0.5.0.tgz | Select-String "^package/[^/]+/?$"

# 不落盘直接看包清单
tar -xzOf .artifacts/tarballs/baize-review-pi-0.5.0.tgz package/package.json
```

```bash
tar -tzf .artifacts/tarballs/baize-review-pi-0.5.0.tgz
tar -tzf .artifacts/tarballs/baize-review-pi-0.5.0.tgz | grep -E '^package/[^/]+/?$'
tar -xzOf .artifacts/tarballs/baize-review-pi-0.5.0.tgz package/package.json
```

条目都以 `package/` 开头（npm/pnpm 的固定布局）。三个必看点：

1. **没有 `package/src/**/*.ts`**：源码不随包发出。`files` 是白名单，`exports.source` 条件只在仓内（vitest / typecheck）生效，安装方走 `exports.default` 的 `dist/*.js`；
2. **依赖里没有 `workspace:*`**：`package/package.json` 应看到 `"@earendil-works/pi-ai": "0.85.1"` 这类**精确版本**（不带 `^`）。看到 `workspace:*` 说明是用 `npm pack` 而非 `pnpm pack` 打的；看到 `^0.85.1` 说明锁版纪律被放宽了（ADR-0035 决策 1）；
3. **`review-pi` 必须有四样**：`package/bin/review-pi.js`、`package/dist/cli/main.js`、`package/presentation/engine-zh.js`、`package/THIRD-PARTY-NOTICES.md`。

#### 2.7.4 安装布局验证：`pnpm verify:pack`

```bash
pnpm verify:pack
```

这是**不发网络请求**的安装面冒烟：不联网、不发布、不写 registry、不碰全局 `node_modules`。做法是把 `.artifacts/tarballs/` 的那个 tarball 解到 `.artifacts/verify/app/node_modules/`（模拟真实安装布局），再把仓内 `packages/review-pi/node_modules` 里已装好的依赖（含内核四包）按包 junction 过去（**只借依赖图，不借源码**），然后逐项断言：

| # | 断言 | 红了说明 |
|---|---|---|
| 1 | 内容面：tarball 恰为 1 个、包名在发行清单里、`src` 下没有源码文件、必需文件齐全 | `files` 配错 / 打包漏文件 / 混进源码 / 混进了别的包 |
| 2 | `review-pi`（无子命令）打印含 `missing command` 的 usage | `bin` 的腿表在安装布局下定位不到 `dist` 或内核依赖 |
| 3 | `config init` 能写、`config show --json` 出配置快照（`version: 1`、`limits.boundary.maxFiles` 是数字） | 配置面引用了仓内路径 |
| 4 | `presentation.engine = "builtin"` 解析到包内 `presentation/engine-zh.js` | 呈现层制品没进 tarball |
| 5 | `tree-sitter-java`（wasm）能 parse、ripgrep 能列文件 | 原生/资产类依赖在安装布局下拿不到 |

全绿时尾部输出：

```text
verify-pack: 全绿（单包发行面可用）
```

它还会在 `.artifacts/verify/INSTALLED.md` 留一份安装面清单（包名 + 版本 + 临时目录），排障时先看这个。每次运行都会先 `rm -rf` 整个 `.artifacts/verify/`，可以随时删。

注意：

- 需要系统 `tar`，缺了会报 `verify-pack: 无法列出 tarball（需要系统 tar）`；
- 借用的是**本仓已安装**的依赖，所以先 `pnpm install`；仓里没装 `@vscode/ripgrep` 时第 5 条会红；
- 「不联网」的准确含义：脚本自身不发网络请求；首次 `pnpm install` 仍需网络（ADR-0035 的负项之一）；
- 它不是发布门（发布必须由人确认 registry），只是「打出来的包到底能不能用」的本地门。

#### 2.7.5 把 tarball 装到机器上

完整命令、两种 shell 写法与五步验证见 §2.4 与 §2.5，这里只给最短版：

```powershell
cd .artifacts\tarballs
npm i -g .\baize-review-pi-0.5.0.tgz
review-pi   # 打印 usage 且 exit 1 = 装通
```

```bash

```

内网分发时把 `baize-review-pi-0.5.0.tgz` 拷走即可；目标机器上仍需能访问 registry 拉内核四包与第三方依赖（§2.4 最后一条）。

#### 2.7.6 打包 ≠ 发布

- `pnpm pack:packages`：只往本地产出文件，**不联网**；
- `pnpm publish:packages`：= `pnpm build:dist && pnpm -r publish`，**会真的往 registry 推**。需要：`.npmrc` 指向目标 registry（§2.3）、有写权限的 token、`review-pi` 的版本号在 registry 上不存在（npm 不允许覆盖已发布版本）；
- 只想把 tarball 交给别人（U 盘 / 内网制品库）时，**不要**跑 `publish:packages`。

发布前检查单：

- [ ] `pnpm build:dist` 是本次新跑的（不是昨天的 `dist/`）；
- [ ] `pnpm pack:packages` exit 0，`baize-review-pi-0.5.0.tgz` 在；
- [ ] `pnpm verify:pack` 全绿；
- [ ] `git status` 干净（`prepack` 复制的 `packages/review-pi/THIRD-PARTY-NOTICES.md` 是 gitignored，不算脏）；
- [ ] 已确认 registry 与凭据，再执行 `pnpm publish:packages`。

#### 2.7.7 打包失败对照

| 现象 | 原因 | 处置 |
|---|---|---|
| `review-pi prepack: 发布物不完整（N 项缺席）——先跑 pnpm build:dist` | 没构建，或只跑了 `pnpm --filter @baize/review-pi build` | 跑完整 `pnpm build:dist`，再打包 |
| `ERR_PNPM_BIN_CRLF` | `bin/` 行尾被改成 CRLF（编辑器 / git autocrlf） | `git checkout -- packages/review-pi/bin` 恢复；`.gitattributes` 已把 `packages/review-pi/bin/**` 固定为 LF，不要手工改行尾 |
| tarball 的 `package.json` 里依赖还是 `workspace:*` | 用了 `npm pack` 而非 `pnpm pack` | 只用 `pnpm pack:packages`（内部即 `pnpm pack`） |
| `pack: N 个包打包失败` | `pnpm pack` 非零退出（常见是 `prepack` 断言失败或 `bin` 行尾被改） | 看上面那段输出，先修构建/行尾 |
| `verify-pack: 没有 tarball —— 先跑 pnpm pack:packages` | `.artifacts/` 被清过 | 重新打包 |
| `verify-pack: 单包发行只应有 1 个 tarball` | `.artifacts/tarballs/` 里还有旧的多包产物 | 删掉旧 tarball 重新 `pack:packages`（脚本会先清空目录） |
| `verify-pack: ... 里混进了源码` | 包的 `files` 白名单被改宽 | 改回白名单，不要把 `src` 加进去 |
| `verify-pack: 无法列出 tarball（需要系统 tar）` | 系统没有 `tar` | 装 tar（Windows 用内置 bsdtar 即可） |
| 装完 `@baize/review-pi` 报 `Cannot find module '@earendil-works/pi-ai'` | 内核依赖没装齐（离线/registry 解析失败） | 确认 `@earendil-works` scope 可解析（§2.3），再 `npm i -g @baize/review-pi`/重装 tarball |

## 3. 配置

配置是**唯一**的凭据与运行参数来源（ADR-0025）。环境变量层已彻底移除：`REVIEWER_*` / `DEEPSEEK_*` / `REVIEW_PI_*` 不再被读取，`--env` 是确定性错误。

### 3.1 文件位置与优先级

| 场景 | 路径 |
|---|---|
| Windows 默认 | `%USERPROFILE%\.PiAgent\PiAgent.jsonc` |
| macOS / Linux 默认 | `$HOME/.PiAgent/PiAgent.jsonc` |
| 显式指定 | `--config <path>`（`review` / `smoke` / `config` 全子命令通用） |

规则：

1. `--config` 优先；相对路径按**进程 cwd** 解析。
2. 没给 `--config` 就读用户主目录（Windows 读 `USERPROFILE`，POSIX 读 `HOME`）。
3. **WSL 读的是 Linux 的 `$HOME`**，不是 Windows 的 `C:\Users\...`。两边要各配一份，或者统一用 `--config /mnt/c/Users/...`。
4. 配置文件**不存在**不是错误：按内置缺省运行，但 review / smoke 会因为没有 `reviewer.apiKey` 而 fail fast。
5. 配置在进程启动时**读一次**，运行中改文件不影响本次 run。

### 3.2 生成配置文件

```bash
review-pi config init
```

输出：

```text
review-pi: 已写入配置文件 /home/you/.PiAgent/PiAgent.jsonc
```

行为：

- 目录自动创建；POSIX 下目录 `0700`、文件 `0600`（Windows 上 mode 只影响只读位）；
- 文件已存在时**拒绝覆盖**：`配置文件已存在（...）——加 --force 覆盖`，退出码 1；
- `--force` 会整文件覆盖，**包括你已填的 key**。更推荐用编辑器改，而不是 `--force`；
- 写到自定义路径：`review-pi config init --config /path/to/PiAgent.jsonc`。

生成的内容是完整模板（所有键 + 逐项中文注释 + 缺省值），与仓库根 [`PiAgent.example.jsonc`](../PiAgent.example.jsonc) 同源。顶层按 `reviewer` / `model` / `presentation` / `codeintel` / `mcp` / `limits` 分区；`limits` 下每个分组（轮次、超时、重试、并发、置信度过滤、边界、分片、归档、文本截断）都有中文说明，`mcp` 示例块也逐键注释了传输、握手、批量与背压。

### 3.3 最小可跑配置

手工创建也可以。文件**一旦存在就必须有 `version: 1`**（缺 `version` 会 fail fast）：

```jsonc
{
  // 配置版本：当前只支持 1，不匹配即 fail fast。
  "version": 1,
  "reviewer": {
    // 模型网关密钥（必需）。
    "apiKey": "sk-..."
  }
}
```

其余键全部走内置缺省：

- `reviewer.baseUrl` = `https://api.deepseek.com`（官方直连）
- `reviewer.maxOutputTokens` = `null`（自动判档）
- `model.default` = `deepseek-v4-flash`
- `model.presentation` = `null`（跟随检视模型）
- `presentation.engine` = `null`（手写最小文件、整段省略即不配置）；`config init` 生成的模板会显式写 `"builtin"`。**ADR-0065 后该键不再驱动控制台翻译**：stdout 恒英文，中文只由片级语义生成产 `reviews_tips_zh.json`
- `codeintel.languages` = `"auto"`（跟随当前版本已实现的代码智能解析器，当前语言 id 为 `java` / `typescript` / `python` / `go` / `cpp`）
- `limits` = 内置缺省（见 §3.5.5）

### 3.4 推荐配置（两个场景）

**场景 A：官方直连**

```jsonc
{
  // 配置版本：当前只支持 1。
  "version": 1,
  "reviewer": {
    // 模型网关密钥（必需）。
    "apiKey": "sk-...",
    // 官方直连基址。
    "baseUrl": "https://api.deepseek.com",
    // 单次请求输出上限：null = 自动（官方直连不发 max_tokens）。
    "maxOutputTokens": null
  },
  "model": {
    // 默认检视模型（--model 可覆盖）。
    "default": "deepseek-v4-flash",
    // 报文 / 总结 / 语义生成模型：null = 跟随本次检视模型。
    "presentation": null
  },
  "presentation": {
    // legacy 兼容键：ADR-0065 后不再驱动控制台翻译（stdout 恒英文）。
    "engine": "builtin"
  }
}
```

**场景 B：OpenAI 兼容网关 / 方舟接入点**

```jsonc
{
  // 配置版本：当前只支持 1。
  "version": 1,
  "reviewer": {
    // 网关密钥（必需）。
    "apiKey": "gw-...",
    // OpenAI 兼容网关基址：路径前缀（通常 /v1）必须自己写全。
    "baseUrl": "https://gateway.example.com/v1",
    // 显式输出预算：网关档 32768 与 null 等效。
    "maxOutputTokens": 32768
  },
  "model": {
    // 方舟接入点或网关别名，自由 id 透传。
    "default": "ep-20261031-xxxxxxxx",
    // 报文 / 总结 / 语义生成模型：null = 跟随本次检视模型。
    "presentation": null
  },
  "presentation": {
    // legacy 兼容键（ADR-0065）：不再驱动控制台翻译。
    "engine": "builtin"
  },
  // 代码智能语言：auto = 跟随已实现的解析器（当前 java / typescript / python / go / cpp）；也可写 ["java"]。
  "codeintel": { "languages": "auto" }
}
```

要点：

- **`baseUrl` 必须自带网关要求的路径前缀**（通常是 `/v1`）。OpenAI SDK 只会追加 `/chat/completions`，不会替你补 `/v1`；
- `maxOutputTokens` 显式写 `32768` 与写 `null` 在网关档效果相同（自动判档就是 32768）；只有在网关上限更小、或你想压成本时才需要调小；
- 目录外的模型 id（网关别名、`ep-xxx`）也能直接跑，但内置目录没有它的画像，`contextWindow` / `maxTokens` / `cost` 会借用 `deepseek-v4-flash`（见 §3.5.2）；成本数字因此可能失真；
- `presentation.engine` 是 legacy 兼容键，ADR-0065 后**不再影响控制台**；中文按行建议恒由片级语义生成产出，与业务上报开关无关（§3.5.3）。

### 3.5 字段逐项说明

#### 3.5.1 `reviewer`（检视链接入点）

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `reviewer.apiKey` | string | 无（`null`） | **必填**。只写在这个文件里；`config show` 与审计只报 `set|missing`（stdout 不输出配置），绝不回显值或长度。缺失时 review / smoke 在触碰文件系统前 fail fast。 |
| `reviewer.baseUrl` | string | `https://api.deepseek.com` | OpenAI 兼容 base URL。尾斜杠会被归一；官方/网关判档对 **scheme + host 大小写不敏感**，但 **path 逐字符有意义**（`/v1` 不是同一端点）——所以 `HTTPS://API.DEEPSEEK.COM/` 仍算官方直连，而 `https://api.deepseek.com/v1` 算网关。网关路径（如 `/v1`）要自己写全。 |
| `reviewer.maxOutputTokens` | 正整数或 `null` | `null` | 输出预算。`null` = 自动：**官方直连不发 `max_tokens`**；其他 baseUrl（网关）发 `32768`。显式数字则无论官方/网关都发送该值。 |
| `reviewer.stripModelPrefix` | boolean | `false` | 模型 id 前缀剥离。`true` 时**所有**发往网关的模型 id（`--model` / `model.default` / `model.presentation`，含 smoke 探针）剥掉**最后一个 `/` 前的所有**：`pan/deeseek` → `deeseek`、`vendor/group/model-x` → `model-x`。给「平台侧传 `厂商/模型` 形态、网关只注册裸名」的部署用。**缺省 false = 原样直发**——OpenRouter 等网关的合法 id 本身就带斜杠，不能无条件剥。生效值全面一致：参数回显 / 审计 / wire 记的都是剥后的 id；开关本身进审计 config 快照。 |

**`maxOutputTokens` 判档细节**：

- 官方直连不发 `max_tokens`，是为了对齐历史审计 wireBody 字节；不要为了「显式一点」而写 `32768`，那会改变请求体；
- 网关不显式给预算时，很多网关默认 2048，会把思维链吃光并静默截断——所以网关档默认发 32768；
- 网关上限较小（例如只允许 8192）时写 `8192`，否则会被网关以 `400` 拒绝；
- 出现 `truncationReasons` 含 `MODEL_MAX_TOKENS_REACHED` 时，优先调大该值（官方直连需要显式写才会下发）。

#### 3.5.2 `model`（模型选择）

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `model.default` | 非空 string | `deepseek-v4-flash` | 不传 `--model` 时使用。自由 id 透传，不做别名映射。 |
| `model.presentation` | 非空 string 或 `null` | `null` | **报文 / 总结 / 片级语义生成**使用的模型。`null` = 跟随本次检视模型（三级链：`model.presentation` → `--model` → `model.default`）。 |

`--model <id>` 优先于 `model.default`；`model.presentation` 只影响报文 / 总结 / 语义生成，不影响检视模型。**模型 id 不做别名映射、不拆 `厂商/模型`**——斜杠只是普通字符，原样进请求的 `model` 字段；网关只认裸名时开 `reviewer.stripModelPrefix`（见 §3.5.1）。

目录外 id 的画像回退：id 不在内置目录（`deepseek-v4-flash` / `deepseek-v4-flash-vision-exp` / `deepseek-v4-pro`）时，使用 `deepseek-v4-flash` 的画像作模板，只替换 id。因此这类 id 的上下文窗口与单价都按 flash 计算，成本数字仅供参考；`--model` 的 id 本身不做别名映射，网关要能直接识别。

#### 3.5.3 `presentation`（legacy 兼容键）

| 值 | 含义 |
|---|---|
| `"builtin"` | 指向包内呈现引擎（安装形态下是 `<包目录>/presentation/engine-zh.js`）。**`config init` 生成的默认值** |
| `null` | 不配置引擎（整段省略 = 同此） |
| 路径 | 模块路径。**相对路径按配置文件所在目录解析**，不是进程 cwd（ADR-0026） |

- **ADR-0065 起该键不再影响运行结果**：CLI 不调用呈现投影，stdout 恒英文、没有 `presentation` 键；中文交付物（`reviews_tips_zh.json` / MCP 报文）由片级语义生成产出，与这个键无关。
- 配置校验、路径解析与 `.env` 迁移行为保留（写错路径也不会让 run 失败，只是不再有使用者）。
- 引擎模块（`src/presentation/*` 与 `cli/presentation-projection.ts`）保留为 legacy，供外部消费方直接调用。
- 中文落盘产物只有一份：`reviews_tips_zh.json`（ADR-0022 / ADR-0065）。`reviews_zh.json` 已停产，旧文件会被主动清除。

#### 3.5.4 `codeintel`（代码智能语言）

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `codeintel.languages` | `"auto"` 或语言 id 数组 | `"auto"` | 符号 / 引用 / 调用链工具扫哪些语言。`"auto"` = 跟随当前版本已实现的解析器（当前：`java` / `typescript` / `python` / `go` / `cpp`），升级后自动扩语言、不用改配置；数组 = 只启用列出的语言（如 `["java"]`）；空数组 = 显式关闭代码智能。未实现的条目**装载期告警并跳过**，不静默。 |

检视本体读 diff，**本来就不限语言**；这个开关只影响 `review.get_symbol` / `review.find_references` / `review.get_call_chain` 的符号级能力。非本语言仓调用这些工具会返回明确的 `no supported source files detected ...` 提示，不再静默 0 命中。

#### 3.5.5 `limits`（轮次、超时、重试、并发、置信度过滤、边界、分片、归档、文本截断）

完整缺省：

```jsonc
{
  "limits": {
    // 检视轮次（ADR-0046）：一轮 = 六阶段完整一遍；最后一轮强制 complete。
    // 轮次上限是成本线而非失败（不产生截断）。范围 1–20。
    "loop": { "maxRounds": 3 },
    // 各阶段超时（毫秒）。
    "timeouts": {
      "skillPassMs": 1200000,            // 单个规则 Skill 会话的总超时。
      "skillBashMs": 120000,             // 规则 Skill 里 bash 工具单次执行超时。
      "ruleSkillExtractMs": 30000,       // 规则包 zip 解压超时。
      "ripgrepMs": 30000,                // ripgrep 单次调用超时。
      "probeHealthMs": 15000,            // smoke 网关健康探针超时。
      "probeModelMs": 120000,            // smoke 模型探针超时。
      "reviewTurnMs": 180000,            // 主检视回合 / 规则 Skill 会话单次请求的建立超时。
      "oneShotMs": 300000,               // 片级报文 / 收尾总结单次请求超时。
      "presentationRequestMs": 90000,    // legacy 呈现引擎单次请求超时（ADR-0065 后 CLI 不再调用）。
      "presentationBufferMs": 30000      // legacy 呈现引擎整批总超时余量。
    },
    // LLM 调用重试（ADR-0051）：次数一律是「总尝试次数（含首次）」，1 = 不重试。
    // Agent 内会话走 pi-ai 的请求建立阶段重试；报文 / 总结 / 内置呈现引擎 / smoke 走本仓统一重试。
    // 流已开始后断开会显式报错，不做整回合重放（避免重复工具副作用与消息状态错乱）。
    "retry": {
      "maxAttempts": 3,                  // 全局缺省；路径级次数未写时继承它。
      "baseDelayMs": 500,                // 指数退避基准（毫秒）。
      "maxDelayMs": 10000,               // 单次退避上限（毫秒）。
      "maxRetryAfterMs": 30000,          // 服务端 Retry-After 上限（毫秒）；0 = 不设上限。
      "reviewTurnAttempts": 3,           // 主检视回合 / 规则 Skill 会话。
      "oneShotAttempts": 3,              // 片级报文 / 收尾总结。
      "presentationAttempts": 3,         // legacy 呈现引擎逐请求（ADR-0065 后 CLI 不再调用）。
      "smokeAttempts": 1                 // smoke 探针；缺省 1 = 不重试。
    },
    // legacy：呈现引擎的 suggestion 并发生成数（ADR-0065 后 CLI 不再调用）。
    "concurrency": { "suggestion": 4 },
    // 中文 tips 置信度过滤（ADR-0052）：confidence < min 的意见不进入
    // reviews_tips_zh.json 与 mrReviewResult.reviewTips；英文 findings / stdout 恒全量。
    // 0–1，缺省 0.5（= 过滤 Low 档）；0 = 不过滤，1 = 只保留满置信。
    "confidence": { "min": 0.5 },
    // 检视意见严重级过滤：severity < min 的意见不进入
    // reviews_tips_zh.json 与 mrReviewResult.reviewTips；英文 findings / stdout 恒全量。
    // 取值 P0–P3，缺省 P3（= 不过滤）；P2 = 只保留 P0/P1/P2，丢弃 P3 建议级。
    "severity": { "min": "P3" },
    // 测试文件是否跳过检视（缺省 true）：检视输入阶段整块剔除。
    "testFiles": { "skip": true },
    // 按 glob 跳过检视（ADR-0069；缺省排除 Markdown / lockfile / fixtures / snapshot）：
    // 命中的文件块在检视输入阶段整块剔除（不进 diff / findings / tips / MCP 意见），
    // 但仍按 ADR-0068 上报空检视意见。空数组 = 不排除任何文件。
    // 匹配仓库相对 POSIX 路径，大小写不敏感；不含 "/" 的 glob 只比文件名（*.md 与 **/*.md 等价）；
    // * / ? 不跨目录，** 跨目录。例：["**/*.md", "docs/**"] 跳过全部 Markdown 与 docs 目录。
    "mrFilter": { "excludeGlobs": ["**/*.md", "**/*.lock", "**/fixtures/**", "**/*.snap"] },
    // 非 diff 区域过滤（缺省开启）：意见必须落在本遍 diff 的变更 hunk 内，
    // 或距 hunk 边界不超过 contextLines 行；文件不在本遍 diff 的直接丢弃。
    "findingScope": { "enabled": true, "contextLines": 10 },
    // MR 边界护栏：超界只告警（domainWarning）不拒检；null = 该维不设界。
    // maxDiffChars 是输入体积门：过滤后超限直接报错（不发模型请求），null = 关闭门禁。
    "boundary": {
      "maxFiles": 10,                    // 变更文件数上限。
      "maxDiffLines": 2000,              // 变更行数上限。
      "maxDiffChars": 1000000            // 过滤后 diff 字符数上限（超限直接报错；约 1.6 万–2.9 万变更行）。
    },
    // 大 MR 分片（ADR-0039）：过滤后的 diff 超过一片预算时，按 diff --git 文件块切开
    // 分别检视（绝不切 hunk），最后把各片 findings 合并去重。
    // 单个文件本身超过 maxShardChars 时，只保留文件头 + 前缀若干个完整 hunk（尾部
    // 整 hunk 丢弃并留痕，ADR-0070），不再报错。
    // 注意：maxShardChars 应小于 maxDiffChars，否则体积门先报错、分片永不触发。
    // 片尺寸按 128K 上下文定（ADR-0071）：单片 12 万字符 ≈ 3.1 万 tokens diff，
    // 叠加工具往返 + 输出的固定增长 ≈ 4.5 万，峰值 ≈ 8 万（实测口径见 ADR-0071）。
    "split": {
      "enabled": true,                   // 是否启用自动分片；false = 超预算仍单遍跑（旧行为，窗口风险自负）。
      "maxShardChars": 120000,           // 单片字符目标（约 1900–3500 变更行；峰值上下文约 8 万 tokens）。
      "maxShards": 12,                   // 片数上限（成本护栏）；1000000/120000 最坏 9 片，12 片留余量。
      "contextSummaryChars": 8000        // 每片附带的「其他文件变更摘要」字符上限（不是证据源）。
    },
    // 规则包 zip 解压前的审计上限。
    "archive": {
      "maxArchiveBytes": 8388608,        // 压缩包体积上限（字节）。
      "maxEntries": 2000,                // 压缩包条目数上限。
      "maxTotalUncompressed": 67108864,  // 解压后总字节上限（防解压炸弹）。
      "maxCompressionRatio": 100         // 压缩比上限（解压后 / 压缩后，100 = 100:1）。
    },
    // 文本截断上限：工具输出、包头部、检索回显、调用链跳数、进度明细；一般不用改。
    "micro": {
      "skillBashOutputChars": 256000,    // 规则 Skill 中 bash 工具的输出字符上限。
      "packageHeadBytes": 8192,          // 读取文件头以提取包名时的最大字节数。
      "queryEchoChars": 120,             // 检索工具回显 query 的字符上限。
      "callChainHops": 2,                // get_call_chain 降级为名字级引用链时的跳数。
      "toolNameChars": 60,               // 未知名工具回显的字符上限。
      "argumentsSummaryChars": 80,       // 进度行里工具入参摘要的字符上限（脱敏）。
      "progressDetailChars": 120         // 进度行里失败 / 结果摘要的字符上限（只取首行）。
    }
  }
}
```

| 组 | 作用 |
|---|---|
| `loop` | 检视轮次（ADR-0046）：`maxRounds` = 一轮六阶段的硬上限（缺省 3，范围 1–20）。**最后一轮强制 complete**：模型判断「还要再审」也不再开新轮，本轮产出即最终结果；轮次耗尽不是失败，不产生截断。 |
| `timeouts` | 各阶段超时（毫秒）。`skillPassMs` 单个规则 Skill 会话；`skillBashMs` 规则包里的 bash 调用；`probeHealthMs` / `probeModelMs` 是 smoke 双探针；`reviewTurnMs` 主检视回合 / 规则 Skill 会话的单次请求**建立**超时；`oneShotMs` 片级报文 / 收尾总结 / 片级语义生成单次请求；`presentationRequestMs` / `presentationBufferMs` 为 legacy 呈现引擎保留（ADR-0065 后 CLI 不再调用）。 |
| `retry` | LLM 调用重试（ADR-0051）。`maxAttempts` 是**总尝试次数（含首次）**；`reviewTurnAttempts` / `oneShotAttempts` / `presentationAttempts` 未写时继承 `maxAttempts`，`smokeAttempts` 缺省固定 `1`。`baseDelayMs` / `maxDelayMs` 只作用于核外一次性调用；`maxRetryAfterMs` 同时约束服务端 `Retry-After` 与 pi-ai 的 `maxRetryDelayMs`。只重试传输失败 / 超时 / 408 / 409 / 429 / 5xx / `x-should-retry: true`；确定性 4xx、配额类 429、非 JSON 输出不重试。`presentationAttempts` 为 legacy 保留，不再被 CLI 使用。 |
| `concurrency.suggestion` | legacy：呈现引擎的 `suggestion` 并发生成数（缺省 4）。ADR-0065 后 CLI 不再调用呈现引擎，此值不再影响运行。 |
| `confidence.min` | 中文 tips 置信度下限（ADR-0052）：`confidence < min` 的意见不进入 `reviews_tips_zh.json` 与 `mrReviewResult.reviewTips`；英文 findings / stdout 恒全量。0–1，缺省 `0.5`（过滤 Low 档）；`0` = 不过滤，`1` = 只保留满置信。丢弃条数与阈值写入审计 / `run.json` 的 `tipsFilter`。 |
| `severity.min` | 中文 tips / MCP 上报的严重级下限：`severity` 低于 `min` 的意见不进入 `reviews_tips_zh.json` 与 `mrReviewResult.reviewTips`；英文 findings / stdout / 审计 findings 恒全量。取值 `P0`–`P3`（大小写不敏感），缺省 `P3`（= 不过滤）；`P2` = 只保留 P0/P1/P2，丢弃 P3 建议级。丢弃条数与阈值写入审计 / `run.json` 的 `severityFilter`。 |
| `testFiles.skip` | 是否跳过检视测试文件（缺省 `true`）：`true` = 检视输入阶段整块剔除测试文件（不产 findings / tips / MCP 上报）；`false` = 与生产代码同等检视。剔除清单写入审计 / `run.json` 的 `mrFilter`（`reason = "test"`）。 |
| `mrFilter.excludeGlobs` | 按 glob 跳过检视（ADR-0069；缺省排除 `**/*.md` / `**/*.lock` / `**/fixtures/**` / `**/*.snap`，ADR-0070；设 `[]` = 不排除）：命中的文件块在检视输入阶段整块剔除，不进 diff / findings / tips / MCP 意见；被跳过的文件仍按 ADR-0068 补一条空 `reviewTips` 的 `mrReviewResult`（不会变成「未检视」）。匹配仓库相对 POSIX 路径、大小写不敏感；不含 `/` 的 glob 只比文件名（`*.md` 与 `**/*.md` 等价），`*` / `?` 不跨目录、`**` 跨目录。剔除清单写入审计 / `run.json` 的 `mrFilter`（`reason = "exclude"`）。 |
| `findingScope.enabled` | 非 diff 区域过滤（ADR-0064，缺省 `true`）：只在候选拦截链保留落在本遍 diff 变更 hunk 内（或距边界不超过 `contextLines` 行）的意见；文件不在本遍 diff 的直接丢弃。影响 findings / tips / MCP / 审计（被拒候选只留 `rejectionCounts.OUT_OF_SCOPE`）；`false` = 同文件远处、甚至未改动文件里的意见也保留。 |
| `findingScope.contextLines` | hunk 前后放宽的行数（缺省 `10`，取值 `0`–`2000`）：`0` = 只保留 hunk 内。仅在 `findingScope.enabled = true` 时生效。 |
| `boundary` | MR 边界护栏与输入体积门。`maxFiles` / `maxDiffLines` 任一维设 `null` = 该维不设界（两维都 `null` = 护栏停用，不度量、不告警）；超界只**告警**并加 `domainWarning`，不截断、不改退出码。`maxDiffChars` 是过滤后的字符数门（缺省 `1000000`）：超限**直接报错**（不发模型请求），`null` = 关闭门禁。 |
| `split` | 大 MR 分片（ADR-0039）。缺省 `enabled=true` / `maxShardChars=120000` / `maxShards=12`（ADR-0071，按 128K 上下文实测标定：峰值上下文约 8 万 tokens）。`enabled=false` = 超预算仍单遍跑（旧行为）；`maxShardChars` 是**单片**字符目标（不是硬失败线），`maxShards` 是片数上限（成本护栏），`contextSummaryChars` 限每片附带的「其他文件变更摘要」。单块超预算改为整 hunk 截取（ADR-0070），片数超上限仍是预检期报错，不发模型请求。 |
| `archive` | 规则包解压前的审计上限：压缩包字节、条目数、解压后总字节、压缩比。 |
| `micro` | 文本截断（工具输出、包头部、检索回显、调用链跳数、工具名/摘要、进度明细）。一般不用改。 |

### 3.7 从旧 `.env.local` 迁移（一次性）

```bash
review-pi config init --from-env .env.local
```

- `--from-env` 只在 `config init` 有效；路径按 **cwd** 解析；
- 读文件，但**不写 `process.env`**，不改变「env 层已关闭」的语义；
- 可迁移的源键只有七个：

| 源键 | 落到 |
|---|---|
| `REVIEWER_API_KEY` / `DEEPSEEK_API_KEY` | `reviewer.apiKey` |
| `REVIEWER_URL` / `DEEPSEEK_URL` | `reviewer.baseUrl`（必须以 `http(s)://` 开头，尾斜杠会去掉） |
| `REVIEWER_MAX_TOKENS` | `reviewer.maxOutputTokens`（必须是正整数） |
| `REVIEW_PI_PRESENTATION_ENGINE` | `presentation.engine`（相对路径按**迁移时的 cwd** 解析成绝对路径再写入） |
| `REVIEW_PI_PRESENTATION_MODEL` | `model.presentation` |

- 其余键会被丢弃，并在 stdout 列出 `已丢弃未识别键：...`；
- 源文件有无法解析的行时逐行提示并跳过；
- **`REVIEW_PI_PRESENTATION_ENGINE=builtin` 也会被当成相对路径**（迁移时统一 `resolve(cwd, value)`），不会保留哨兵。要内置引擎，迁移后手工把 `presentation.engine` 改回 `"builtin"`；
- 目标配置已存在时仍受 `--force` 约束；
- 迁移完成后建议删除 `.env.local`。它不会再被读取；放在 cwd 里只会让每次 review / smoke 多打一行提示：

```text
review-pi: 已不再读取 .env.local（本版配置见 --config 或 ~/.PiAgent/PiAgent.jsonc）；迁移：review-pi config init --from-env .env.local
```

> 这行提示只 stat 当前目录的 `.env.local`，不读内容。看到它不代表配置被使用。

### 3.8 多份配置（项目 / 环境切换）

```bash
review-pi review --config ./ci/PiAgent.ci.json --repo ... --mr-diff ... --taskId ... --tasks-dir ...
review-pi smoke  --config ./ci/PiAgent.ci.json
review-pi config show --config ./ci/PiAgent.ci.json
```

- `--config` 相对路径按 cwd；
- 每份配置独立 `digest`，审计里能区分；
- 不要把带 key 的配置提交到仓库；CI 里用 secret 挂载到临时文件，或由流水线在 job 内生成。

### 3.9 配置安全

- **秘密只进配置文件**：没有 `--api-key` 之类的旗标，避免 key 出现在 shell history / 进程列表 / CI 日志；
- POSIX 权限建议 `0600`；文件宽于 `0600` 只警告，不影响运行，但同机其他用户可能读到；
- 目录 `0700` 的意义是「连这里有个配置文件都不让其他用户看到」；
- `config show`、审计、stdout、错误信息都不会回显 key 值或长度；
- 审计里的 `config` 是**脱敏快照**（`secret.reviewer.apiKey = set|missing`），`digest` 不是 key 的哈希，不能反推。

### 3.10 MCP 上报（可选）

把检视过程与结果外发给已有的 MCP 服务（HTTP + JSON-RPC；ADR-0037 / ADR-0045）。整块不配置 = 零建连、零请求、退出码与产物字节都不变。

**最小默认形态（只要四个业务 tool）**——`mcp.report.tool` 可选，缺席 = 事件通道整体关闭：

```jsonc
"mcp": {
  "servers": {
    "myserver": {
      // 传输形态："http" = Streamable HTTP（单端点 POST，推荐，url 填消息端点）；
      // "http-sse" = 老式 HTTP+SSE（GET 长连接收 endpoint 事件，响应从 SSE 流回来，
      //              url 填 SSE 端点，如 …/sse）
      "transport": "http",
      // 握手策略（缺省 "auto"）：先试 initialize，服务端不认就降级为无状态直调
      // （每次 tools/call 独立 POST，与 Postman 单发同形）；"required" = 握手失败即
      // 上报不可用；"off" = 从不握手。
      "handshake": "auto",
      "url": "https://你的-mcp-server/mcp",
      "headers": { "Authorization": "Bearer <token>" },   // 可选
      "timeoutMs": 60000                                     // 可选，缺省 60s（每条 MCP 请求上界）
    }
  },
  "report": { "server": "myserver" }
}
```

**服务端只实现 `tools/call`（不认 `initialize`）**：不用改配置——缺省 `handshake: "auto"` 会在握手失败时自动降级为**无状态直调**，每个 `tools/call` 都是独立 POST（与 Postman 单发完全同形），stderr 只多一行说明。要严格 MCP 语义（握手失败即放弃上报）用 `"handshake": "required"`；要从头就不发 `initialize` 用 `"handshake": "off"`。注意：连接层失败（DNS / 拒绝连接 / 超时）与协议版本不匹配**不降级**，会如实报错。

**老式服务端（`"transport": "http-sse"`）**：给只实现了 2024-11-05 老传输（`GET /sse` 长连接 + 消息 POST 到 `endpoint` 事件给的路径、响应从流回来）的服务端用——Java/Spring 系旧版常见。`url` 填 **SSE 端点**（如 `http://127.0.0.1:8003/…/sse`），消息端点由服务端在流上告知，客户端自动解析；对上层（四个业务 tool、事件通道）完全透明。

这一个配置就会按序调用四个业务 tool（`task` 缺省 `true`）：

- `startTask(taskId)`：开跑前（建连握手后、读 diff 之前）；
- `mrReviewResult(taskId, filePath, reviewTips)`：每片检视意见定型后**按文件**上报（大 diff 分片时逐片流式）。**`saveReviewSummary` 之前，diff 里的每个变更文件都必须有一条上报**（ADR-0061）：有意见的带 tips，没有意见的也发一条 `reviewTips: []`（平台据此知道该文件已检视过、无问题）；有 finding 但片级报文生成失败 / tips 全部被校验跳过时**同样补空列表**（覆盖率优先，失败原因留在 stderr 与未覆盖登记里）。整个 diff 解析不出任何文件时只打一行 stderr、不发无路径的空调用。**被预过滤剔除的文件同样要登记**（ADR-0068）：它们也是变更文件，收尾按「过滤前变更文件全集 − 已上报」补报一条 `reviewTips: []`（stderr 一行 `MCP mrReviewResult 已补报 N 个变更文件 / 0 条意见`），因此全 test / 全 lockfile 的 MR 也不会出现「零 `mrReviewResult` + 总结说没问题」。报文里**结构字段由代码确定性组装**（文件路径规范化、源码行取自 `--repo` 真源、行号、严重级四档映射、规则 id），模型只生成四个语义字段（`category` 七枚举归一 / `subcategory` / `review` / `suggestion`）——枚举外或空值逐条跳过并留痕，脏数据不出进程；
- `saveReviewSummary(taskId, markdownContent)`：中文检视意见落盘后上报 Markdown 总结报告（有意见 = 模型生成、失败降级模板；**零意见 = 固定文案 `# 检视总结\n\n本次检视未发现缺陷。`，不调用模型**）；
- `endTask(taskId)`：收尾（`startTask` 成功发出过才补发）。

调用顺序恒为 `startTask` → 全部 `mrReviewResult` → `saveReviewSummary` → `endTask`，且每个调用都等上一个结束才发。为应对服务端异步处理（`tools/call` 返回 2xx 只代表收到/入队）导致前端回调顺序错乱，客户端在两处各加**固定 5 秒沉降**（ADR-0053）：最后一条 `mrReviewResult` 之后、`saveReviewSummary` 之前；`saveReviewSummary` 结束后、`endTask` 之前。因此启用业务上报的运行固定多约 10 秒，stderr 各有 `MCP 固定等待 5000ms（…）` 一行。业务关闭、建连失败、或检视在总结前失败时不等待。

**可选的事件通道**（要进度事件才配 `tool`）：

```jsonc
"report": {
  "server": "myserver",
  "tool": "report_events",     // 给了才批量发进度事件（批量塞进该 tool 的 events 数组）
  "include": ["run.start", "run.end", "phase", "request.end"],  // 缺省即这四类
  "batch": { "maxEvents": 50, "maxDelayMs": 2000 },
  "queue": { "maxEvents": 1000 },
  "flushTimeoutMs": 5000,
  "findings": "summary"        // run.end 是否带 findings 摘要（条数+严重度分布）
}
```

- 事件通道的字段白名单纪律：finding 正文、工具入参、本地绝对路径、密钥**永不出进程**；`task: false` 可单独关业务 tool（只留事件）；`include: []` 可单独关事件（此时 `tool` 不会被调）。
- **旁路纪律**：业务调用共 3 次尝试（仅传输 / 超时 / HTTP 5xx 类瞬时失败重试，退避 100 / 400 ms）、失败只打一行 stderr（`review-pi: MCP startTask 失败（…），继续检视`）、**绝不改变退出码**；`server-error` / `isError: true` / 4xx 等确定性失败不重试。建连/握手失败降级为一行 stderr，检视照常。
- `taskId` 同值直传 `--taskId`（本地任务目录名与远端任务标识同源）。
- **调用留痕**：业务调用开启时，每次 run 在 `<tasks 根>/<taskId>/runs/mcp.json` 记录四个 tool 的输入 / 输出 / 调用时间（含重试总耗时与服务端回包正文；ADR-0054）。写失败只打一行 stderr、不改退出码；纯本地 run / 只开事件通道时不产这个文件。
- **统一 tips（效率关键，ADR-0065）**：`mrReviewResult` 与 `reviews_tips_zh.json`（及 cwd 副本 `review-result.json`）始终**复用同一份片级语义生成**——中文只生成一遍，与是否配置呈现引擎无关；每条 tip 在原 10 键之上**只增不删**地加 `id`（聚合 finding id）与 `level`（四档）。业务上报开启时由片级回调生成；业务上报关闭时收尾补一次同源生成（只登记语义、不发报文）。**不再回落呈现引擎**：生成失败则不产 tips 并清陈旧，部分失败时**尽力而为**（成功片照常进 tips、失败片缺席并逐条留痕）。

## 4. 网关自检（`smoke`）

### 4.1 什么时候跑

- 第一次安装后；
- 改了 `reviewer.baseUrl` / `reviewer.apiKey` / `model.default`；
- 换了网关、换了模型 id（尤其是 `ep-xxx`）；
- review 报网络错、401、404、429、长时间无输出；
- 升级 `review-pi` 后。

### 4.2 命令

```bash
review-pi smoke
review-pi smoke --model ep-20261031-xxxxxxxx
review-pi smoke --config ./ci/PiAgent.ci.json
```

`smoke` 只认 `--model` 与 `--config`；端点与 key 永远取配置。不传 `--model` 时用 `model.default`。

### 4.3 它实际做什么

两个探针，**成功时都会发真实 HTTP 请求**（健康探针失败时第 2 步会跳过）：

| 探针 | 请求 | 目的 |
|---|---|---|
| 1/2 网关健康 | `GET <baseUrl>/models` | 确认网关可达、DNS/TLS/代理通、key 至少能过传输层 |
| 2/2 模型可达 | `POST <baseUrl>/chat/completions`，body 含 `max_tokens: 1`、`stream: false` | 确认该模型 id 被网关接受，并且返回带 `choices` 与 `usage` 的 chat completion |

第 2 步会消耗极少 token（`max_tokens: 1`），但不是零成本。

smoke 是**诊断**命令：缺省每个探针只做 **1 次尝试**（`limits.retry.smokeAttempts = 1`），避免把一次瞬时抖动拖成十几秒的等待后仍然报同一失败。确有抖动环境可显式提高该值；重试只覆盖传输失败 / 超时 / 408 / 409 / 429 / 5xx，鉴权失败、模型不存在这类确定性错误不会重试。

### 4.4 输出怎么读

通过时：

```text
smoke probes at https://gateway.example.com/v1 (model ep-20261031-xxxxxxxx): OK
[1/2] gateway health: gateway is up at https://gateway.example.com/v1 (HTTP 200)
      models visible at the gateway (first 8 of 42): ..., ...
[2/2] model reachability: model "ep-20261031-xxxxxxxx" is reachable at https://gateway.example.com/v1 (...)
```

失败时第 1 行是 `FAILED`，随后每个探针给出人话归因与 `detail`（网关错误体摘要）。退出码：**通过 0 / 任何失败 1**。

### 4.5 失败诊断对照

| 诊断关键字 | 含义 | 处置 |
|---|---|---|
| `gateway unreachable ... DNS lookup failed` | 域名解析不了 | 检查 `baseUrl` 拼写、内网 DNS、VPN |
| `connection refused` | 主机端口没人监听 | 检查端口、是否该走代理 |
| `request timed out` | 连接/响应超时 | 检查网络与代理；网关慢时调大 `limits.timeouts.probeHealthMs` / `probeModelMs` |
| `authentication failed (HTTP 401/403)` | key 被拒 | `review-pi config show` 确认 `set`；确认 key 属于该网关；环境变量不再生效 |
| `rate limited (HTTP 429)` | key 有效但被限流 | 稍后重试；批量跑时降低并发 |
| `model ... was not found (HTTP 404)` | 模型 id 不被该端点服务，或 `baseUrl` 少了 `/v1` | 补 `/v1`；确认 `ep-xxx` 属于该 region/账号；`GET /models` 的列表可对照 |
| `gateway server error (HTTP 5xx)` | 网关自身故障 | 重试或联系网关运维 |
| `rejected the request body (HTTP 4xx)` | 请求体不被接受（常见是 `max_tokens` 超上限或参数不兼容） | 调小 `reviewer.maxOutputTokens`；确认网关是 OpenAI Chat Completions 兼容 |
| `not with a chat completion carrying choices and usage` | 返回不是标准 chat completion，或缺 `usage` | 该网关不满足计费/审计契约；换端点或让网关补齐 `usage` |
| `silently routed to a different model` | 请求的 id 与实际响应 model 不一致 | 典型是 `baseUrl` 路径错（缺 `/v1`）；修好前不要相信任何 run 结果 |

### 4.6 smoke 通过但 review 仍失败

| 可能 | 说明 |
|---|---|
| 模型在长上下文/工具调用下才失败 | smoke 只发一条 `ping`；review 会发系统提示、工具 schema、仓内代码。看 stderr 与审计里的 `truncationReasons` |
| 429 在批量时出现 | smoke 是单请求；批量跑会叠加并发，见 §7 |
| 输出预算不够 | 网关档默认 32768；若被路由到小输出模型，显式调小反而可能更稳；出现 `MODEL_MAX_TOKENS_REACHED` 时调大 |
| MR 超界 | 只告警不失败，但结论按 out-of-domain 看待（运行手册 §6「单次结果的读法」） |
| 规则包脚本失败 | 主检视照常；看审计 `ruleSkill[]` / `skillPassLog[]` 与 stderr |

## 5. 第一次检视

### 5.1 准备三样输入

| 输入 | 要求 | 说明 |
|---|---|---|
| 仓库快照 | 一个**目录** | 停在 diff 的 **base 侧**。CLI 不会 apply diff；它读的是目录现状。 |
| MR 变更 | `--mr-diff` **或** `--mr-json`，二选一 | `--mr-diff` = 标准 unified diff 文件；`--mr-json` = GitCode/GitLab 文件变更 JSON（见下）。`caseId` = 文件名去掉最后一个扩展名。 |
| issue 文本 | 可选字符串 | 原样进入初始 user 消息。建议用数据集原文，不要自编写。 |

`caseId` 细节：

- `VUL4J-38.diff` → `VUL4J-38`；
- `a.b.diff` → `a.b`（只去掉最后一段扩展名）；
- 无扩展名 → 整个文件名；
- 落盘时会再做文件系统安全化：非 `[A-Za-z0-9_.-]` 的字符替换成 `_`。所以 `a b.diff` 与 `a_b.diff` 会得到同一个 `caseId`（`caseId` 只作数据字段，不进产物路径，ADR-0032）。

**两种输入不通用**：接口 JSON 不能直接喂 `--mr-diff`（没有文件头会被判成空 diff），`.diff` 也不能喂 `--mr-json`（不是 JSON）。选对旗标即可，不需要手工转格式。

### 5.2 `--mr-json`：直接吃 GitCode 接口返回

`--mr-json` 吃的是「按文件切片的 hunk 片段」，但**同一平台不同接口的形状并不统一**。支持下面四种（顶层两种形态 × 条目两种层级）：

| 顶层 | 每项路径 | 每项正文 | 出处 |
|---|---|---|---|
| 数组 | `new_path` | `diff` | GitLab `/merge_requests/:iid/changes` |
| 数组 | `filename` | `patch` | GitCode `/pulls/:number/files`、GitHub `/pulls/:number/files` |
| 对象 `{diffs:[…]}` | `new_path` | `diff` | GitCode `/pulls/:number/files.json` |
| 数组 | `file_path`（外层） | `diff.diff`（内层对象） | GitCode 文件树包装（`{diff:{…}, file_path, file_type, level, title}`） |

读取优先级（取第一个非空值，外层优先）：

- 路径：`new_path` → `filename` → `file_path` → `path`（外层没有就看 `diff` 内层同名键）
- 正文：`diff` → `patch`（`diff` 是对象时向内递归到 `diff.diff` / `diff.patch`）

```json
[
  { "filename": "src/api/user.ts", "status": "modified", "patch": "@@ -12,9 +12,15 @@\n   id: number;\n-  email: string;\n+  email: string | null;\n }" },
  { "new_path": "src/utils/date.ts", "diff": "@@ -0,0 +1,3 @@\n+export const A = 1;" },
  {
    "diff": { "diff": "@@ -5,2 +5,2 @@\n-a\n+b", "new_path": "src/tree.ts", "too_large": false },
    "file_path": "src/tree.ts", "file_type": "file", "level": 9, "title": "src/tree.ts"
  }
]
```

- 四种形态可以混在同一份数组里（逐项按优先级取值），其余字段（`old_path` / `new_file` / `deleted_file` / `renamed_file` / `status` / `too_large` / `sha` / `level` / `title` / …）**一律忽略**；
- 新增 / 删除由 hunk 头自行判定：`@@ -0,0 ` = 新增（`--- /dev/null`），`+0,0 @@` = 删除（`+++ /dev/null`）；
- 正文为空的条目（二进制、纯改名、`too_large`；GitHub 形态里根本没有 `patch` 键）跳过；一个可转换条目都没有时 **exit 1**，不会静默当成「零变更」；
- 正文已经是整段 patch（`diff --git` 开头）时原样透传，不重复包头；
- 形状不符时错误带**条目序号**与**该项实际键名**（如 `第 1 项缺 new_path（…也可放在 diff 内层）——该项现有键：sha、file_path、title`），照提示换接口或换字段即可。

> 若所有条目的正文都为空，通常是**拉到了只有文件树的响应**（例如只有 `new_file` / `too_large` 元数据、`diff` 是空串）。这时换带补丁正文的接口重新导出，别硬跑——CLI 会明确报「全部为空 diff / 二进制 / too_large / 纯改名」而不是产出一份零变更的假结论。

```powershell
# 拉接口 → 直接检视，不用中间 .diff 文件
curl.exe -H "Authorization: Bearer $env:GITCODE_TOKEN" `
  "https://api.gitcode.com/api/v5/repos/OWNER/REPO/pulls/1234/files" -o MR-1234.json

review-pi review --repo D:\work\myrepo --mr-json MR-1234.json --taskId MR-1234
```

两个坑：

1. **编码**：`curl.exe -o` 写的是原始字节（UTF-8），没问题；但 PowerShell 用 `>` / `Out-File` 重定向会写成 UTF-16，任何 JSON 解析都会失败。改用 `Invoke-RestMethod ... | ConvertTo-Json -Depth 100 | Set-Content -Encoding utf8`，或直接用 `curl.exe -o`。
2. **`--repo` 与 diff 的对应关系**：本仓约定快照停在 diff 的 **base 侧**（CLI 不 apply diff，见 §5.1）。接口 JSON 与 `.diff` 在这点上完全一致——不要因为换成 `--mr-json` 就另外 checkout 到 head，否则基线会和既有 `--mr-diff` 跑法不一致。

### 5.3 最简命令

```bash
review-pi review \
  --repo /data/snapshots/my-repo-base \
  --mr-diff /data/diffs/change-001.diff \
  --taskId change-001
```

- `--taskId` **必需**：产物落 `~/.PiAgent/tasks/<taskId>/`；
- `--tasks-dir <dir>` 只覆盖 tasks **根**（缺省 `~/.PiAgent/tasks`；相对 cwd 解析），产物仍是 `<tasksDir>/<taskId>/`；
- `--repo` / `--mr-diff` / `--tasks-dir` 都按 **cwd** 解析相对路径；
- `--taskId` 是**单段目录名**：不能含 `/` `\`、盘符、前导点、`<>:"|?*`、控制字符，也不能是 Windows 保留名（`CON` / `NUL` / `COM1`…）或尾随点；允许中文与空格；
- 建议第一次就用绝对路径，避免「我在哪个目录跑的」这种问题。

### 5.4 带 issue

```bash
review-pi review \
  --repo /data/snapshots/my-repo-base \
  --mr-diff /data/diffs/change-001.diff \
  --issue "Fix NPE in OrderService when customer is null (CVE-2026-xxxx)." \
  --taskId change-001
```

PowerShell 里 issue 含空格、括号、URL 时整体用双引号包住；注意 `$` 会被 PowerShell 展开，issue 文本里尽量避免 `$`，或用单引号。

### 5.5 带规则 Skill

规则包**只认显式输入**，不会扫描被检视仓库的 `.review-rules/`（ADR-0027）。**一个包就是一个 skill**，多包一次传入（ADR-0034）：

```bash
# zip 包：逗号列表一次传多个（执行顺序 = 列表顺序）
review-pi review ... \
  --rule-skill-zip /data/rules/general-code-review.zip,/data/rules/java-rules.zip

# 不加引号也成立：bash 保留尾逗号、PowerShell 连逗号一起吃掉，两种形态都归并成同一列表
review-pi review ... \
  --rule-skill-zip /data/rules/general-code-review.zip, /data/rules/java-rules.zip

# 已解压目录（同样可逗号列表；与 zip 共存时排在全部 zip 之后）
review-pi review ... \
  --rule-skill /data/rules/general-code-review,/data/rules/java-rules

# --skill 当前与 --rule-skill 同义（同一类 Skill；装载时排在全部 --rule-skill 之后）
review-pi review ... \
  --skill /data/rules/general-code-review,/data/rules/java-rules

# 重复旗标是等价写法（两种可混用）
review-pi review ... \
  --rule-skill-zip /data/rules/general-code-review.zip \
  --rule-skill-zip /data/rules/java-rules.zip

# 装载失败即失败（CI / 生产）
review-pi review ... \
  --rule-skill-zip /data/rules/general-code-review.zip \
  --strict-rule-skill
```

不传规则包也能跑：主检视照常，stderr 一行提示，exit 0。带 `--strict-rule-skill` 但不传任何包会报错。包内若意外含多个 skill，该包按「不合规」降级（`degradedReason` 留痕；strict 下 exit 1）——正确处置是拆成多个包。

**同名 skill 只保留一个**：装载序是「全部 zip → 全部 `--rule-skill` → 全部 `--skill`」，同名时**后装载者胜出**——所以用 `--skill` 传入同名目录可以直接覆盖 `--rule-skill` / zip 里的版本（临时替换共享规则包里的某条规则时很有用）。降级占位（`name` 为空）不参与去重，失败过的包仍在审计里留痕。

`--rule-skill` / `--rule-skill-zip` / `--skill` 后面**没有值**（argv 结束，或紧跟另一个旗标）时按「未传」处理，只在 stderr 提示一行 `--rule-skill 缺少值，已忽略（本轮不装载该包）`，**不再报用法错误**：这些旗标几乎总是由脚本按变量拼出来，PowerShell 在变量为空时会把这个参数整个丢掉，那种「机器上变量没设」不该让整条命令起不来。值位置**给了空串 / 纯空白 / 纯逗号**（`--skill ""`、`--rule-skill " , "`）也按「未传」处理——bash 的 `--skill "$dirs"` 在变量为空时正是这个形态，与 PowerShell 丢参数是同一件事。要装载就把路径补上，或脚本里只在非空时拼旗标。

### 5.6 中文按行建议（`reviews_tips_zh.json`）

**ADR-0065 起中文建议不再依赖呈现引擎**：命令不变、不加任何旗标，只要有检视意见（且通过 `limits.confidence.min` / `limits.severity.min` 过滤）就会产出：

```bash
review-pi review --repo ... --mr-diff ... --taskId ...
```

- 业务上报开启：片级回调把同一份语义既发给 `mrReviewResult`，也落成 `reviews_tips_zh.json`；
- 业务上报关闭：收尾补一次同源语义生成（只登记语义、不发报文），落成同一个文件；
- 零意见 / 全部被过滤：产 `[]`；生成失败：不产文件并清陈旧。

stdout 始终是英文源文档（见 §5.7），不因中文建议而改变。

### 5.7 一次 review 的完整行为

```text
parse args
  → 配置装载（读一次 → 不可变快照）
  → 凭据 fail fast（缺 reviewer.apiKey）
  → 解析 --repo / --mr-diff 路径与 tasks 根（ADR-0033）
  → stderr 回显本次生效参数（ADR-0043：开跑前）
  → 读 --repo 目录 / --mr-diff 文件（或 --mr-json 并在装载期补文件头）
  → runReview：
       MR 初始上下文 → 六阶段循环（工具驱动 + Context Ledger）
       → Phase 5 后每个规则 Skill 一个独立会话
       → 候选门 → 合并 → 判定
       → 写 RunRecord / 审计 / 会话转录 / reviews_en.json
  → 片级语义生成 / 中文 tips 组装（业务开关无关；业务关闭时收尾补一次）
  → stdout 单 JSON（恒英文）
  → 退出码
```

**stdout 契约**：整个 stdout 是**一个 JSON 文档**，不会混入日志。顶层键：

```json
{
  "ok": true,
  "caseId": "change-001",
  "runId": "20261031_101500_000",
  "truncated": false,
  "rounds": 5,
  "toolCalls": 23,
  "findings": [ ... ],
  "auditPath": "C:\\Users\\me\\.PiAgent\\tasks\\change-001\\audit\\20261031_101500_000.json"
}
```

- `findings` 与审计 / `reviews_en.json` 同一份英文真源；ADR-0065 起恒英文，**没有** `presentation` 键；
- 成本与 usage **不在 stdout**，在 `run.json` 与审计里；
- 一切诊断、进度、警告都在 **stderr**。

**传入参数回显（开跑前，同样只走 stderr）**：在装载 diff 与进度投影之前，把本次**实际生效**的参数逐行打印出来——相对路径已按 cwd 解析成绝对路径，缺省值已落成生效值并标注来源，可重复旗标按传入顺序全列（ADR-0043：打印点已从收尾提前到开跑前）：

```text
review-pi: 本次 review 传入参数
  --repo              /data/repo
  --mr-diff           /data/in/MR-1234.diff
  caseId              MR-1234
  --issue             "修复登录超时"
  --taskId            change-001
  --tasks-dir         /home/me/.PiAgent/tasks（缺省：~/.PiAgent/tasks）
  --model             deepseek-v4-flash（缺省：配置文件 model.default）
  --config            /home/me/.PiAgent/PiAgent.jsonc（缺省用户级路径）
  --rule-skill-zip    rules/java.zip
  --rule-skill        (未传)
  --skill             (未传)
  --strict-rule-skill 未启用
  --no-progress       未启用（缺省打印）
```

- `--mr-json` 形态时标签就是 `--mr-json`；`--issue` 用 JSON 字符串转义（多行不会破行）；
- `--no-progress` 显示的是**实际开关**：未传 = 缺省打印进度事件行，传了就静音（ADR-0055）；`--progress` 已移除，继续传会 `exit 1` 并给迁移提示；
- 这一路只回显参数，**不含 apiKey / baseUrl 等配置秘密**；stdout 仍是单 JSON 文档。

**收尾总结行（恒定打印，与进度事件行无关）**：每次 review 结束前往 stderr 写一行，无论是否传 `--no-progress`：

```text
✓ 完成 · 耗时 358.2s · 模型调用 17 次 · token 输入 179,527（未命中） · 输出 20,854 · 缓存命中 165,888（48.0%） · 工具 30 次（主会话 18 + 规则 Skill 12） · Ledger 命中 4 次（未重复读取原文） · $0.0312
```

- **耗时**只算检视本体，不含之后的中文 tips 生成 / 落盘（所以可能比墙上时钟短）；
- **token 三段**与审计 `usage` 同源（含规则 Skill 会话）；「输入」是**未命中**部分，缓存命中率分母 = 未命中输入 + 缓读 + 缓写；
- **模型调用** = 主会话请求 + 规则 Skill 会话请求；
- **工具** = 主会话 + 规则 Skill 的检视工具（与 `record.baseline.toolCalls` 同口径）；规则 Skill 内真跑过 `bash` 时另加一段 `skill bash N 次`（指标口径不含 bash，ADR-0014）；
- **Ledger 命中** = Context Ledger 复用次数：同一读取请求再次出现时返回 `Already loaded: ctx#NNN` 引用，原文没有第二次进上下文；该计数只用于这一行，不写审计；
- 成本用与转录同一份模型画像 + 同一个 `calculateCost` 公式。

**退出码**：

| 码 | 含义 |
|---|---|
| `0` | 完成。包括**诚实截断**（`truncated: true`）——截断是完成的一种，不是失败 |
| `1` | 用法错误、配置错误、凭据缺失、网络/模型错误、产物写失败、`--strict-rule-skill` 装载失败等 |

**stderr 常见但不算失败的行**：

- `✓ 完成 · 耗时 … · 模型调用 … · token … · 工具 … · Ledger 命中 … · $…`（每次 review 收尾恒打一行，见 §5.7）
- `review-pi: 本次 review 传入参数`（开跑前先打，逐行回显本次生效参数，见 §5.7）
- `review-pi: 未装载任何规则包（...），照常检视`
- `review-pi: 检视意见未获统一生成覆盖（…），tips 缺席该条：…`
- `review-pi: 中文 tips 语义生成失败（…），本次不产分组意见`
- `review-pi: 统一生成未覆盖任何意见，本次不产分组意见（不回落英文引擎）`
- `review-pi: 已清除陈旧 …`
- `review-pi: 执行目录副本写入失败（路径: 原因）`（cwd 只读等，exit 仍 0）
- `.env.local` 已不再读取的提示

### 5.8 取回 session（cwd 索引与 `export`）

每次 `review` 成功后在**执行目录**写一份隐藏索引 `.review-pi-session.json`（ADR-0036）：只有绝对路径与 runId，不含检视内容，重复执行整份覆盖。

```json
{
  "version": 2,
  "taskId": "change-001",
  "tasksDir": "C:\\Users\\Li\\.PiAgent\\tasks",
  "runId": "20261103_112336_401",
  "repo": "D:\\data\\repos\\my-repo-base",
  "updatedAt": "2026-11-03T11:23:36.401Z",
  "mains": [
    "C:\\Users\\Li\\.PiAgent\\tasks\\change-001\\runs\\session-20261103_112336_401.json"
  ],
  "skills": []
}
```

- `version: 2`（ADR-0039）：主转录是数组 `mains[]`（单遍长度 1；分片按 `s01 → s02 → …`），读取端兼容 v1 的单个 `main`，新写一律 v2。

`review-pi export` 读它并往 stdout 打**一行**绝对路径（逗号 + 空格分隔；单遍：主 session 在前、skill 按装载顺序；分片：`s01 主 → s01 skill → s02 主 → …`）。ADR-0072 起**缺省返回 OpenCode 兼容版**（`<runs>/opencode/session-*.json`），`--native` 切回 pi 原生转录：

```bash
review-pi export                      # OpenCode 兼容版 session 路径
review-pi export --native             # pi 原生转录路径
review-pi export --path ./sessions    # 复制所选表示到该目录（平铺、同名覆盖），返回复制后的路径；复制兼容版时目标目录多一份 manifest.json
review-pi export --taskId change-001  # 不经索引：去 tasks 根下读该任务最新一次 run
review-pi export --path ./sessions --taskId change-001
```

- **不加载配置、不需要 apiKey、不调模型**：纯文件系统命令，配置文件缺席 / CI 容器里同样可用。
- `--taskId` 的 tasks 根判定：cwd 索引里的 `tasksDir` → `--tasks-dir <dir>` → 缺省 `~/.PiAgent/tasks`。runId 由 `run.json` 的 `baseline.auditPath` 反推。
- 只认**最新一次 run**；`--path` 目标不存在则创建（相对 cwd），同名覆盖，失败 `exit 1` 不回滚。
- 索引缺失 / 任务或文件不存在 / 索引非法 ⇒ `exit 1` + 人话原因（不返回幽灵路径）。
- 索引是隐藏文件，**别提交进仓库**：在 git 仓库根跑时把 `.review-pi-session.json`（连同 `review-result.json`）加进 `.gitignore`。

> 产物树、结果读法、MR 边界与重跑覆盖语义的完整版见《[运行手册：单次检视](运行手册-单次检视.md)》§5 / §6。

### 5.9 重跑与覆盖语义

`rep` 概念已从路径与文件名退场（ADR-0032）。同一个 `--taskId` 再跑一次：

| 产物 | 行为 |
|---|---|
| `<tasks 根>/<taskId>/runs/run.json` | **覆盖** |
| `<tasks 根>/<taskId>/runs/reviews_en.json` | **覆盖** |
| `<tasks 根>/<taskId>/runs/reviews_tips_zh.json` | 覆盖；本次不产则**删除** |
| cwd `review-result.json` | 覆盖；本次不产则**删除** |
| cwd `.review-pi-session.json` | **覆盖**（每次都指向最新一次成功 run） |
| `<tasks 根>/<taskId>/audit/<ts>.json` | **新增**（`<ts>` 含毫秒，旧审计保留） |
| `<tasks 根>/<taskId>/runs/session-<ts>.json` | **新增**（旧转录保留） |
| `<tasks 根>/<taskId>/.cache/rule-skills/` | 命中缓存则复用；规则包内容变了就是新哈希目录 |

所以：

- **想保留多次结果 → 每次换一个 `--taskId`**（一个任务目录 = 一次 run 的快照）；
- 同一个 `--taskId` 适合「同一任务的迭代重跑」，磁盘上只留最新一份 `run.json` / `reviews_*.json`，但审计/转录会累积；
- `caseId` 由 `--mr-diff` / `--mr-json` 文件名决定，只出现在 `run.json`、审计与转录 `info.title` 的数据字段里。

## 6. 在任意目录运行

### 6.1 为什么可以

安装形态下，命令不依赖你在哪个目录：

1. **bin 在 PATH 里**：`npm i -g` 生成全局 shim（Windows 是 `review-pi.cmd`），由 npm 的全局 bin 目录提供；
2. **依赖从包的安装位置解析**：bin 用 `import.meta.url` 定位自己，再按 Node 的包解析规则找本包 `dist/` 与 `node_modules` 里的内核四包，与 cwd 无关；
3. **配置从 home 读**：默认 `~/.PiAgent/PiAgent.jsonc`，与 cwd 无关；
4. **builtin 引擎在包内（legacy，ADR-0065）**：`"builtin"` 解析到 `<包目录>/presentation/engine-zh.js`，不依赖 cwd；CLI 不再调用它；
5. **只有输入/输出路径相对 cwd**：那是你显式给 CLI 的路径，理应按你当前所在目录解释。

### 6.2 相对路径基准表

| 参数 | 相对谁 | 说明 |
|---|---|---|
| `--repo` | cwd | `resolve(args.repo)` |
| `--mr-diff` | cwd | `readFile(resolve(args.mr))`，内容按统一 diff 解析 |
| `--mr-json` | cwd | 同上取文件；装载期补文件头转统一 diff（ADR-0029），坏 JSON 立即 exit 1 |
| `--taskId` | — | 必需；单段目录名，产物落 `<tasks 根>/<taskId>/` |
| `--tasks-dir` | cwd | tasks 根覆盖；缺省 `~/.PiAgent/tasks`（home，不在 cwd） |
| `--config` | cwd | 缺省走 home |
| `--rule-skill-zip` | cwd | loader 直接 stat/read |
| `--rule-skill` | cwd | loader 直接 stat/copy |
| `--skill` | cwd | 当前与 `--rule-skill` 同链路 |
| `--from-env` | cwd | 仅 `config init` |
| 自定义引擎路径 | **配置文件所在目录** | 不是 cwd（ADR-0026） |

### 6.3 cwd 的四个副作用

跑 review 时，当前目录会发生四件事：

1. **`review-result.json` 的写/删**：产出 tips 时写一份；不产时删除旧副本。写失败只警告，exit 0。
2. **`.review-pi-session.json` 的写**：每次成功 run 整份覆盖（绝对路径索引，供 `review-pi export` 用，ADR-0036）。写失败只打一行 stderr 警告，exit 0。
3. **`.env.local` 探测**：只 `stat`，不读内容；存在就打一行「已不再读取」提示。
4. **规则 Skill 的 bash 子进程 cwd 是规则包缓存目录**，不是你的 cwd。规则包里的脚本写相对路径文件时，落在 `<tasks 根>/<taskId>/.cache/rule-skills/<digest>/` 下。

除此之外，review **不写 cwd**：审计、转录、导出、规则包缓存全部在 `<tasks 根>/<taskId>/` 下。

### 6.4 推荐姿势

- 第一次跑：所有路径用**绝对路径**；
- 长期跑：给每个任务一个固定 `--taskId`，产物自动归到 `~/.PiAgent/tasks/<taskId>/`；
- 不要在只读目录（如系统目录、挂载的只读盘）里跑：canonical 产物写 `<tasks 根>/<taskId>` 没问题，但 cwd 副本与索引会失败并警告；
- 在 git 仓库根跑时，把 `review-result.json` 和 `.review-pi-session.json` 加进 `.gitignore`。

### 6.5 三种 shell 的示例

**PowerShell**

```powershell
$case = "change-001"

  --repo "D:\data\repos\my-repo-base" `
  --mr-diff "D:\data\diffs\change-001.diff" `
  --issue "Fix NPE when customer is null." `
  --taskId $case
```

**cmd**

```bat

```

**bash**

```bash

  --repo /data/repos/my-repo-base \
```

### 6.6 CI 里的最小步骤

```yaml
- run: npm i -g @baize/review-pi
- run: |
    mkdir -p "$RUNNER_TEMP/review-cwd"
    cd "$RUNNER_TEMP/review-cwd"
    review-pi review \

      --mr-diff "$DIFF_PATH" \
```

- key 用 CI secret 写进临时配置文件，跑完删除；
- 退出码直接作为 job 结果：0 成功（含截断），1 失败。

## 7. 并发与隔离

### 7.1 结论先说

**不同 `<tasks 根>/<taskId>` + 不同 cwd = 不冲突。**

两个 run 只要满足：

- 产物目录不同（不同 `--taskId`，或同一个 taskId 但 `--tasks-dir` 指向不同物理目录）；
- 进程 cwd 不同（或你接受 cwd 副本互相覆盖）；

那么它们的 canonical 产物、审计、转录、规则包缓存、cwd 副本全部隔离，可以并行跑（前提是网关与机器资源扛得住并发请求；见 §7.4 第 6 条）。

但以下情况会冲突：

| 场景 | 冲突点 | 严重度 |
|---|---|---|
| 同 taskId（无论 `caseId`） | `run.json`、`reviews_en.json`、`reviews_tips_zh.json` 互相覆盖；同毫秒还会撞转录 / 审计文件名 | 高（产物不可信） |
| 同 taskId 并发 | 以上全部 + 共享 `.cache/rule-skills` | 高（规则包冷启动竞态） |
| 不同 taskId + 同 cwd | cwd 的 `review-result.json` 互相覆盖/删除 | 中（只影响便利副本） |
| 同 taskId + 同 cwd | 以上全部 | 高 |
| 不同字符串但同一物理目录（同一 tasks 根 + 同 taskId） | 等价于同 taskId | 高 |

### 7.2 「不同」怎么判定

- `--tasks-dir` 相对路径按 cwd 解析、`.` / `..` 归一；缺省根来自 home（`~/.PiAgent/tasks`），与 cwd 无关；
- 但 `resolve` **不跟随符号链接 / junction**。两个字符串指向同一个物理目录（例如 `D:\tasks` 与 `D:\link-to-tasks`）仍然会冲突；
- Windows 文件系统大小写不敏感：`D:\Tasks` 与 `D:\tasks` 是同一目录；taskId 同理（`Change-001` 与 `change-001` 会落到同一个目录）；
- 网络盘 / 挂载点：不同挂载路径指向同一后端存储，也会冲突；
- `caseId` 由 `--mr-diff` 的 basename 派生，**完全不影响路径**（ADR-0032 / ADR-0033）——两个不同 case 共用同一个 taskId 会互相覆盖。

### 7.3 共享任务目录时到底共享什么

**1）canonical 产物不按 `caseId` 分目录**

```text
<tasks 根>/<taskId>/runs/{run.json, session-*.json, reviews_*.json}
<tasks 根>/<taskId>/audit/<ts>.json
```

同一个 taskId 里的两次 run 会互相覆盖 `run.json` 与两份 `reviews_*.json`；转录 / 审计靠毫秒时间戳各自保留（同毫秒才撞）。**要并行或保留多次结果，必须各自用独立 taskId（或独立 `--tasks-dir`）。**

**2）规则包缓存是任务目录级共享**

```text
<tasks 根>/<taskId>/.cache/rule-skills/<sha256>/
<tasks 根>/<taskId>/.cache/rule-skills/dir-<sha256>/
```

装载逻辑是「查 ready marker → 没有就 `rm -rf` → 重建 → 写 marker」。**没有跨进程锁**。两个进程同时冷启动同一个规则包时，可能：

- A 正在解压，B 把目录删了重建；
- A 刚写完 marker，B 又把目录删掉重建，A 后续加载读到的是被替换的目录；
- 结果是一个 run 的规则包装载降级（stderr / 审计 `degradedReason`），`--strict-rule-skill` 时直接 exit 1。

**3）规则 Skill 的 bash 以缓存目录为 cwd**

规则包里的脚本如果写相对路径文件（日志、临时产物），会写进共享缓存目录。两个 run 用同一个规则包、同一个任务目录时会互相踩。

**4）cwd 副本是进程级共享**

`review-result.json` 固定写在 cwd，没有 case 前缀。两个 run 共用一个 cwd 时，后完成的覆盖先完成的；不产 tips 的 run 还会删掉它。

**5）不共享的东西**

- 配置：每个进程启动时读一次，互不影响；
- 审计 / 转录：文件名含 `runId`（时间戳），不同 run 不会覆盖；
- 被检视仓库：只读，规则包缓存绝不写回仓库；
- `review-pi` 包本身：只读。

### 7.4 绝对安全的并发 checklist

1. **一次 run 一个 taskId**；需要固定落点就用 `--tasks-dir` 指绝对路径，不要指向符号链接的同一目标。
2. **一次 run 一个 cwd**（`mkdir` 一个空目录再 `cd` 进去），或者接受 `review-result.json` 最后写入者胜。
3. **同一个任务目录内只跑一个 run**；`caseId` 不再提供任何隔离。
4. **共享规则包时先预热一次**：单独跑一个最小 case，让缓存 marker 落地，再并行；或者每个 run 用独立 taskId。
5. **不要并行 `config init --force` 同一个文件**；配置文件是读一次的，运行中改不影响当前进程，但会让下一次 run 拿到不同配置。
6. **控制对外并发**：`concurrency.suggestion` 是**单进程内**建议生成的并发，不是全局限流；N 个 run 并行 = N 倍请求，容易撞 429。
7. **CI 里给每个 job 独立 workspace / `--tasks-dir`**；不要多个 job 共享缓存目录。

### 7.5 并行配方

**bash（每个 case 独立 cwd + tasks 根）**

```bash
run_one() {
  local case_id="$1" repo="$2" diff="$3"
  local base="/data/reviews/$case_id"
  mkdir -p "$base/cwd"
  (
    cd "$base/cwd" || exit 1
    review-pi review \
      --repo "$repo" \
      --mr-diff "$diff" \
      --taskId "$case_id" \
      --tasks-dir "$base/tasks" \
      --no-progress \
      >"$base/stdout.json" 2>"$base/stderr.log"
  )
}

run_one change-001 /data/repos/a /data/diffs/change-001.diff &
run_one change-002 /data/repos/b /data/diffs/change-002.diff &
run_one change-003 /data/repos/c /data/diffs/change-003.diff &
wait
```

**PowerShell 7（`ForEach-Object -Parallel`）**

```powershell
$cases = @(
  @{ Id = "change-001"; Repo = "D:\data\repos\a"; Diff = "D:\data\diffs\change-001.diff" },
  @{ Id = "change-002"; Repo = "D:\data\repos\b"; Diff = "D:\data\diffs\change-002.diff" }
)

$cases | ForEach-Object -Parallel {
  $base = Join-Path "D:\reviews" $_.Id
  $cwd  = Join-Path $base "cwd"
  New-Item -ItemType Directory -Force -Path $cwd | Out-Null
  Push-Location $cwd
  try {
    review-pi review --repo $_.Repo --mr-diff $_.Diff --taskId $_.Id --tasks-dir (Join-Path $base "tasks") --no-progress `
      *> (Join-Path $base "console.log")
  } finally {
    Pop-Location
  }
} -ThrottleLimit 3
```

PowerShell 5.1 没有 `-Parallel`，用 `Start-Process -Wait` 或 `Start-Job`，同样保证每个进程独立 cwd/tasks 根。

**CI matrix**

```yaml
strategy:
  matrix:
    case: [change-001, change-002, change-003]
steps:
  - run: |
      mkdir -p "runs/${{ matrix.case }}/cwd"
      cd "runs/${{ matrix.case }}/cwd"
      review-pi review \
        --repo "${{ github.workspace }}/repos/${{ matrix.case }}" \
        --mr-diff "${{ github.workspace }}/diffs/${{ matrix.case }}.diff" \
        --taskId "${{ matrix.case }}" \
        --tasks-dir "${{ github.workspace }}/runs/${{ matrix.case }}/tasks" \
        --no-progress
```

每个 matrix job 天然独立 workspace；如果 runner 复用缓存，确保 `--tasks-dir` 不落到共享路径。

## 8. 排障

### 8.1 安装

| 现象 | 原因 | 处置 |
|---|---|---|
| `review-pi: command not found` / `不是内部或外部命令` | 全局 bin 目录不在 PATH | `npm config get prefix`，把对应 bin 目录加进 PATH；重开终端 |
| `EBADENGINE` | Node < 22.19 | 升级 Node；不要忽略 |
| `EACCES` / `EPERM` | 全局目录无写权限 | 用用户级 prefix 或 nvm；不要 `sudo` |
| `failed to spawn ripgrep binary` | postinstall 没下到二进制 | 重装 `@vscode/ripgrep`，检查 GitHub 访问/代理/镜像 |
| `Cannot find module '@earendil-works/pi-ai'` | 内核依赖没装齐（registry 解析失败 / 离线机器没代理该 scope） | 确认 `@earendil-works` 可解析（§2.3），重装 `review-pi` |
| `ERR_PNPM_BIN_CRLF`（打包侧） | bin 行尾被改成 CRLF | 保持 `.gitattributes` 的 `eol=lf`；重新 checkout |
| `config show` 报 `--config 指定的文件不存在` | 显式路径写错 | 用绝对路径或先 `config init --config <path>` |

### 8.2 配置

| 现象 | 原因 | 处置 |
|---|---|---|
| `未找到用户级配置文件 ...（按内置缺省运行）` | 还没 init，或 home 不对（WSL） | `review-pi config init`；WSL 下注意 Linux home |
| `配置文件已存在（...）——加 --force 覆盖` | 重复 init | 直接编辑；确需重置才 `--force` |
| `parse error at line N, column M` | JSONC 语法错 | 按行列修；JSONC 允许注释和尾逗号，但字符串里的注释符是字面量 |
| `version is required` / `version must be 1` | 文件存在但缺/错 `version` | 加 `"version": 1` |
| `reviewer.apiKey must be a string` 等 | 类型错 | 按提示改；不做静默钳制 |
| `unknown key ...` 警告 | 拼写错、旧键或已删除的键（如 `models`） | 删掉或改成正确键；警告不阻断 |
| `... 已钉死（pinned），不会被采用` | 写了工具调用数、温度等死钉项 | 删掉；行为不变（轮次上限已可配：`limits.loop.maxRounds`） |
| `配置文件权限过宽`（POSIX） | 宽于 `0600` | `chmod 600 ~/.PiAgent/PiAgent.jsonc` |
| 缺 key 的人话错误 | `reviewer.apiKey` 为空 | 填 key；`config show` 确认 `set`；环境变量不再生效 |
| `--env 已移除...` | 旧命令 | 改用 `--config`；旧 `.env.local` 用 `config init --from-env` 迁移 |

### 8.4 review

| 现象 | 原因 | 处置 |
|---|---|---|
| `--repo is not a directory: ...` | 路径错，或传了文件 | 传仓库快照根目录 |
| `ENOENT ... open ...diff` / `...json` | 输入路径错 | 用绝对路径；确认文件可读 |
| `missing required flag --repo` / `--mr-diff (or --mr-json)` / `--taskId` | 少参数 | 补参数；注意 PowerShell 续行反引号后不能有空格 |
| `conflicting flags --mr-diff and --mr-json` | 两种输入同给 | 只留一个：diff 文本用 `--mr-diff`，接口 JSON 用 `--mr-json` |
| `--mr 已改名（ADR-0029）...` | 用了旧旗标 | 换成 `--mr-diff` / `--mr-json` |
| `--out 已移除（ADR-0033）...` | 用了旧旗标 | 换成 `--taskId <id>`；要换落盘根用 `--tasks-dir <dir>` |
| `invalid --taskId "...": ...` | taskId 不是单段目录名（含 `/`、`..`、前导点、Windows 保留名、尾随点等） | 换一个不带路径语义的目录名；允许中文与空格 |
| `--mr-json: 不是合法 JSON` / `没有可转换的文本 diff` | 文件不是数组 / 全是空 diff | 用接口 `/files` 的原样响应；确认不是 UTF-16（PowerShell `>` 会写成 UTF-16） |
| `unknown flag --xxx` | 拼写错 / 旧旗标 | 对照运行手册 §1 旗标表；规则包用 `--rule-skill-zip` / `--rule-skill` / `--skill` |
| `未装载任何规则包...` | 没显式给规则包（或旗标缺值被忽略） | 合法降级，exit 0；要跑 skill 会话就补参数 |
| `--rule-skill 缺少值，已忽略...` | 旗标后面没跟值，或值只有空串 / 纯空白 / 纯逗号；PowerShell 变量为空时会把整个参数丢掉，bash 会传空串（`--skill` 同口径） | 合法降级，exit 0；要装载就把路径补上，或脚本里只在非空时拼旗标 |
| `no rule-skill archive given...` | `--strict-rule-skill` + 没给包 | 补包，或去掉 strict |
| 规则包抛错（strict） | 路径错 / 非 zip / 无 `SKILL.md` / 包内多个 skill（一包一 skill） / 目录含符号链接 | 先去掉 strict 看审计 `degradedReason`；包内多个 skill 就拆成多个包（`--rule-skill-zip a.zip,b.zip`）；目录用 `--rule-skill`（或等价的 `--skill`） |
| `--rule-skill-name 已移除（ADR-0034）...` | 用了一包多 skill 时代的包内消歧旗标 | 删掉它：一个包就是一个 skill；多包用逗号列表或重复旗标 |
| `review-pi: 中文 tips 语义生成失败（…），本次不产分组意见` | 片级语义生成调用失败（网关 / 超时 / 非法 JSON） | 检视本体已完成、exit 0；`reviews_en.json` 与 stdout 完好。查网关与 `limits.timeouts.oneShotMs` |
| `review-pi: 统一生成未覆盖任何意见，本次不产分组意见（不回落英文引擎）` | 模型没给出可用的语义字段（逐条被校验跳过） | 读上一行「未获统一生成覆盖」原因；不会回落到呈现引擎 |
| `presentation.engine 指向的模块不存在` | legacy 键的路径写错（ADR-0065 后不影响运行） | 可忽略；要从外部直接调用 legacy 引擎才需要修正路径 |
| `退出码 0 但 truncated=true` | 诚实截断（轮数 / 工具预算） | 不是失败；看审计 `truncationReasons` |
| `MODEL_MAX_TOKENS_REACHED` | 输出撞 `max_tokens` | 调大 `reviewer.maxOutputTokens`；官方直连需显式设才会下发 |
| cwd 没 `review-result.json` | 本次零意见 / 生成失败不产 tips，或 cwd 不可写 | 看 stderr；真源在 `<tasks 根>/<taskId>/runs/reviews_tips_zh.json` |
| `review-pi export` 报 `未找到 session 索引` | 当前目录没跑过成功的 review（或换了目录） | 先在该目录跑一次 review；或改用 `--taskId <id>` + `--tasks-dir <dir>` |
| `review-pi export` 报 `session 文件不存在：…` | 转录被手工删/移走，或 tasks 根指错 | 用 `--taskId` 重算；确认 `--tasks-dir` / 索引里的 `tasksDir` 指对（索引不返回幽灵路径） |
| `review-pi export` 报 `unknown flag "--config"` | `export` 不加载配置，只认 `--taskId` / `--tasks-dir` / `--path` / `--native` | 去掉 `--config` |
| `review-pi export` 报 `该 run 没有 OpenCode 兼容转录（…旧 run 请改用 --native…）` | 本次 run 是 ADR-0072 之前跑的，无 `runs/opencode/` 兼容产物 | 用 `--native` 取原生转录；或升级后重跑同一任务 |
| PowerShell 里每条 stderr 都被包成 `NativeCommandError`（`所在位置 …review-pi.ps1:16`） | npm 生成的 `review-pi.ps1` 把原生命令的 stderr 记录转成 PowerShell 错误记录；**内容是 CLI 原本的人话，退出码也正确** | 这是 PowerShell 对外部命令 stderr 的行为，不是 CLI 失败。要不看到这层外壳：直接调 `node "$(npm root -g)/review-pi/bin/review-pi.js" …`，或 `cmd /c review-pi …`；也可以在脚本里用 `$ErrorActionPreference = "Continue"` 并只看 `$LASTEXITCODE`。 |
| 目录里有旧 `reviews_zh.json` | 已停产产物 | 本次 run 会主动清除；中文看 `reviews_tips_zh.json` |

### 8.5 并发

| 现象 | 原因 | 处置 |
|---|---|---|
| 两个 run 的 `reviews_en.json` 内容混了 | 同 taskId（caseId 不再隔离） | 每个 run 独立 `--taskId`（或独立 `--tasks-dir`） |
| 规则包偶发降级 / `--strict` 偶发 exit 1 | 共享任务目录的规则包缓存冷启动竞态 | 先预热，或独立 taskId |
| cwd 的 `review-result.json` 时有时无 | 多 run 共用 cwd，且有的零意见 / 生成失败不产 tips | 每个 run 独立 cwd |
| `.review-pi-session.json` 指向「另一个」run | 多 run 共用 cwd：索引每次成功 run 整份覆盖，最后一次赢 | 每个 run 独立 cwd；或改用 `review-pi export --taskId <id>` 明确指定任务 |
| 大量 429 | 并行 run 叠加请求 | 降低并行度；错峰；看 `concurrency.suggestion` 只限单进程 |
| 一个 run 写产物时报 EACCES | tasks 根在只读盘 / 网络盘权限 | 换 `--tasks-dir` 到本地可写目录 |

## 9. 安全与隐私

- **凭据**：只放配置文件；不通过命令行参数传 key；不提交配置文件；CI 用 secret 挂临时文件并在 job 末尾删除。
- **发送范围**：检视会把 `--repo` 中被工具读取的文件内容、`--mr-diff` / `--mr-json` 的变更内容、`--issue` 文本发给配置的模型端点。确认数据出境/留存政策后再对敏感仓库使用。
- **产物敏感性**：`reviews_en.json` / `reviews_tips_zh.json` / 审计 / 转录会包含代码片段、文件路径、模型输出与用量。`<tasks 根>/<taskId>` 与 cwd 副本都应按内部资料管理。
- **规则包信任**：`--rule-skill-zip` / `--rule-skill` / `--skill` 里的脚本由规则 Skill 的 `bash` 工具执行，工作目录是 `<tasks 根>/<taskId>/.cache/rule-skills/<digest>/`。只装载可信来源的规则包；不要把不可信 zip 直接喂给生产环境。
- **cwd 副本**：`review-result.json` 可能包含代码行与建议；在共享目录跑完后注意清理，或把它加进 `.gitignore`。`.review-pi-session.json` 只含绝对路径与 runId（不含检视内容），但会暴露本机目录结构，同样不建议提交/外发。
- **审计脱敏**：审计顶层 `config` 只记 `reviewer.apiKey: set|missing`，不记值；`digest` 不能反推 key。
