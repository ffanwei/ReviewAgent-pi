# 运行手册：离线回放与并发阶梯

> 适用范围：本仓工具链 `scripts/offline-replay/`（**不是**产品包的一部分，不随 `@baize/review-pi` 发行）。
> 决策真源：[ADR-0048](../docs/adr/0048-offline-trace-replay-and-concurrency-ramp.md)（v1）与 [ADR-0049](../docs/adr/0049-trace-schema-v2-and-upstream-recording.md)（v2）；术语见 [`CONTEXT.md`](../CONTEXT.md) 的「离线回放」节。
> 一句话：用冻结的 trace 起一个本机 HTTP 服务替代模型网关，让**真实 `review-pi` 进程**在不调模型、不联网、不需要 key 的情况下跑完整检视；再按档位并发，量化这台机器在给定延迟下能扛多少 worker。

---

## 1. 前置

- Node.js ≥ 22（与仓库根一致）。
- 已 `pnpm install`，并构建过 CLI dist：

```bash
pnpm build:dist        # 或 pnpm --filter @baize/review-pi build
```

回放 spawn 的是真 bin（`packages/review-pi/bin/review-pi.js` → `dist/cli/main.js`），bin 有**产物新鲜度门**：src 比 dist 新会直接拒跑，先重建即可。

- 不需要模型 key、不需要改用户配置、不需要网络。回放服务只监听 `127.0.0.1`，lane 子进程会主动清掉 `http_proxy` / `https_proxy`。

## 2. 快速开始

在**仓库根目录**执行：

```bash
# 1) 单次回放（单 worker，不注入延迟）——最快回归
pnpm replay:once core-single-finding

# 2) 全场景（CI 同款）
pnpm test:replay

# 3) 带模拟延迟的并发阶梯（本地探极限）
pnpm replay:ramp core-single-finding --steps 1,5,10,20,30

# 4) 请求体变了，重录（会先真跑一次再回放自检，通过才覆盖）
pnpm replay:record core-single-finding
```

内置场景：

| 场景 | trace | MCP | 覆盖 | trace schema |
|---|---|---|---|---|
| `core-single-finding` | 6 interactions | 省略 | 主循环、单 finding、stdout、退出码 | v1 |
| `core-no-finding` | 6 interactions | 省略 | 空 findings、无 tips、无总结 | v1 |
| `reporting-single-finding` | 8 interactions（+2 oneshot） | stub | 完整路径、MCP 上报序列、统一 tips | v1 |
| `rule-skill-single-finding` | 7 interactions | 省略 | 规则 Skill 独立会话、主/skill 候选联合裁定、skill 转录与规则包缓存 | v2（2 个 toolsVariants） |
| `shard-two-file` | 12 interactions | 省略 | `maxShardChars=10000` 触发两片、每片六相位、跨片 findings 合并、片级产物 | v2 |

用真网关重录（响应字节来自线上，trace 格式不变）：

```bash
node scripts/offline-replay/run.mjs record --scenario core-single-finding \
  --upstream-base-url https://<gateway>/v1 \
  --upstream-api-key "$REPLAY_UPSTREAM_API_KEY"
```

## 3. 命令面

```text
node scripts/offline-replay/run.mjs <record|once|ramp|help> [选项]
```

子命令等价于根 `package.json` 的脚本（`pnpm replay:* <场景>` 会把场景名接在 `--scenario` 后面）：

| 子命令 | pnpm 脚本 | 作用 | 是否起真实 CLI 进程 |
|---|---|---|---|
| `record` | `replay:record` | 录一条 trace：真跑一次并抓请求/响应，随后立即回放自检 | 是（2 次） |
| `once` | `replay:once` | 单次或指定并发回放 + 语义断言 | 是（N 次） |
| `ramp` | `replay:ramp` | 进程级并发阶梯，出 Markdown / JSON 报告 | 是（逐档 × 多次） |
| — | `test:replay` | 逐个场景跑 `once`（CI 门） | 是（每场景 1 次） |

退出码：`0` = 全部断言通过；`1` = 任一 lane 失败、任一请求未命中、安全阀拒绝或参数错误。ramp 本身不因「没测到高档位」失败——停止原因写进报告。

## 4. 参数总表

### 4.1 通用（三个子命令都认）

| 选项 | 默认 | 说明 |
|---|---|---|
| `--scenario <id\|path>` | —（必填） | 场景 id（`scripts/offline-replay/scenarios/<id>.json`）或 JSON 路径 |
| `--trace <path>` | 场景里的 `trace` | 覆盖 trace 路径；可用绝对路径 |
| `--run-dir <dir>` | `replay-runs/<时间戳>-<场景>` | 本次运行产物目录（gitignored） |
| `--model <id>` | 场景里的 `model` | 覆盖请求里的模型 id（同时决定 `/v1/models` 回包） |
| `--timeout-ms <n>` | `120000` | **单个 CLI 进程**的墙钟上限；超时杀进程树 |
| `--latency-mode none\|fixed` | 见 §5 | 延迟模式 |
| `--latency-ms <n>` | `0` | 固定延迟毫秒；给了值会把 `none` 自动升级为 `fixed` |
| `--latency-jitter <r>` | `0` | 抖动比例（`0.2` = ±20%），按 seed 确定性生成 |
| `--seed <n>` | `42` | 抖动种子 |
| `--mcp off\|stub` | 场景里的 `mcp.mode` | 是否挂 MCP 业务 tool stub |

### 4.2 `record` 专属

| 选项 | 默认 | 说明 |
|---|---|---|
| `--store-requests` | 关 | 额外写 `<trace>.requests.json`（完整请求体 sidecar，**不入库**） |
| `--no-verify` | 关 | 跳过「录完立即回放自检」；只建议调试录制器时用 |
| `--upstream-base-url <url>` | — | 真网关 base（与 `reviewer.baseUrl` 同口径，含 `/v1` 等前缀）；也可用 `REPLAY_UPSTREAM_BASE_URL` |
| `--upstream-api-key <key>` | — | 作为 `Authorization: Bearer` 注入；也可用 `REPLAY_UPSTREAM_API_KEY`。**不写进 trace** |
| `--upstream-timeout-ms <n>` | `120000` | 单次上游请求超时；超时回 500，录制失败 |

缺省录制源是仓库内 canned 语料，此时场景必须声明 `corpus`（`one-finding` / `no-finding` / `reporting` / `skill-single-finding` / `shard-two-findings`）。给了 `--upstream-base-url` 就忽略 `corpus`，直接代理真网关。

录制会把响应体与 `--store-requests` sidecar 落盘前做路径脱敏（`<lane>` / `<rule-skill>` / `<fixture-repo>` / `<repo-root>` / `<home>`）；脱敏不参与指纹，指纹在脱敏前已按归一化请求体算好。

### 4.3 `ramp` 专属

| 选项 | 默认 | 说明 |
|---|---|---|
| `--steps <a,b,c>` | `1,2,4,8,16,32`（或场景 `ramp.steps`） | 并发档位，必须严格递增；最后一档即本次测量上限 |
| `--warmup <n>` | `1` | 每档先跑 n 轮不计入统计 |
| `--measure <n>` | `3` | 每档测量轮数 |
| `--max-rss-mb <n>` | 物理内存 × 0.8 | 进程树峰值 RSS 阈值，超了停阶梯 |
| `--max-handles <n>` | `20000` | 进程树峰值句柄数阈值（Windows 有值，Linux 通常 `null`） |
| `--no-overhead-baseline` | 关 | 跳过「同场景 latency:none」的 harness 开销基线 |

## 5. 模拟延迟

延迟语义是**单次模型调用的总耗时**（不是逐帧 TTFT）：命中一条 interaction 后先 `sleep`，再一次性写完整响应体。

| 场景 | 默认延迟 |
|---|---|
| `once` | 场景声明的值（内置场景全是 `none`） |
| `ramp` | `fixed 1500ms / jitter 0.2 / seed 42`；场景自己声明 `fixed` 时用场景值 |

关闭 ramp 的缺省延迟：`--latency-mode none`。

**安全阀**：启动前校验 `ms × (1 + jitter) < 0.5 ×` 对应产品超时，否则拒绝启动并给一行原因。

| 调用面 | 上限口径 |
|---|---|
| 检视回合 | 180 s（`limits.timeouts.reviewTurnMs` 缺省） |
| 一次性模型调用（报文 / 总结） | 90 s（`limits.timeouts.oneShotMs` 缺省） |
| MCP stub | 场景里的 `mcp.timeoutMs` |

回放 lane 生成的配置固定 `limits.retry.*Attempts = 1`（ADR-0051）：回放按请求体 SHA-256 严格命中同一 interaction，失败响应重放多次仍是同一失败，重试没有收益，只会让请求计数与断言失真。产品侧的缺省重试策略（3 次尝试）不适用于回放。

per-interaction 可用 trace 里的 `latencyMs` 覆盖全局（例如给报文/总结单独 300 ms）：

```json
{ "kind": "oneshot", "requestHash": "sha256:…", "latencyMs": 300, "response": { … } }
```

## 6. 场景文件

路径：`scripts/offline-replay/scenarios/<id>.json`。完整示例（`reporting-single-finding` 精简版）：

```json
{
  "schemaVersion": 1,
  "id": "reporting-single-finding",
  "corpus": "reporting",
  "trace": "packages/review-pi/testdata/traces/reporting-single-finding.json",
  "fixture": {
    "repo": "packages/review-pi/testdata/repos/sample",
    "mrDiff": "packages/review-pi/testdata/golden/vul4j-1.diff"
  },
  "model": "deepseek-v4-flash",
  "mcp": { "mode": "stub", "latencyMs": 0, "timeoutMs": 10000 },
  "latency": { "mode": "none", "ms": 0, "jitter": 0, "seed": 42 },
  "timeoutMs": 120000,
  "ramp": { "steps": [1, 2, 4, 8, 16, 32] },
  "expect": {
    "findings": [
      { "file": "README.md", "line": 1, "severity": "P2", "title": "Sentinel finding title", "rule": "sentinel-rule" }
    ],
    "phaseRecords": 6,
    "rounds": 1,
    "tips": "present",
    "tipFilePaths": ["README.md"],
    "tipCounts": [1],
    "mcpCalls": ["startTask", "mrReviewResult", "mrReviewResult", "saveReviewSummary", "endTask"],
    "mcpFilePathCounts": ["README.md", "src/main/java/com/alibaba/fastjson/serializer/ObjectArrayCodec.java"],
    "mcpTipCounts": [1, 0]
  }
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `schemaVersion` | 是 | 目前只支持 `1`（场景 schema 与 trace schema 是两套版本号） |
| `id` | 是 | 场景名（也是默认 run 目录后缀） |
| `corpus` | 仅 canned 录制 | `one-finding` / `no-finding` / `reporting` / `skill-single-finding` / `shard-two-findings`；用 `--upstream-base-url` 录制时可省略 |
| `trace` | 是 | 相对仓库根的 trace 路径 |
| `fixture.repo` / `fixture.mrDiff` | 是 | 被检视的仓库快照与 diff，随 trace 绑定 |
| `model` | 是 | 请求模型 id，回放时同时用于 `/v1/models` |
| `ruleSkills` | 否 | 规则包**已解压目录**列表，按顺序展开成重复的 `--rule-skill` |
| `strictRuleSkill` | 否 | `true` = 追加 `--strict-rule-skill`（装载失败即报错） |
| `split.maxShardChars` | 否 | 写进 lane 配置 `limits.split.maxShardChars`（≥ 10000）；用小值触发分片 |
| `mcp.mode` | 否 | `off`（默认）/ `stub` |
| `mcp.latencyMs` | 否 | stub 每次调用延迟，默认 0 |
| `mcp.failTools` | 否 | 这些工具回 `isError`（测旁路降级） |
| `mcp.eventTool` | 否 | 若配置里要挂事件工具，写工具名 |
| `mcp.timeoutMs` | 否 | MCP 客户端超时（写进 lane 配置），默认 60000 |
| `latency.*` | 否 | 见 §5 |
| `timeoutMs` | 否 | 单 CLI 进程上限，默认 120000 |
| `ramp.steps` | 否 | ramp 缺省档位（命令行 `--steps` 优先） |

`expect` 各级含义：

| 字段 | 断言内容 |
|---|---|
| `findings[]` | `runs/reviews_en.json` 与 stdout 的 findings 投影（`file` / `line` / `severity` / `title` / `rule`）一致且等于期望；顺序无关 |
| `phaseRecords` | 审计 `phaseLog` 条数（六阶段 = 6） |
| `rounds` | 审计 `rounds` |
| `tips` | `absent` / `present` / `any`（`any` = 不检查） |
| `tipFilePaths` / `tipCounts` | `reviews_tips_zh.json` 的文件组顺序与每组条数；统一路径下每组按 12 键校验 |
| `mcpCalls` | `once` 单 worker 的完整 tool 名序列；ramp 多 worker 时按「单次序列 × workers」做聚合计数 |
| `mcpFilePathCounts` / `mcpTipCounts` | `mrReviewResult` 的 `filePath` 序列与每条 `reviewTips` 条数；8 字段类型与 `level` 四档枚举一律校验 |
| `shards` | `run.json.shards[].index` 与期望一致；每片 `transcriptFile` / `auditFile` 存在；聚合审计 `audit.shards[].index` 一致 |
| `stderrContains` | stderr 必须包含的片段数组（如 `分片检视 2 片`） |
| `ruleSkill` | 审计 `ruleSkill` 恰好 1 条，匹配 `name` / `kind`，`digest` 为 64 位小写十六进制 |
| `skillPassLog` | 审计 `skillPassLog` 条数；每条 `skill` 必须是非空字符串 |
| `skillTranscript` | 存在 `*-skill-<name>-r1.json`，且转录含 `Host platform:` 平台提示 |
| `ruleSkillCache` | `true` = 校验 `<taskDir>/.cache/rule-skills/dir-<digest>/` 下的 `SKILL.md`、`.rule-skill-ready`、`rules/` |

规则 Skill 场景的零散字段示例：

```json
{
  "ruleSkills": ["packages/review-pi/testdata/rule-skills/general-code-review"],
  "strictRuleSkill": true,
  "expect": { "ruleSkill": { "name": "general-code-review", "kind": "dir" }, "skillPassLog": 1, "skillTranscript": "general-code-review", "ruleSkillCache": true }
}
```

分片场景把 `split.maxShardChars` 压到 10000，再用 `two-file-shard.diff`（11,545 字符、两块各 < 10000）稳定切两片：

```json
{ "split": { "maxShardChars": 10000 }, "expect": { "shards": [1, 2], "stderrContains": ["分片检视 2 片"] } }
```

> 断言只测**行为等价**，不逐字匹配文案，也不比对 runId / 时间戳。

## 7. ramp 报告怎么读

产物：`replay-runs/<时间戳>-<场景>/report.md`（人读）+ `report.json`（机器）。

```text
| workers | success | median | p95 | min | max | peak RSS | peak handles | 备注 |
```

- `success`：该档测量轮次里通过的 lane 数 / 总数。
- `median` / `p95` / `min` / `max`：**主口径含模拟延迟**的 wall 时间。
- `peak RSS` / `peak handles`：进程树峰值（best effort，400 ms 采样；Linux 句柄通常 `n/a`）。
- 报告头同时给 `harness 基线（latency none）` 与 `模拟延迟带来的增量`——两者相减才是回放器自身开销。

停止条件（任一命中即停当前阶梯）：

1. 某 lane 失败（退出码 / 断言 / 超时）；
2. 该档 `p95 > 2 × 基线中位数`；
3. 峰值 RSS 或句柄数超阈值；
4. 到达配置的最后一档（正常结束）。

另有全局超时：`最高档 × 单 run 上限 × 1.5`，超出记 `global-timeout`。

> 「并发上限」只在**同一台机器 + 同一延迟档位**下有意义；换一个都不可以直接比数字。ramp 不进 CI 门禁。

## 8. 排障

### 8.1 请求未命中（最常见）

```text
replay: 请求未命中 trace（sha256:3e52f49eb183…）
  最近邻：sha256:000000000000…（kind=review）
  messages[2] 首次不同：live(role=user, 269 chars) vs trace(role=user, 261 chars)
  当前请求体（前 2000 字符）：
    {…}
```

含义：真实请求体的 SHA-256 不在 trace 里。常见原因与处理：

| 现象 | 原因 | 处理 |
|---|---|---|
| 第 1 条就未命中 | 提示词 / 工具定义 / `max_tokens` / 模型 id 变了 | 重录该场景 |
| 中途某轮未命中 | 夹具仓或 diff 改动导致工具结果/消息拼接变化 | 恢复夹具或重录 |
| `model` / `max_tokens` 一行差异 | 配置或 CLI 参数与录制口径不同 | 用 `--model` 对齐，或重录 |
| 消息逐条一致但整体 hash 不同 | 字段顺序 / 多出未知字段 | 看当前请求体，对照录制时代码 |

恢复手段：`pnpm replay:record <场景>`。需要看原文时加 `--store-requests`，对照 `<trace>.requests.json`。

### 8.2 其它

| 现象 | 处理 |
|---|---|
| `review-pi: failed to spawn` / bin 拒跑 | `pnpm build:dist` 重建（产物新鲜度门） |
| `模拟延迟超过安全阀，拒绝启动` | 降低 `--latency-ms` / `--latency-jitter`，或确认产品超时口径 |
| ramp 首档就失败 | 先跑 `pnpm replay:once <场景>`，把 harness 问题与并发问题分开 |
| 峰值 RSS / handles 是 `n/a` | 本机没有可用的进程查询后端（`wmic` / PowerShell / `ps`）；不影响正确性结论 |
| 中文输出乱码（Windows） | 控制台代码页问题：`[Console]::OutputEncoding=[Text.Encoding]::UTF8`；报告文件本身是 UTF-8 |

## 9. 重录与新增场景

### 9.1 什么时候必须重录

trace 与以下输入**逐字节绑定**，任何一处变化都会让指纹失配：

- `packages/review-pi/src` 里的系统提示词、工具定义、阶段消息、会话拼装；
- `testdata/repos/sample` 夹具仓与 `testdata/golden/{vul4j-1,two-file-shard}.diff`；
- `testdata/rule-skills/general-code-review/` 内容（规则包 digest、skill 会话提示词与 `location` 都会变）；
- `REVIEW_MODEL_ID`、`max_tokens` 缺省、`reasoningEffort` 等请求参数。

lane 绝对路径不在这个清单里：v2 trace 声明了 `requestNormalization` 后，lane 目录在算指纹前已被替换成 `<lane>`，换 worker / 换运行都不会失配。

重录命令见 §2 第 4 条；`record` 会先跑一次录制，再**用同一份 trace 立即回放一次**，两步断言都过才覆盖原文件。

### 9.2 新增一个场景

1. 在 `lib/corpora.mjs` 加一份 canned 回复（或复用现有五份）；
2. 在 `scenarios/` 加 JSON，声明 `corpus` / `fixture` / `trace` / `expect`（规则 Skill 加 `ruleSkills`，分片加 `split`）；
3. `pnpm replay:record <新 id>` 生成 trace；
4. `pnpm replay:once <新 id>` 确认断言；
5. `pnpm test:replay` 确认全场景。

> v2 已覆盖单遍检视、规则 Skill（S5）与两片分片（S4）。新增多会话路径时优先复用：主会话 7 工具 / skill 会话 8 工具（`bash`）已由 `toolsVariants` 表达；分片只需把 `split.maxShardChars` 压小并断言 `shards`。

### 9.3 v2 已落地（ADR-0049）

| 能力 | 状态 | 落地要点 |
|---|---|---|
| **S4 分片** | 已落地 | 场景 `shard-two-file`：`split.maxShardChars=10000` + `two-file-shard.diff`（11,545 字符）稳定切两片；每片六相位，findings 合并为 Alpha.java / Beta.java 两条；断言 `shards: [1,2]`、片转录/片审计可寻址、stderr 含「分片检视 2 片」 |
| **S5 rule-skill** | 已落地 | 场景 `rule-skill-single-finding`：`--rule-skill` 目录装载 + `--strict-rule-skill`；主候选 + skill 候选在 Phase 6 联合裁定；断言审计 `ruleSkill` / `skillPassLog`、`*-skill-<name>-r1.json` 转录、`.cache/rule-skills/dir-<digest>/` |
| **真网关录制代理** | 已落地 | `record --upstream-base-url/--upstream-api-key/--upstream-timeout-ms`；原样转发请求、原样冻结响应（含 SSE 与 content-type），trace 格式不变；key 不落盘，响应体/sidecar 落盘前脱敏 |
| **trace schema v2** | 已落地 | `toolsVariants[]`（按 digest 去重）+ 每 interaction `toolsRef`；可选 `requestNormalization.placeholders`。v1 trace 继续可读、继续原样哈希 |

两项 schema 决策一句话：`toolsVariants` 解决「同一 trace 里工具面不止一份」，`requestNormalization` 解决「请求里含运行期绝对路径」。两者都只抹**结构性差异**，模型 / 消息 / 工具 / 参数 / diff 内容仍全量参与哈希。

S4 / S5 / 真网关录制三者的共同点：都不改产品 CLI，只改工具链与数据。决策细节见 [ADR-0049](../docs/adr/0049-trace-schema-v2-and-upstream-recording.md)。


## 10. 产物与目录

```text
replay-runs/<时间戳>-<场景>/          # gitignored
├── report.json                       # once / ramp 的机器结果
├── report.md                         # 仅 ramp
└── workers/<label>/
    ├── config.json                   # 每 lane 的只读配置（指向共享回放服务）
    ├── cwd/                          # 独立工作目录（session 索引 / review-result.json）
    ├── home/                         # 独立 HOME（绝不读真实 ~/.PiAgent）
    └── tasks/t-1/                    # 独立任务目录（run.json / reviews_en.json / audit）
```

**为什么两个都要隔离**：任务目录里的 `run.json` / `reviews_en.json` / `reviews_tips_zh.json` 是固定名，`.cache/rule-skills/<digest>` 解压无锁；cwd 里的 session 索引与 `review-result.json` 是 last-writer-wins。只隔离一个就会互相覆盖。
