## M-001 MCP 业务 tool 之间的固定 5 秒沉降

- **状态**：生效中（2026-11-07 起）
- **来源**：[ADR-0053](adr/0053-mcp-task-tool-fixed-settle-gap.md)（修订 [ADR-0045](adr/0045-mcp-business-task-tools.md) 的调用时机）
- **代码位置**：`packages/review-pi/src/cli/main.ts`（`waitTaskToolSettle`）、`packages/review-pi/src/mcp/task-tools.ts`（`TASK_TOOL_SETTLE_MS` / `resolveTaskToolSettleMs`）

### 现象

客户端发送顺序是严格串行的（`startTask` → 全部 `mrReviewResult` → `saveReviewSummary` → `endTask`，每个调用都 await），但前端实际收到的回调顺序会错：总结 / 结束可能早于部分片级结果。判断根因在服务端异步处理——`tools/call` 返回 2xx 只代表收到/入队，落库与推送前端是异步的。

### 现在的处理

- 最后一条 `mrReviewResult` 结束后，固定等 `TASK_TOOL_SETTLE_MS = 5000 ms` 再发 `saveReviewSummary`；
- `saveReviewSummary` 调用结束后，再等 5000 ms 才发 `endTask`；
- 只在业务上报实际开启且走到对应阶段时等；业务关闭 / 建连失败 / 未走到总结的失败路径不等待；
- 两段等待各打一行 stderr（`MCP 固定等待 5000ms（… → …）`）。

### 风险

- **不是正确性保证**：服务端处理延迟超过 5 秒时仍可能乱序；只是把窗口缩小；
- 启用业务上报的每次运行固定多约 10 秒；
- 前端若改为直接消费事件通道，`run.end` 仍可能早于业务调用（事件在 `run/review-run.ts` 内就发出），本措施不覆盖该路径；
- 进程测试依赖专用 env `PIAGENT_TEST_TASK_TOOL_SETTLE_MS` 才能不慢 10 秒——这是一个只为测试存在的生产代码分支。

### 清账条件（全部满足后删除）

1. 服务端给业务调用提供**顺序保证**（每条带 `seq`，或提供「片级结果已全部收齐」的完成标记 / ack）；
2. 客户端在 `mrReviewResult` / `saveReviewSummary` / `endTask` 报文里带上该字段，服务端按 `taskId` 排序或缓冲后再推前端；
3. 删除 `waitTaskToolSettle` 的两处调用与 stderr 行；
4. 删除 `TASK_TOOL_SETTLE_MS` / `TASK_TOOL_SETTLE_ENV` / `resolveTaskToolSettleMs`，以及 `cli/bin.process.test.ts` 里 `runBin` 的 env 注入和顺序用例的 30 ms 覆盖；
5. 同步改 ADR-0053 状态注记、ADR-0045 后续修订、`CONTEXT.md` 与两份手册里「固定 5 秒」的说明；
6. 顺带复核 `run.end` 与业务调用的先后：若前端仍消费事件通道，考虑把 `run.end` 扣到最终 `flush`（或 `endTask` 之后）。

### 验证

- `pnpm --filter @baize/review-pi exec vitest run src/mcp/task-tools.test.ts`
- `pnpm --filter @baize/review-pi exec vitest run src/cli/bin.process.test.ts -t "MCP 业务 tool"`
- 手工：启用 MCP 跑一次，stderr 应出现两行 `MCP 固定等待 5000ms（…）`，且远端回调顺序为 `saveReviewSummary` 在全部 `mrReviewResult` 之后、`endTask` 最后。
