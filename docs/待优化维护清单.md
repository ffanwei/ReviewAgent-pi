# 待优化维护清单

记录已上线但**不打算长期保留**的临时措施与技术债。每条都写清：现象、现在的处理、风险、什么时候可以删。新条目追加在末尾，编号 `M-<三位序号>`；删除时保留条目并把状态改为「已清账（日期 + 提交）」，不直接删行——历史可追溯。

## M-001 MCP 业务 tool 之间的固定 5 秒沉降

- **状态**：生效中（2026-11-07 起）
- **来源**：[ADR-0053](adr/0053-mcp-task-tool-fixed-settle-gap.md)（修订 [ADR-0045](adr/0045-mcp-business-task-tools.md) 的调用时机）
- **代码位置**：`packages/review-pi/src/mcp/task-lifecycle.ts`（`createTaskLifecycle` 内的 `settle`、`TASK_TOOL_SETTLE_MS` / `resolveTaskToolSettleMs`）；两段沉降都由 facade 拥有

### 现象

客户端发送顺序是严格串行的（`startTask` → 全部 `mrReviewResult` → `saveReviewSummary` → `endTask`，每个调用都 await），但前端实际收到的回调顺序会错：总结 / 结束可能早于部分片级结果。判断根因在服务端异步处理——`tools/call` 返回 2xx 只代表收到/入队，落库与推送前端是异步的。

### 现在的处理

- 最后一条 `mrReviewResult` 结束后，固定等 `TASK_TOOL_SETTLE_MS = 5000 ms` 再发 `saveReviewSummary`；
- `saveReviewSummary` 调用结束后，再等 5000 ms 才发 `endTask`；
- 只在业务上报实际开启且走到对应阶段时等；业务关闭 / 建连失败 / 未走到总结的失败路径不等待；
- 两段等待各打一行 stderr（`MCP 固定等待 5000ms（… → …）`）。

### 风险

- **不是正确性保证**：服务端处理延迟超过 5 秒时仍可能乱序；只是把窗口缩小；
- 启用业务上报的每次运行固定多约 10 秒；
- 前端若改为直接消费事件通道，`run.end` 仍可能早于业务调用（事件在 `run/review-run.ts` 内就发出），本措施不覆盖该路径；
- 进程测试依赖专用 env `PIAGENT_TEST_TASK_TOOL_SETTLE_MS` 才能不慢 10 秒——这是一个只为测试存在的生产代码分支。

### 清账条件（全部满足后删除）

1. 服务端给业务调用提供**顺序保证**（每条带 `seq`，或提供「片级结果已全部收齐」的完成标记 / ack）；
2. 客户端在 `mrReviewResult` / `saveReviewSummary` / `endTask` 报文里带上该字段，服务端按 `taskId` 排序或缓冲后再推前端；
3. 删除 `createTaskLifecycle` 里的 `settle` 调用与两行 stderr（`mrReviewResult → saveReviewSummary` / `saveReviewSummary → endTask`）；
4. 删除 `TASK_TOOL_SETTLE_MS` / `TASK_TOOL_SETTLE_ENV` / `resolveTaskToolSettleMs`，以及 `cli/bin.process.test.ts` 里 `runBin` 的 env 注入和顺序用例的 30 ms 覆盖；
5. 同步改 ADR-0053 状态注记、ADR-0045 后续修订、ADR-0086、`CONTEXT.md` 与两份手册里「固定 5 秒」的说明；
6. 顺带复核 `run.end` 与业务调用的先后：若前端仍消费事件通道，考虑把 `run.end` 扣到最终 `flush`（或 `endTask` 之后）。

### 验证

- `pnpm --filter @baize/review-pi exec vitest run src/mcp/task-tools.test.ts`
- `pnpm --filter @baize/review-pi exec vitest run src/cli/bin.process.test.ts -t "MCP 业务 tool"`
- 手工：启用 MCP 跑一次，stderr 应出现两行 `MCP 固定等待 5000ms（…）`，且远端回调顺序为 `saveReviewSummary` 在全部 `mrReviewResult` 之后、`endTask` 最后。

## M-002 `--model` 旗标与模型降级机制（ADR-0093 阶段 2）

- **状态**：生效中（阶段 1 已落地，2026-11-16；**阶段 2 未完成**）
- **来源**：[ADR-0093](adr/0093-single-source-review-model.md)（检视模型单源）；取代 [ADR-0080](adr/0080-model-fallback-on-model-not-found.md)
- **代码位置**：`packages/review-pi/src/cli/args.ts`（`stripIgnoredModelFlag` / `parseModelFlag` / `KNOWN_SMOKE_FLAGS`）、`cli/main.ts`（废弃告警与 `requireExplicitModelDefault`）、`shared/config.ts`（`reviewer.modelFallback` 告警与 `ModelFallbackMode`）、`provider/model-fallback.ts`（已无调用点）

### 现象

阶段 1 只为迁移保留接口：`review --model` 仍被接受但值被忽略并告警；`reviewer.modelFallback` 仍被识别但恒 `off`、只产生装载期告警。两者在配置面和 CLI 面都表现为“可写但无效”，长期保留会让读者误以为仍有覆盖 / 兜底能力。

### 现在的处理

- `review` 在旗标循环前整段剥离 `--model`，只把“传过”这一事实回显并告警；
- `smoke --model` 仍是合法的探针目标覆盖（唯一保留点）；
- `reviewer.modelFallback` 装载期告警，生效值恒 `off`，模型探测与替换代码不执行；
- `provider/model-fallback.ts` 保留纯函数与单测，文件头标 `TODO(ADR-0093 阶段2)`。

### 风险

- 调用方可能继续传 `--model`（告警可见，但行为已不是他们以为的覆盖）；
- 配置里的 `modelFallback` 看似可调，实际无效果；
- `model-fallback.ts` 是无调用点的死代码，阶段 2 前不得重新接线。

### 触发信号（满足后下一个版本执行）

1. 仓库内已无 `--model` 调用方：`scripts/offline-replay`、`.agents/skills` 两份 eval skill、`scripts/eval` 与文档都不再产生该旗标；
2. 平台侧确认不再传 `--model`（接入点 id 已迁到 `model.default`）。

### 清账条件（全部满足后删除）

1. 删除 `args.ts` 的 `stripIgnoredModelFlag`、review 面的 `ignoredModel` 字段与 `parseModelFlag` 的 smoke 分支；`--model` 改为专用错误「已移除，检视模型取 model.default」（旗标 token 再留一个版本后清理）；
2. 删除 `main.ts` 的废弃告警、`requireExplicitModelDefault` 的 smoke 例外与 `args-echo` 的 `--model` / 已忽略标记；
3. 删除 `shared/config.ts` 的 `reviewer.modelFallback` 键、告警、`ModelFallbackMode` / `MODEL_FALLBACK_MODES`；
4. 删除 `provider/model-fallback.ts`、其单测、`contracts/run.ts` 的 `ModelFallbackRecord` 与审计 / `run.json` / delivery 的 `modelFallback` 写入（历史产物仍可读，不回写）；
5. 同步改 ADR-0093 状态注记、`CONTEXT.md`（模型降级词条删除）、两份手册与 `PiAgent.example.jsonc`；
6. 删除本条目并改为「已清账（日期 + 提交）」。
