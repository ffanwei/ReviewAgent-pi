# 开发指南：仓库结构与文件职责

**状态**：现行（2026-11-17，对应 ADR-0098 结构重整后的形态）
**维护约定**：新增 / 删除 / 改名模块或目录时，同步更新本文；历史路径口径见
[`docs/adr/README.md`](adr/README.md)（ADR-0098 之前的 `zoneb/`、`experiment/`
等写法按当时形态读）。

本文回答两个问题：

1. 这个目录 / 文件是干什么的？
2. 一次检视从入口到产物，应该按什么顺序读？

## 3. `src/` 模块总览

`src/` 的 19 个目录并不都在同一层。按依赖方向可以分成四层：

```
入口 / 表现层     cli, repo-spike
引擎层            run, loop, knowledge, gate, tools, mcp, export
横切能力层        shared, provider, observability, audit, analysis, codeintel
叶子 / 基础层      contracts, diff, finding, testing
```

| 模块 | 一句话 | 主要下游 |
|---|---|---|
| `contracts/` | 纯类型 / 常量契约，零内部依赖 | 所有模块 |
| `diff/` | unified diff 的统一解析层（4 种视图 + 路径 / hunk 语法） | run, gate, analysis |
| `finding/` | Finding 合并键与 10 字段运行时校验 | run, gate |
| `shared/` | 配置、重试、解析、过滤、目录等横向能力 | 所有上层 |
| `codeintel/` | ripgrep / 文件系统 / tree-sitter wasm 装载 | analysis, tools, run |
| `analysis/` | 静态分析（Zone B）：符号、引用、调用链、仓库上下文 | tools, run |
| `gate/` | 候选归一与拦截（Evidence Gate / 位置范围 / skill 合并） | loop |
| `loop/` | 六阶段主循环、消息、提示词、缓存断点、候选修复 | run |
| `knowledge/` | 规则 Skill 装载与独立 skill 检视会话 | loop, run |
| `tools/` | 七个 `review.*` 工具 + skill bash + 适配 / 预算 / 账本 | loop, run |
| `provider/` | 模型接入：端点、pi-ai 客户端、一次性调用、探针、重试策略 | run, loop, cli |
| `observability/` | 请求时间线（`request-timeline.jsonl`） | provider, cli |
| `audit/` | 审计 JSON 落盘 | run |
| `run/` | 检视引擎：入口、单遍 / 分片执行、diff 输入、边界、合并、记录 | cli |
| `export/` | 产物落盘：转录、reviews、run 布局、session 索引、OpenCode 兼容 | run, cli |
| `mcp/` | MCP 事件上报 + 四个业务 tool（任务生命周期） | cli |
| `cli/` | 进程入口、参数、交付链、渲染、tips、总结、子命令 | — |
| `repo-spike/` | 一次性全仓探针：枚举 → 合成「全新增」diff → 按目录/文件数分组调用 `runReviewOutcome`；**不是产品化 scan**（无覆盖账本 / scan 提示词 / 评测口径） | cli |
| `testing/` | 测试夹具加载器（不进 dist） | 测试 |
| `index.ts` | 公开导出面：`runReview` + 契约类型 + 网关解析 / 探针 | 包使用者 |

## 5. 测试布局

- **单元 / 集成测试与源码同目录**：`X.ts` ↔ `X.test.ts`。共 104 个测试文件；
  `tsconfig.build.json` 排除 `src/**/*.test.ts`，`dist` 与 npm 包不含测试。
- **进程级测试**用 `*.process.test.ts` 命名（`cli/bin.process.test.ts`、
  `cli/config.process.test.ts`），会 spawn 真实 CLI；与普通单测共用同一
  vitest 配置。
- **测试夹具**在 `src/testing/`（只被测试 import，build 排除）。
- **根包测试**在 `tests/`，只覆盖 `scripts/` 工具链的纯函数。
- 不把测试搬到独立目录：同居便于“改哪个文件就看哪个测试”，打包隔离已由
  build 配置解决；若将来要分档执行，优先用 vitest project 拆快 / 慢，
  而不是搬目录（详见 ADR-0098 的讨论记录）。

## 7. 文件多时怎么读

- 先用第 3 节的四层划分定位：入口 → 引擎 → 横切 → 叶子，不需要逐个目录翻。
- 编辑器的 **file nesting** 可以把 `*.test.ts` 折到同名源文件下，目录视图会立刻
  少掉 104 行。
- `bin/`、`dist/`、`testdata/`、测试文件、以及 gitignored 的本地目录都属于
  “不必先读”的面；产品逻辑集中在 `src/` 的五个核心模块：
  `cli`（含 `delivery`）/ `run` / `loop` / `tools` / `knowledge`。
- 新增文件时先问“它属于哪一层、哪个模块”，再按本文的模块表落位；新增模块
  需要先写 ADR。
