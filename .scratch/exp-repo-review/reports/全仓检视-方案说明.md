## 1. 目标与边界

### 1.1 目标

在现有 MR/diff 检视之外，增加「无 diff 的全仓检视」能力，并在一个真实 Java 仓库上验证三件事：

1. **能跑通**：整仓文件枚举、分组、逐组检视、结果合并；
2. **成本可控**：文件数 / 字符数 / 工具调用 / 轮次 / 超时都有显式上界；
3. **准确率可评估**：产出可定位到真实文件行，能被模型判官与人工逐条复核。

### 1.2 本轮不做

- 不把全仓扫描做成 `limits.group.enabled` 的开关翻版；
- 不改 `review-run.ts` / `loop/*` / `gate/*` 的 MR 主路径；
- 不测召回（无逐行 GT），召回留 R-06b；
- 不把全仓结果与 iterF91 / AACR 的 MR 指标混报；
- 不承诺 `repo-spike` 是最终产品形态——它是 R-04 前的探针。

## 2. 总体架构

```text
仓库快照（git 工作树）
  │
  ├─ enumerateRepoFiles      git ls-files + untracked；目录/后缀/二进制/大小过滤
  │
  ├─ groupRepoFiles          directory / files / language / none
  │                          文件数 + 字符数双上限；maxGroups 护栏
  │
  ├─ synthesizeGroupDiff     每组把文件合成为「全部新增」unified diff
  │                          +行号 = 真实文件行号
  │
  ├─ runReviewOutcome × N    每组一次现有 MR 流水线（六阶段 + 候选门 + tips）
  │                          组并发有界；组失败不影响其他组
  │
  └─ merge                    findings / usage / coverage 合并
                             → repo-spike-result.json
                             → runs/<group>/runs/run.json
```

核心取巧：**不修改 MR 流水线**，只为它合成一份合法的 diff。这样分片、六阶段、证据门、候选门、输出都能复用；代价是提示词仍把既有代码说成「本次新增」（语义债，R-04 产品化时替换 scan Zone A）。

### 2.1 为什么不是「review 命令少一个 diff 参数」

diff 在现有实现里同时承担五层职责：

| 层 | diff 的作用 | 全仓扫描的替代 |
|---|---|---|
| 输入 | 哪些文件/行要检视 | 文件树 + 过滤规则 |
| 覆盖分母 | 覆盖账本的 hunk | 文件 × 区域三态 |
| 证据范围 | finding 必须落在变更 hunk ±N | 真实文件行 ±N |
| 提示词语义 | 「本次新增」「回归风险」 | 整文件 / 既有行语义（待 R-04） |
| 评测口径 | MR GT | 全仓 GT / 注入缺陷（R-06b） |

所以本轮先做独立探针，再定产品契约。

## 3. 核心设计决策

### 3.1 合成「全新增」diff

每个文件写成：

```diff
diff --git a/<path> b/<path>
new file mode 100644
--- /dev/null
+++ b/<path>
@@ -0,0 +1,N @@
+<文件每一行>
```

效果：

- 现有流水线认为整文件都是新增，不会因为「不在 diff 里」丢弃 finding；
- `+` 行号恰好等于真实文件行号，行锚点成立；
- 不需要给 `runReviewOutcome` 增加 repo 模式分支。

### 3.2 确定性枚举与过滤

- git 仓库：`git ls-files -z` + `git ls-files -z --others --exclude-standard`；
- 非 git：递归 walk；
- 排除目录（`.git`、`node_modules`、`dist`、`build`、`target`、`vendor`、`generated`、`testdata` 等）；
- 排除文件名（lockfile）与后缀（`.min.js`、`.map`、`.d.ts`）；
- 源码扩展名白名单；
- 8 KB 二进制嗅探；空文件、超大文件、符号链接跳过并留原因；
- 输出按路径排序，两次枚举字节一致。

### 3.3 分组与预算

| 策略 | 键 | 适用 |
|---|---|---|
| `directory`（缺省） | 路径前两段 | 保留模块边界 |
| `files` | 按排序切固定文件数桶 | 只想控成本 |
| `language` | 扩展名 | 多语言按规则分组 |
| `none` | 每文件一组 | 精确定位 / 重跑 |

双上限：

- `maxFilesPerGroup`：单组文件数；
- `maxGroupChars`：单组估算字符数（文件大小 + diff 头开销）；
- 单文件超限 → `group-too-large`，整文件跳过，**不截断**；
- `maxGroups`：组数护栏，超限显式失败，不静默截断；
- `maxFiles`：全局文件数上限，按排序截断并留原因。

### 3.4 执行预算与并发

全仓最大的风险是「模型在一个组里无限读文件」。本轮加了三层封顶：

| 预算 | 缺省 | 本轮探针 |
|---|---|---|
| `maxRounds` | 3 | **1** |
| `maxToolCalls`（实际执行的工具调用） | 100 | **15** |
| `maxToolAttempts`（含被 retrieval 预算跳过的调用） | 不限 | **20** |
| `limits.retrieval.maxReadsPerFile` | 不限 | **1** |
| `limits.retrieval.maxConsecutiveEmptySearches` | 不限 | **2** |
| `limits.retrieval.maxReadCharsPerRun` | 不限 | **120,000** |
| `reviewTurnMs` | 180s | **90s** |
| `reviewTurnAttempts` | 3 | **1** |
| `streamAttempts` | 3 | **1** |

这些值只注入 `repo-spike` 的 `ReviewRuntime`；`DEFAULT_REVIEW_RUNTIME` 不变，MR 路径零漂移。

组并发本次用 3（契约上限 5）。并发不是越高越好：网关、内存、单组上下文都会成为瓶颈；3 组 + OCR 2 子任务可稳定共存，总并发 5。

### 3.5 与 MR 路径的隔离

新增模块与命令，不修改 MR 核心：

```text
新增：
  src/repo-spike/{types,enumerate,group,synthesize-diff,runtime,output,run}.ts
  src/cli/repo-spike-command.ts
修改（仅参数/分发/运行时类型）：
  src/cli/args.ts
  src/cli/main.ts
  src/shared/review-runtime.ts   # 新增可选 maxToolCalls / maxToolAttempts
  src/loop/agent-review-loop.ts  # 读取可选预算；缺省行为不变
未修改：
  src/run/review-run.ts
  src/run/pass-runner.ts
  src/run/shard-planner.ts
  src/run/coverage-ledger.ts
  src/gate/*
  src/loop/system-prompt.ts / phases.ts / messages.ts
```

隔离证据：独立 `--out`、独立 `runsRoot`、独立 `caseId` 前缀；MR 全包测试 1267 passed / 1 skipped；MR 提示词未改，不需要重录 replay。

### 3.6 行锚点与输出

- `Finding.line` = 真实文件行号（1-based）；
- `Finding.file` = 仓库相对 POSIX 路径；
- 不引入 `lineType`（没有 added/context 概念）；
- `Finding.tips` 随候选产出，按文件分组不依赖变更行；
- 聚合产物 `repo-spike-result.json`：
  - `mode` / `repoPath` / `files` / `groups` / `findings` / `usage` / `coverage` / `skippedFiles` / `errors`；
  - 组内保留 MR 兼容的 `run.json` / `audit` / `reviews_all.json`；
  - 不写 `mrReviewResult` / `baseSha` / `headSha`。

### 3.7 规则 Skill 透传

`--rule-skill` / `--rule-skill-zip` / `--skill` 直接透传到 `runReviewOutcome`；每组独立加载并运行一次规则 Skill 会话。本轮实测未装载规则包（裸检视），以对比工具本身。

## 5. 实测结果摘要

### 5.1 覆盖与耗时

| 指标 | ReviewAgent-pi | OCR |
|---|---:|---:|
| 检视文件 | 1,390 / 1,390（255/255 组） | 1,388 / 1,390 |
| 墙钟 | **207.5 min**（主跑并发 3 + 补跑并发 2） | **285 min 分片执行**（+36 min 空档；并发 2→4） |
| 失败组 | 0；主跑被宿主内存保护停在 253 组，缺失 2 组已补跑 | 0 |

### 5.2 Token

| 指标 | ReviewAgent-pi | OCR | 比值 |
|---|---:|---:|---:|
| 未命中输入 | 5.63M | 10.29M | **1.83x** |
| 缓存命中 | 57.46M | 79.31M | 1.38x |
| 输出 | 5.54M | 5.91M | 1.07x |
| 总 token | **68.63M** | **95.51M** | **1.39x** |
| 每文件总 token | 49.4k | 68.8k | 1.39x |
| 每千行总 token | 356.0k | 495.4k | 1.39x |

### 5.3 准确率（模型判官）

| 指标 | ReviewAgent-pi | OCR |
|---|---:|---:|
| 产出 | 1,342 findings | 3,561 comments |
| 抽样 | 120（严重级分层） | 150（严重级分层） |
| VALID / INVALID / UNCERTAIN | 85 / 19 / 16 | 79 / 36 / 35 |
| Precision | **0.82** | **0.69** |

分档：

| 工具 | 高档 | 中档 | 低档 |
|---|---|---|---|
| 我方 | P0 0.75（3/4）、P1 1.00（34/34） | P2 0.88（30/34） | P3 0.56（18/32） |
| OCR | critical 1.00（32/32）、high 1.00（23/23） | medium 0.63（17/27） | low 0.21（7/33） |

### 5.4 已人工复核的 P0 样例

| 文件:行 | 断言 |
|---|---|
| `SandboxManager.java:137` | Python 沙箱 `allowAllAccess(true)`，可越权访问宿主文件/进程/网络 |
| `AESCryptUtils.java:34` | AES 密钥硬编码为 `public static final`，可解密全部已存 API Key |
| `RequestContextThreadPoolWrapper.java:236` | 使用 `ThreadPoolExecutor` 但未 import，server-core 无法编译 |

两侧都找到了真实缺陷；OCR 的 high/critical 也有真实样例（请求头凭证泄漏、workspace 硬编码、Reactor 顺序错误等）。

## 6. 结论

1. **默认全仓检视走我方路径**：更高 precision（0.82 vs 0.69）、更少噪声、更低 token。
2. **OCR 可作为高档补充**：只取 high/critical 时 precision 1.00，但覆盖收窄到 23%。
3. **成本差距来自输入组织**：组级合成 diff 让整文件只进一次上下文；OCR 逐文件 agent 循环会重复读关联文件。
4. **两侧都需要「档位过滤」**：我方 P3（0.56）、OCR low（0.21）都是噪声集中区；消费方应按严重级/置信度过滤。我方 P0–P2 precision 0.93（占 88%）。
5. **不能从 precision 推 recall**：本轮未测召回；R-06b 用注入缺陷/真实修复回滚补齐。

### 6.1 重要限制

- 我方主跑在 **253/255 组**时被 Claude Code 的后台内存压力机制停止，这是**宿主资源保护，不是命令失败**。随后用 `--files` 精确补跑缺失的 2 组（12 文件），最终 **255/255 组、1,390/1,390 文件**；207.5 min 是两次执行时间之和，不含中间空闲。
- 单仓、单模型、单次运行；没有重复实验方差。
- 我方是 `repo-spike` 探针，提示词仍是 MR 语义（合成「全新增」diff）；行锚点正确，但「本次新增」措辞会误描述既有问题。
- OCR 跳过 PLAN / PROJECT_SUMMARY；DEDUP 在 3 个批次解析失败并保留原始 comments，可能抬高 comment 数与噪声。
- 模型判官与检视模型同源，存在同偏好偏差；关键结论已用人工样例复核。

## 7. 产品化路线

```text
R-01 契约（已完成）
  ├─ R-02 文件枚举（已完成）
  ├─ R-03 分组与预算（已完成）
  │    └─ R-04 执行路径（已完成，repo-spike 形态）
  │         ├─ R-05 输出契约（已完成）
  │         └─ R-07 增量扫描（TODO）
  ├─ R-06 全仓对照（已完成）
  └─ R-06b 召回（TODO）
```

下一步优先级：

1. **scan 专用 Zone A**：去掉「本次新增」措辞，改成整文件 / 既有行 / 覆盖纪律；
2. **产品化命令 `repo-review`**：保留 dry-run、分组、预算、Skill 透传；
3. **覆盖账本**：文件 × 区域三态（candidate / no-issue / not-reached），补 R-04 的 `not-reached` 归因；
4. **规则召回**：语言级规则索引 + 触发信号 + 预算，避免全量规则注入；
5. **R-06b 召回**：合成缺陷注入 / 真实修复回滚，precision + recall 一起报；
6. **第二仓复跑**：Dubbo（30.9 万行生产 Java）或 Kestra（20.7 万行）。
