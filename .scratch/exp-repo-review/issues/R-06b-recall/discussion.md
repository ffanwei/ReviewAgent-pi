# R-06b 讨论归档

## 2026-11-25 · 召回是否可测、是否本轮做

**问题**：能验证召回吗？这个仓是不是没有标准的召回数据？

**结论**：

- 该仓没有标准的全仓逐行 GT。全仓召回的分母是「所有真实缺陷」，不存在权威全集；GitHub PR 评论只覆盖变更行且噪声大，不是全仓 GT。
- AACR-Bench 里有 `alibaba/spring-ai-alibaba` 的 2 个样本（`3555a95` / `4bc7305`），但它们是 diff 级人工评论，commit 与本次快照 `17e26ff` 不同，不能直接复用。
- 当前快照是 `--depth 1` 浅克隆，没有历史修复记录可回滚。

**可行路径（按保真度/成本）**：

1. 真实修复回滚：`git fetch --unshallow`，选 10–20 个 bug-fix commit，副本里 `git apply -R` 回滚，跑全仓；命中 = finding 落在修复 hunk ±N 行。保真度最高，筛选与判定成本高。
2. 合成缺陷注入：20–30 个语义缺陷模板注入真实文件，跑同一配置；recall = 命中/注入，同时报注入文件 precision。成本可控，但模板偏教科书缺陷。
3. 人工 PR 评论对照：只对评论所在行判断是否被全量 findings 覆盖，得到「人类已发现缺陷的召回下限」。成本低、分母不完整。

**决定**：本轮暂不测 recall，后续可能做。若启动，建议先做 20 条合成注入，再做 10 条真实修复回滚抽样。
