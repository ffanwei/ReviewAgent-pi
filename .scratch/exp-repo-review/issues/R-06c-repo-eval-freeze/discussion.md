# R-06c 讨论归档

## 2026-11-26 · 仓级冻结评测集是什么、标准答案哪里来

**问题**：R-06 v2 冻结集是什么？仓级检视有没有标准测评集？OCR 有没有相关仓检视测评？
标准答案哪里来？

**结论**：

- “R-06 v2 冻结集”不是已有资产，是建议名称：把 R-06 从单仓一次对照升级为
  版本固定、可复跑、可做回归的仓级评测集。
- 公开界没有面向“无 diff 全仓检视”的广泛采用标准集；AACR-Bench / iterF91 都是
  MR / diff 级。OCR 公开 benchmark 只覆盖 PR，`ocr scan` 没有公开仓级评测。
- R-06 是探索性对照：单仓 `spring-ai-alibaba@17e26ff`、1,390 生产 Java 文件、
  只测 precision 抽样（我方 0.82 / OCR 0.69），没有逐行全仓 GT，也没测 recall。
- 冻结集要冻结：仓库 SHA、检视范围、GT、运行配置、prompt / Skill hash、判官
  rubric 与种子、基线、运行器；任一项变化升版本。
- 标准答案不是“找”来的，是“造”出来的：
  - 真实修复回滚：保真度最高，但只覆盖历史上被修过的 bug；
  - 合成缺陷注入：最可控，但必须声明“注入召回 ≠ 自然召回”；
  - 人类 PR 评论：只能做召回下限，不是全仓缺陷全集；
  - 静态分析 / 漏洞库：只能做候选池，需人工确认；
  - 专家审计：局部可信，无法覆盖全仓。
- precision、coverage、cost 不需要全仓缺陷全集；只有 recall 需要构造封闭缺陷集。
- 建议首版：40–60 条真实回滚 + 60–100 条合成注入 + 可用人类评论下限 +
  30–50 个负样本文件；双人标注、第三人仲裁、盲评、行号容忍、GT 版本化。
- 与现有任务关系：R-06b 先验证召回口径；R-06c 再把 precision / recall / coverage /
  cost 合并成冻结集。

**决定**：2026-11-26 仅记录方案，**先不做**。不新增评测代码、不建脚本、不改 CLI /
workflow；后续启动时再补首版仓库列表、注入模板与标注排期。
